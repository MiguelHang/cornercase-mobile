# Upstream gaps

What the app cannot do because cornercase lacks it. No workarounds: each gap names the upstream issue or the proposal.

- **Conversation history**: cornercase gives only an agent's last message (`read --last-message`): the newest text of the assistant, also halfway through a turn, and nothing older, as 0.13.19 answers. So the chat's thread is short: your last send, which the app keeps while its `Chat` lives, and one message of the agent, the one you answered until a new one replaces it; nothing older, and nothing said from the Mac (see Chat › The thread).
- **No event when the last message grows**: `events` gives `status`, `exited`, `opened` and `closed` (cornercase 0.13.24 on `origin/main`, read on 2026-11-09), and an agent's message grows within a turn without a status change. So while an agent works and its screen is in sight, the chat reads `read --last-message` every 10 s (see Chat › Reading the message). Proposal: a `message` event naming the pane whose last message changed, or `read --last-message --follow`, a line per change.
- **`/cli` endpoint**: the bridge stands in for it during development (see Bridge).
- **`requests --follow` and `input --follow` have no name in the contract**: they are subcommands of the CLI, not operations of the socket, so `contract --json` lists neither and the app cannot check them before using them; `REQUIRED` leaves them out, and 011 falls back to single commands when they do not start, telling a CLI that lacks them by clap's refusal (see Connection › The contract, and the ordered queue).
- **`requests` carries no bytes**: a line's `stdin` is text, so a command with bytes (`paste-file … -`, a pasted image) runs as its own command, a connection of its own, in its turn in the queue (see Connection › the ordered queue).
- **A pasted file holds the next `send`**: `paste-file` types the path as a person's paste does, so the pane counts as drafting, and a `send` waits until that draft is submitted or lapses after 60 s without input (upstream's `held-sends.md`), past the chat's `--timeout 30`. There is no way to say that the draft is the sender's own. So after attaching an image the chat's `Send` goes with `--force`, which also skips the refusal over a dialog or a poll, until a send or the row's `Enter` succeeds (see Chat › Attaching an image). The chips live in the chat's screen, so leaving it with an image unsent forgets them while the path stays in the agent's input: back on the screen, a plain `send` is held and ends in `nothing was sent` until the paste lapses. Proposal: `paste-file --then-send`, or a `send` that names the paste it follows, so the text joins the path without `--force`.
- **No sized view that watches without claiming**: a `view` that is active, sized and showing a tab claims it as it opens, and only such a view counts as seen; a passive `surface --tab` never does. So the phone either sizes the tab, as the terminal does by default since 043 (see Terminal › Fitted by default), or watches it through `surface --tab`, as the terminal with its switch off and the chat's question do (the Mac keeps its size); then opening an agent in `done` sends `mark --pane P --reviewed`, which clears the Mac's `✓` without a view or a size (see Terminal › Passive with the switch off, and Chat › Seen from the phone). What is left: reviewed is not seen, so the Mac's notices go on while the phone shows the agent passively, and one that turns `waiting` or `done` in sight can notify on the Mac before the `mark` arrives; and `--reviewed` also clears `pending`, with no mark that clears only `done`, so a `pending` set on the Mac between the phone reading `done` and the `mark` arriving is lost. Proposal: `view --no-claim`, a sized and visible view that sees and streams `surface --view` but leaves the tab's size to the window (Proposal for upstream, task 033, its draft 03).
- **The pending question is not data**: `status` says that an agent is `waiting`, with `dialog: true` while a dialog shows, but not what it asks, nor its options, and the agent's records are not the contract. So the chat reads the question from the screen: a passive `surface` of the agent's tab, cropped from the highest rule over the last rows with text, with a button per numbered option (see Chat › The question), as upstream's own Telegram bot does (`messenger::choices`, #248). It is a heuristic over how each agent draws its menus, it loses the top of a question taller than its 24 rows, and it cannot tell a description from an option's label, a multi-select from a single choice, nor which tab of several questions is open. Proposal: `read --pending --pane P --json` (or a `question` field per pane in `status --json` and its `status` events) that gives, while a pane waits: the agent; where the question comes from (`AskUserQuestion`, a tool's permission with the tool and its command, a Codex approval); each question with its header (the tabs of several questions) and which one is open; its options, each with its number, label and description, which one is selected, and whether several can be chosen; whether it takes free text; and `null` once nothing is pending. Until then the chat reads the screen; once upstream gives it, the chat uses it instead of the crop. No issue is open for it yet: it goes with the proposals of task 033.
- **A pane's status does not say since when**: `status` gives each pane's status without the time it took it, so the board knows it only for the changes the app saw as `status` events; an agent already in its status when the app connects shows no time, and every time is dropped when the app may have missed events (a new `events` stream, a `dropped` event; see Board › Since when). Proposal: a `since` per pane, the RFC 3339 time of its last change, in `status --json` and its `--follow` lines.
- **`send`, `keys` and `read` take no `--boot`**: in 0.13.19 only `close` and `rename` do, so a send queued before a server restart can reach the pane that inherited its id, and a read can show another agent's message. Today the queue's `reconnect` skips what was queued before a reconnection, and the chat counts its agent as gone for good once the rows turn `null` (see Chat › Gone), which narrows the window without closing it. `mark` takes `--boot` since 0.13.30, with no feature naming it, and an older CLI refuses it, so the chat's `mark --reviewed` goes without it until the app asks for 0.13.30 (see Chat › Seen from the phone). Proposal: `--boot` on `send`, `keys` and `read`, failing with `stale-boot` as `close` does.
- **No fold per client, nor folded at birth**: a pane's `collapsed` (`collapse` and `expand --pane`, feature `agent-folds`) is one flag shared by every client, unfolded by default and unfolded by the Mac's reveal, and upstream left out on purpose an orchestrator starting folded. The board wants its branches folded by default and without changing the Mac's sidebar, so the app keeps its own fold per machine, `boot` and pane and ignores the flag (see Board › Tree and folding). Proposal: a fold per client, or an option for an agent with children (a flow's orchestrator at least) to start folded.
- **No models per agent**: `account list` says which agents are installed but not which models each one takes, so the start form's model is free text, sent as `--model=` and checked only by the agent (see Starting work). Upstream: usecornercase/cornercase-terminal#704.
- **`issue list` takes no query and has no pages**: only `--source`, `--closed`, `--assignee`, `--author` and `--cached` (0.13.19, and 0.13.28 on `origin/main`, read on 2026-11-10), and each tracker gives at most 100 issues. So the issues' search runs on the phone over the rows it got, and when a tracker gave 100 a line asks to narrow the filters (see Starting work › From an issue). Proposal: `--query` passed to each tracker's own search, and a cursor to ask for the next page.
- **No prompt of one's own with an issue**: `start` refuses `--prompt` with `--issue` (clap's `conflicts_with`, and the server's `give the prompt or the issue, not both`), while `flow run --issue` takes one (feature `flow-issue-prompt`). So the issue's form shows the prompt cornercase will use, read-only, and has no field to add to it (see Starting work › From an issue). Proposal: `start --issue --prompt`, the user's words after the issue's prompt.
- **`issue sources`, `issue list` and `issue read` take no `--boot`**: after a server restart a project's id can name another project, so a list or an issue read around it can be another project's. The issues' screens read again each time the connection comes back, as it does after every restart: that narrows the window without closing it. Proposal: `--boot` on the three, failing with `stale-boot` as `close` does.
- **`changes file` and `changes viewed` take no `--boot`**: after a server restart a workspace's id can name another workspace, so a diff read around it can show another workspace's file, and a mark sent around it can land on that workspace. The queue's `reconnect` skips a mark queued before a reconnection, and the stream opens again only on a new session that lists the workspace (see Changes and files › Following the list), which narrows the window without closing it. Proposal: `--boot` on both, failing with `stale-boot` as `close` does.
- **`files list`, `files read` and `files search` take no `--boot`**: after a server restart a workspace's id can name another workspace, so a tree, a file or a search read around it can show another workspace's files. The files screens follow no stream and do not look at the `Store`'s session, so nothing narrows that window; only an id the new session does not hold is refused, and then the screen says the workspace was closed (see Changes and files › Files). Proposal: `--boot` on the three, failing with `stale-boot` as `close` does.
- **`changes viewed` with a stale digest answers OK**: upstream stores the mark without reading the file, so a mark for a version that has changed since, or for a digest read during a write, applies to nothing and says nothing; the phone learns it only from the next summary, which shows the file unmarked (see Changes and files › Viewed). Upstream rejected a `conflict` here on purpose, since it would need the file read or a model in memory.
