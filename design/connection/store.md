# Store

A topic of [Connection](../connection.md): the live state of one Mac's cornercase on the phone, the streams that feed it, and how it reconnects.

- **One `Store` per machine** (`crates/core/src/store.rs`, `store/`): the session (`Snapshot`, `cli/status.rs`: groups, projects, workspaces, tabs, panes and their agents), since when each pane is in its status (below), the rest of the app (`app`, a `serde_json::Value` until a screen reads it), the state of the connection and the ordered queue. The app keeps one, the active machine's, and turns its changes into Tauri events (In the app, below). Like the queue, the core starts nothing: `Store::new` returns a handle that can be cloned and the driver as a future the caller spawns, so the tests run it on a paused clock and tokio gains no feature.
- **Three streams**, opened on the winning route's transport in this order: `events --json --notices`, `status --follow --json` (the `watch` stream) and `status --app --follow --json` (`app`). Each line of `status --follow` is the whole session, not a patch, so the newest one replaces the session; an `app` line replaces the app; an event goes to the channel. `events` opens first so that nothing that happens while the first snapshot is on its way is missed.
  - **`watch`, not `view`**: cornercase-gpui follows the session with `view --cols --rows`, but a view is registered on the server: what it shows counts as seen (it takes a tab's `✓` away and silences the Mac's notices for it), and it needs a size. A phone listing its agents must mark nothing as seen, so `status --follow` gives the same snapshot without a view and without effects; `view` stays for the terminal screen (019, 020). This departs from the ticket's "use what gpui uses", not from its intent.
  - **`--notices`**: the `notice` events ("claude needs you") are what the phone wants most, and the CLI refuses the flag without the `notices` feature, hence that feature in `REQUIRED` (Connection › The contract).
  - Not followed: `status`'s `machines` (the servers cornercase links, not the phone's machines), `view` and `surface` (019 to 022), and the reads that order nothing (`read`, `changes`, `files`), which stay one-shot beside the `Store`.
- **Lines are read leniently**: every type of the snapshot takes defaults and ignores the keys it does not know (`machines`, `shown`, `view`, `layout`, …), and a `path: null` is `None`. A pane has no `name` in the JSON; the UI uses `title` and `program`. An event whose `event` the app does not know (`recap`, `bell`, `clipboard`, …), or a known one of an unexpected shape, becomes `What::Other` with its whole JSON, never an error, so what upstream adds breaks nothing (serde's `#[serde(other)]` only takes unit variants, so the line is read as a `Value` first). A line that does not parse is skipped and goes out as `Change::Warning(Json)`, which names the kind of mistake and never the text, and the stream goes on. A one-shot `status --json` has no `revision` at its root (only `config.revision`), so it reads as 0; the `Store` never reads it.
- **States** (`Connection`): `Connecting` while it picks a route, reads the contract and waits for the first snapshot; `Connected { route }` from the first snapshot of `status --follow`, not when the streams open, so a stream that opens and dies at once never shows as connected; `Retrying { in, error }`; `Offline`, while the phone has no network (Network); and four that stop until `resume_now`, since retrying fixes none of them and the UI must say what does:
  - `Missing`: the contract lacks something in `REQUIRED` (all or nothing, Connection › The contract).
  - `Unauthorized`: every route refused the token or has none, or the machine has no routes; scanning the Mac's code again fixes it.
  - `NotPaired` (058): a cornercase route answered `403` on `/cli`, the Mac having forgotten the phone; it wins over the other routes' errors, below `Outdated`, since a LAN that hangs while Tailscale says `403` must not retry for ever. Forgetting the phone while it is connected ends its streams (`Dropped`), and the next attempt gets the `403`, so it ends here and not in retries. Scanning the code again pairs it again.
  - `Incompatible`: a route answered that cornercase is too old (`Outdated`, which wins over any other route's error, since it names the fix), the contract is too new for the app (`ContractTooNew`) or does not parse; updating cornercase or the app fixes it.
  - A failed `pick_route` with any other error retries with the first error that is not a refusal.
  - Rejected: putting these states in `Retrying` (a loop that never succeeds, and nothing tells the user what to do), retrying `Incompatible` on its own (an update on the Mac is seen at the next `resume_now`, when the app returns to the foreground).
- **What ends a connection**: any of the three streams ending ends the other two (dropping them, so the bridge ends their commands) and goes to `Retrying`, once the lines already read are applied. An exit 0 is `StreamEnded`, its own error rather than `Dropped`, which says the network failed; another code is `Failed`, or `StaleBoot` for 4, as `transport::printed` reads it; a transport error stays as it is. While `Retrying`, the last session and app stay, so the list does not flicker while the network comes back; `Connection` says they may be stale.
- **Backoff**: 1, 2, 4, 8 s, then 15 s for ever, the same for a failed `pick_route` and for a stream that ends. It goes back to 1 s only once a connection got a snapshot, not when `contract` answers: a server whose `contract` answers and whose `status --follow` fails at once would otherwise be tried every second. No jitter: a phone retries one Mac, not a crowd the server must spread out.
- **`resume_now()`** (013 calls it when the app returns to the foreground): from `Retrying` it skips the wait; from `Connected` it drops the streams and picks a route again at once, keeping the state, since iOS leaves sockets half-open while it suspends the app and the transport would only notice after its 45 s of silence; from a state that stopped it tries once more. While connecting (picking a route, reading the contract, waiting for the first snapshot) a call does nothing, and calls made before an attempt starts count as one, so a burst of calls asks each route for its `contract` once. Rejected: doing nothing while `Connected` and trusting the 45 s, which would show stale data for that long after every return to the foreground.
- **Why it was woken**: `resume_now()`, `network_changed()`, `offline()` and `online()` send their reason (`Resume`, `store/resume.rs`) on the one channel the driver reads. A network change and `offline()` also interrupt an attempt in progress, which the return to the foreground does not; `offline()` goes to `Offline` from any state; while `Offline`, only `online()` and `resume_now()` start an attempt, and a failure with the network still down goes back to `Offline` rather than `Retrying`. Why each: Network.
- **A restart** (`boot`): one `BootWatch` follows the server's `boot` from both places it is read, each contract and each snapshot of `status --follow`, for the whole life of the `Store`. When it changes, the session and the app are emptied and `Change::Session` and `Change::App` go out, so that no id of the old server stays, since the new one may give it to something else. A snapshot of another boot is not applied: the queue moves at once to the transport the streams used, so nothing queued with the old ids runs while a route is picked again, the streams are dropped and a new attempt starts at once, without the backoff, which reads the contract again and moves the queue to its transport (below). That covers a restart between `contract` and the streams starting, also on the first connection, when there is no session to compare with, and the contract that follows then has the snapshot's boot, so it empties nothing a second time.
  - **`Store::boot`** reads the last `boot` the `BootWatch` saw, `None` before the first contract, so the app can tell whether a new URL is the active machine's (Machines › The same machine).
  - The two are compared because they are the same value: upstream writes both from `control::server_token()` (its `contract.md` › `boot`: "`status --json` carries it too"). Rejected: watching each place on its own, which let a first snapshot of a new boot through after a contract of the old one and emptied the session again at the next connection. Upstream rules out a server whose contract and snapshots disagree for ever, but the `Store` does not trust it: a second restart seen in a snapshot with no snapshot applied since the last one goes to `Retrying` with `StaleBoot`, through the backoff, rather than reconnecting at once again and again. Rejected: reading a contract with an empty `boot` as `Incompatible`, which covers one way to disagree and not the others.
  - A snapshot without a `boot` (a line of another shape, which the lenient types still read) is skipped and goes out as `Change::Warning(Json)`, like a line that does not parse, rather than counting as a restart.
  - A snapshot whose `revision` is not above the session's, of the same boot, is dropped, so a late line never replaces a newer session.
- **The queue lives in the driver**: the `Store` makes the `Queue` with the transport of its first connection (`Store::queue()` is `None` until then, and is made before the contract is checked, so `Missing` has one that nothing uses), and the queue's worker is polled inside the driver's future, so the caller spawns one future per machine and dropping the `Store` ends the queue too. Rejected: returning the worker for the caller to spawn, a second future to keep track of that could outlive the `Store`. The queue's `on_error` goes out as `Change::Warning`.
  - **`Store::transport()`** gives the transport the queue was last given (`None` until a route answers its `contract`), for a stream of its own that is neither one of the three nor a job of the queue, such as a pane's `surface --patches` (task 020) and a workspace's `changes list --follow` (025), and for the one-shot reads beside the queue (`read --last-message`, `design/chat.md`; `changes file`, `design/changes-and-files.md`), so they go to the same Mac by the same route as the queue. Each connection replaces it, so a caller reads it again every time it opens its stream or its read rather than keeping one that may be dead. Like the queue's, it is not emptied by a restart, `Retrying` or `Offline`: a read then fails with the transport's own error. Rejected: picking a route again for each read, a `contract` round trip that may land on another route.
  - **`queue.reconnect(transport)` on every connection after the first**: another route, a restart or a `resume_now` while `Connected`, since each `pick_route` builds new transports and the old one may be dead. Without a restart too, so the command in flight then gets `Unanswered` and what was queued before it `Skipped` (Connection › reconnect): accepted, since there is seldom a command in flight when the app returns to the foreground. Rejected: reconnecting only when `boot` changed, which would leave the queue on a transport that may be dead.
- **The channel of changes**: `changes()` gives each subscriber its own unbounded channel. `Change::Session` and `Change::App` carry nothing: a subscriber reads `session()`, `agents()` or `app()` from the handle, and another one is not sent while the last is unread, so a UI that does not read holds at most one of each however many snapshots come (one about every 500 ms while an agent works). `Event`, `Warning` and `Connection` go in order with their payload, since each one counts (the board takes "since when" from them, below). `Reopened` carries nothing and goes out each time the streams open again after the first time, since the events heard meanwhile are lost: whoever shows something an event would have changed reads it again (Chat › Reading the message › When it is read again). A subscriber whose receiver was dropped is removed at the next change. Rejected: tokio's `watch` (it keeps only the last value, so events would be lost), `broadcast` (a slow reader loses the oldest, a notice among them), the snapshot as the payload (the channel would grow with snapshots).
- **Since when** (`board::Since` in the `State`, `design/board.md` › Since when): the session says each pane's status but not when it took it, and the `status` events carry their `time`, so the `Store` keeps a record per pane. A `status` event of a pane fills it before the event goes out, so a subscriber that reads `agents()` on it sees the new time; each snapshot it applies reconciles it; `forget()` empties it with the session on a restart. `agents()` gives the board's rows from the session and the record, `None` while there is no session. Rejected: keeping the record in the app's forwarder, which the `agents` getter could not see without a second shared state.
- **Dropping the `Store`**: once the last handle is dropped the driver ends, and with it the streams, whose commands the bridge then ends, and the queue's worker. Unlike dropping the queue's own last handle, the jobs it still holds do not run: a caller waiting on one gets `Unanswered`.
- **The last route**: the `Store` keeps no winner of its own, since `pick_route` reads none (Connection › No lead for the last winner); `Connected { route }` gives the winner to the app, which saves it with `Machines::remember`. So the core's `Store` has no file to write and no lock on `Machines`. Rejected: the `Store` writing `Machines` itself, through a callback or a shared registry. Routes that change while a `Store` lives (scanning the code again) are the app's: `connect` makes a new `Store`. Routes the bridge tells after connecting are the exception: `Store::learn` hands them to the driver, which adds them to its copy of the machine before its next `pick_route`, without cutting the connection (Machines › Routes learned from the bridge).
- **The fixtures** (`crates/core/tests/fixtures/control/`): `watch/v1/snapshot.json`, `view/v1/snapshot.json` (the same with `view` and `controller`, to show that extra keys are ignored), `events/v1/*.json` and `app/v1/snapshot.json` are upstream's, from `origin/main` at `7f08441f` (0.13.19). `status/0.13.19.json` is `status --json` from an installed cornercase 0.13.19 on a server of its own: a temporary `HOME`, XDG folders and `CORNERCASE_SOCKET`, made-up projects (a group, a worktree, a split tab), and the temporary prefix replaced with `/home/me`, so nothing comes from a real Mac. Its panes run `bash`, since `/bin/sh` is bash on macOS. The contract fixture and the `watch` one come from different servers, so the `Store`'s tests answer `contract` with the real contract carrying the `watch` fixture's `boot`.

## In the app

- **One `Store`, the active machine's** (`src-tauri/src/state.rs`): `AppState` holds the machines, the identity and at most one `Active`, the machine with its `Store` and two tasks on Tauri's runtime, the driver and the forwarder. `connect` makes a new one every time, also for the machine already active, which is how changed routes are taken. Replacing or dropping `Active` aborts both tasks: the forwarder holds a clone of the `Store` to read `agents()`, so dropping the handle alone would leave the driver and its streams running. `machine_remove` drops it when the machine is no longer in the list afterwards, even if removing its secrets then failed, and sends `connection-changed` with `none`. Rejected: one `Store` per saved machine, streams to every Mac at once from a phone whose screens show one.
- **The forwarder** (`src-tauri/src/events.rs`) turns each change into events: `Connection` into `connection-changed`, a `Warning` into an error toast with the error's message, and `Session` and the `status` events into `agents-changed` with `agents()`, only when the rows differ from the last ones it sent. It keeps those last rows, so the snapshot that comes about every 500 ms while an agent works sends nothing until a row changes, and a `status` event sends one when it gives a row its time. One change after several unread snapshots sends the rows once. The other events and `App` give nothing until a screen reads them. Rejected: comparing in the WebView, which would still cross IPC on every snapshot. `Connected { route }` first saves the route with `Machines::remember`, then emits, so a UI that reads `machines_list` on `connected` sees it; a failed save adds an error toast and the connection stays. `remember` writes the small file with blocking IO inside the forwarder's task, once per connection and only when the route changed: accepted, since it holds a runtime worker for a moment; move it to `spawn_blocking` if it grows.
- **`resume_now` on the return to the foreground** (`src-tauri/src/lifecycle.rs`): on `RunEvent::WindowEvent` with `WindowEvent::Resumed`, which tao sends from `applicationWillEnterForeground` and `sceneWillEnterForeground`, once per window (the app has one). Not `RunEvent::Resumed`, which the task named: in Tauri 2.12.5 it is the event loop's `StartCause::Poll` (tauri-runtime-wry 2.12.3), not a return; the task's intent is kept. `WindowEvent::Suspended`, which also comes when the Control Centre is pulled down without leaving the app, does nothing: iOS suspends the app, and the return takes care of the sockets. That event exists only on mobile, so on the desktop nothing calls `resume_now`. `on_event` calls `resume`, which reads the state with `try_state`, since an event can come before `setup` manages it; without a `Store` it does nothing.
- **Network changes** (`src-tauri/src/network.rs`): the network plugin's paths, debounced, call `offline()`, `online()` or `network_changed()` on the active `Store`; the last network lives in `AppState`, so `connect` starts a new `Store` already `Offline` when the network is down (Network).
- **On start** (`setup` in `src-tauri/src/lib.rs`): the network plugin is registered with the builder; in `setup`, tauri-specta's `mount_events` first, since emitting an event it has not registered panics, then the identity and the machines are loaded into the state and managed, and the task that follows the network starts. Machines that did not load send no toast, which no WebView could hear yet: the UI gets the error from `machines_list` (`design/architecture.md` › Commands and events). The UI connects to the first machine while no `Store` runs (`design/architecture.md` › Commands and events).
- **Tests**: `connect`'s logic takes a `Launcher`, the transports per route and the `spawn`: the command passes the bridge's and Tauri's runtime, the tests a `FakeTransport` (the core's `test-util`) and their own runtime, on a paused clock for the backoff. They answer `contract` with the core's real contract fixture, read from its folder rather than copied. The wrappers, `Emit for AppHandle` and `resume` are tested on Tauri's `MockRuntime` (`design/architecture.md` › Commands and events); `run`, the mobile `foreground` and so `on_event`'s call to `resume` only by the simulator check below.
- **Checked live** on 2026-11-09 in the iPhone 17 simulator (iOS 27.2, Tauri 2.12.5) against the bridge on loopback and cornercase 0.13.19: the app connects and counts the panes the Mac's `status` has; with the bridge killed it goes to retrying within a few seconds, keeping the last session, and comes back on its own once the bridge starts on the same port. Thirty seconds in the background left the streams alive: the simulator does not suspend sockets the way an iPhone does. On the return, the three old commands had ended on the Mac within a second and three new ones were running, none left over. After `xcrun simctl terminate` the old commands ended within 3 s, and the next launch connected to the saved machine on its own, with the token from the Keychain. The app drops its WebSockets without a Close frame, so the bridge logs a reset, as for any cancelled command (Connection › Cancelling is dropping the future). Not checked yet: an iPhone, where iOS does suspend the sockets (029), and the queue (Connection › the ordered queue).
