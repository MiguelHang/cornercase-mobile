# Store

A topic of [Connection](../connection.md): the live state of one Mac's cornercase on the phone, the streams that feed it, and how it reconnects.

- **One `Store` per machine** (`crates/core/src/store.rs`, `store/`): the session (`Snapshot`, `cli/status.rs`: groups, projects, workspaces, tabs, panes and their agents), the rest of the app (`app`, a `serde_json::Value` until a screen reads it), the state of the connection and the ordered queue. 013 makes one per machine and turns its changes into Tauri events. Like the queue, the core starts nothing: `Store::new` returns a handle that can be cloned and the driver as a future the caller spawns, so the tests run it on a paused clock and tokio gains no feature.
- **Three streams**, opened on the winning route's transport in this order: `events --json --notices`, `status --follow --json` (the `watch` stream) and `status --app --follow --json` (`app`). Each line of `status --follow` is the whole session, not a patch, so the newest one replaces the session; an `app` line replaces the app; an event goes to the channel. `events` opens first so that nothing that happens while the first snapshot is on its way is missed.
  - **`watch`, not `view`**: cornercase-gpui follows the session with `view --cols --rows`, but a view is registered on the server: what it shows counts as seen (it takes a tab's `✓` away and silences the Mac's notices for it), and it needs a size. A phone listing its agents must mark nothing as seen, so `status --follow` gives the same snapshot without a view and without effects; `view` stays for the terminal screen (019, 020). This departs from the ticket's "use what gpui uses", not from its intent.
  - **`--notices`**: the `notice` events ("claude needs you") are what the phone wants most, and the CLI refuses the flag without the `notices` feature, hence that feature in `REQUIRED` (Connection › The contract).
  - Not followed: `status`'s `machines` (the servers cornercase links, not the phone's machines), `view` and `surface` (019 to 022), and the reads that order nothing (`read`, `changes`, `files`), which stay one-shot beside the `Store`.
- **Lines are read leniently**: every type of the snapshot takes defaults and ignores the keys it does not know (`machines`, `shown`, `view`, `layout`, …), and a `path: null` is `None`. A pane has no `name` in the JSON; the UI uses `title` and `program`. An event whose `event` the app does not know (`recap`, `bell`, `clipboard`, …), or a known one of an unexpected shape, becomes `What::Other` with its whole JSON, never an error, so what upstream adds breaks nothing (serde's `#[serde(other)]` only takes unit variants, so the line is read as a `Value` first). A line that does not parse is skipped and goes out as `Change::Warning(Json)`, which names the kind of mistake and never the text, and the stream goes on. A one-shot `status --json` has no `revision` at its root (only `config.revision`), so it reads as 0; the `Store` never reads it.
- **States** (`Connection`): `Connecting` while it picks a route, reads the contract and waits for the first snapshot; `Connected { route }` from the first snapshot of `status --follow`, not when the streams open, so a stream that opens and dies at once never shows as connected; `Retrying { in, error }`; and three that stop until `resume_now`, since retrying fixes none of them and the UI must say what does:
  - `Missing`: the contract lacks something in `REQUIRED` (all or nothing, Connection › The contract).
  - `Unauthorized`: every route refused the token or has none, or the machine has no routes; scanning the bridge's code again fixes it.
  - `Incompatible`: a route answered that cornercase is too old (`Outdated`, which wins over any other route's error, since it names the fix), the contract is too new for the app (`ContractTooNew`) or does not parse; updating cornercase or the app fixes it.
  - A failed `pick_route` with any other error retries with the first error that is not a refusal.
  - Rejected: putting these states in `Retrying` (a loop that never succeeds, and nothing tells the user what to do), retrying `Incompatible` on its own (an update on the Mac is seen at the next `resume_now`, when the app returns to the foreground).
- **What ends a connection**: any of the three streams ending ends the other two (dropping them, so the bridge ends their commands) and goes to `Retrying`, once the lines already read are applied. An exit 0 is `StreamEnded`, its own error rather than `Dropped`, which says the network failed; another code is `Failed`, or `StaleBoot` for 4, as `transport::printed` reads it; a transport error stays as it is. While `Retrying`, the last session and app stay, so the list does not flicker while the network comes back; `Connection` says they may be stale.
- **Backoff**: 1, 2, 4, 8 s, then 15 s for ever, the same for a failed `pick_route` and for a stream that ends. It goes back to 1 s only once a connection got a snapshot, not when `contract` answers: a server whose `contract` answers and whose `status --follow` fails at once would otherwise be tried every second. No jitter: a phone retries one Mac, not a crowd the server must spread out.
- **`resume_now()`** (013 calls it when the app returns to the foreground, 028 on a network change): from `Retrying` it skips the wait; from `Connected` it drops the streams and picks a route again at once, keeping the state, since iOS leaves sockets half-open while it suspends the app and the transport would only notice after its 45 s of silence; from a state that stopped it tries once more. While connecting (picking a route, reading the contract, waiting for the first snapshot) a call does nothing, and calls made before an attempt starts count as one, so a burst of calls asks each route for its `contract` once. Rejected: doing nothing while `Connected` and trusting the 45 s, which would show stale data for that long after every return to the foreground.
- **A restart** (`boot`): the contract's `boot` is watched with `BootWatch` from one connection to the next, and each snapshot's is compared with the session's. When either changes, the session and the app are emptied and `Change::Session` and `Change::App` go out, so that no id of the old server stays, since the new one may give it to something else. A snapshot of another boot is not applied: the streams are dropped and a new attempt starts at once, without the backoff, which reads the contract again and moves the queue (below). That covers a restart between `contract` and the streams starting, which the contract's `boot` cannot see.
  - Each boot is compared with the previous one from the same place, never the contract's with a snapshot's: both are the server's, but nothing in the contract promises the two keys are written alike, and the tests' fixtures come from different servers.
  - A snapshot whose `revision` is not above the session's, of the same boot, is dropped, so a late line never replaces a newer session.
- **The queue lives in the driver**: the `Store` makes the `Queue` with the transport of its first connection (`Store::queue()` is `None` until then, and is made before the contract is checked, so `Missing` has one that nothing uses), and the queue's worker is polled inside the driver's future, so the caller spawns one future per machine and dropping the `Store` ends the queue too. Rejected: returning the worker for the caller to spawn, a second future to keep track of that could outlive the `Store`. The queue's `on_error` goes out as `Change::Warning`.
  - **`queue.reconnect(transport)` on every connection after the first**: another route, a restart or a `resume_now` while `Connected`, since each `pick_route` builds new transports and the old one may be dead. Without a restart too, so the command in flight then gets `Unanswered` and what was queued before it `Skipped` (Connection › reconnect): accepted, since there is seldom a command in flight when the app returns to the foreground. Rejected: reconnecting only when `boot` changed, which would leave the queue on a transport that may be dead.
- **The channel of changes**: `changes()` gives each subscriber its own unbounded channel. `Change::Session` and `Change::App` carry nothing: the UI reads `session()` and `app()` from the handle, and another one is not sent while the last is unread, so a UI that does not read holds at most one of each however many snapshots come (one about every 500 ms while an agent works). `Event`, `Warning` and `Connection` go in order with their payload, since each one counts (015 may take "since when" from the events). A subscriber whose receiver was dropped is removed at the next change. Rejected: tokio's `watch` (it keeps only the last value, so events would be lost), `broadcast` (a slow reader loses the oldest, a notice among them), the snapshot as the payload (the channel would grow with snapshots).
- **Dropping the `Store`**: once the last handle is dropped the driver ends, and with it the streams, whose commands the bridge then ends, and the queue's worker. Unlike dropping the queue's own last handle, the jobs it still holds do not run: a caller waiting on one gets `Unanswered`.
- **The last route**: the `Store` keeps the winner in memory for its next `pick_route`, and `Connected { route }` gives it to 013, which saves it with `Machines::remember`. So the core's `Store` has no file to write and no lock on `Machines`. Rejected: the `Store` writing `Machines` itself, through a callback or a shared registry. Routes that change while a `Store` lives (scanning the code again) are 013's: it makes a new `Store`.
- **The fixtures** (`crates/core/tests/fixtures/control/`): `watch/v1/snapshot.json`, `view/v1/snapshot.json` (the same with `view` and `controller`, to show that extra keys are ignored), `events/v1/*.json` and `app/v1/snapshot.json` are upstream's, from `origin/main` at `7f08441f` (0.13.19). `status/0.13.19.json` is `status --json` from an installed cornercase 0.13.19 on a server of its own: a temporary `HOME`, XDG folders and `CORNERCASE_SOCKET`, made-up projects (a group, a worktree, a split tab), and the temporary prefix replaced with `/home/me`, so nothing comes from a real Mac. Its panes run `bash`, since `/bin/sh` is bash on macOS.
- Not checked live yet: nothing runs the `Store` until 013; it is tested with `FakeTransport` only, on a paused clock.
