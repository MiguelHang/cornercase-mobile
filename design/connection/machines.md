# Machines

A topic of [Connection](../connection.md): the Machines screen's side of the connection (027). It covers adding a machine from cornercase's code (058), pairing with cornercase's code, telling that a code belongs to a machine already saved and merging it, the routes learned from the machine, which route wins, names, removing and ordering routes, the active machine remembered between starts, switching it, and trying the other machines. How the screens look is in `design/look.md`; the bar's `not_paired` is in [The connection bar](bar.md).

- **Adding a machine**: scan the QR code that cornercase shows in Settings › Remote › Phone app (058; the bridge's before), with the `barcode-scanner` plugin (027), or paste its code, one per computer since 035. The empty screen's `Add machine` opens a form for the code and a name (Look › Forms); the rest is below.
- **`Try a demo`** (064, `design/demo.md`) is the link of a line of text, `No machine nearby? Try a demo` (`DemoOffer`, 068), under the empty screen's card and under `Add machine` in Machines, and hides with the form, as `Add machine` does; until 068 it was a plain button under the primary. Machines leaves it out while the Demo machine is listed, which is while the demo is on; the empty screen never shows with the demo on, since the Demo machine counts as one. A tap shows the board connecting to the demo, its id exported in the bindings as `DEMO_MACHINE`, before `demo_start`: the demo connects with no network at once, and the connection's events of a machine the screen does not show are dropped (`apply`), so showing it after would leave the bar on `Connecting`. Then the list is read again, for the bar's name and tag. Rejected: entering through `connect`, which only knows machines of the registry; reading the state again after `demo_start`, as on opening, which still loses an event that lands between the read and the screen.
  - **The Demo machine's `Edit` keeps only `Delete machine`** (`src/routes/Machine.svelte`): no name field and no routes, since `machine_rename` and the routes' commands act on the registry, which does not hold the demo, and answered `no saved machine has that id` in the simulator (T18). Its confirmation says `The demo ends, and nothing of it stays on this phone.` instead of the routes, secrets and access a saved machine loses.
  - **The code is checked before `machine_add`** (`src/lib/machineForm.ts`): trimmed, it must start with `ws://`, parse and carry a `code=` that is not empty. Each refusal has its own message under the field, so a paste cut short or an `http://` address is caught without a round trip. The core still parses the route; its `route_*` errors also go under the `Machine code` field, any other under the form, which stays open with what was typed.
  - **Sending it** (`AddMachine`, `src/lib/addMachine.svelte.ts`, a class with the form's fields in `$state`, so the steps are tested without a WebView): the form is busy from `machine_add` until the machine is handed over, and stays busy after, since it still shows while its card fades out and a second tap on `Add` would save the same machine twice, which 014 cannot remove. Only a refusal makes it rest again. A rejected IPC call goes under the form with its message, as the toasts tell it.
  - **An empty name takes the code's name, else its host** (Names, below).
  - **Once added**, the app goes to `home` at `Connecting…` (Machines stays open, on top of it), reloads the machines for the bar's name and connects. A `connect` that fails leaves the machine saved and says why in a toast, so that nobody adds it twice.
  - **The last `connect` asked wins** (`latestWins`, Switching, below): a double tap on `Add` or the first load meeting the form connects once, and a machine added while another connects ends up connected.
- **Adding by QR code or by pasting** (`src/lib/ui/UrlField.svelte`, `src/lib/scanner.svelte.ts`): one field, `Machine code`, with `Scan QR code` above it; the forms for adding speak of the machine and its code, not of routes (035). The same field serves `Add machine`, on the empty screen and in Machines, and a machine's `Add route`, so the forms share it rather than copy it. It takes cornercase's machine code, of one address or several (Pairing with cornercase's code, below). A code that is read fills the field and is sent at once, along the same path as a pasted one: it is checked with `checkUrl`, then by the core.
  - **The scanner's steps** (`Scanner`, a class with its state in `$state` and the plugin's calls passed in, so the tests drive every path without a camera):
    - It asks for the camera before scanning: `checkPermissions`, then `requestPermissions` if needed. On iOS 14 and later `scan` does not ask by itself; it rejects with "Camera permission denied or not yet requested", after it has already put the camera's view in.
    - Refused, it shows `Open Settings` (`openAppSettings`).
    - Any other failure, such as no camera (the simulator, the desktop) or the plugin's error, shows its message. The field for pasting stays usable under it in both cases.
    - Every way out calls `cancel` in a `finally`: a code read, `Cancel`, or an error. It also takes away `html.scanning`, so the camera's view never stays over the page and the page's ground always comes back.
    - `stop` takes `html.scanning` away itself before it calls `cancel`, rather than waiting for `cancel` to end the pending `scan`, and `UrlField` calls `stop` when it goes away in the middle of a scan (its form closed, its screen left): otherwise the page stayed hidden, the camera on and no `Cancel` in sight.
  - **`windowed: true`**: without it, the plugin's view covers the WebView with no way to close it, since it brings no button. In windowed mode the WebView turns transparent over the camera and the page draws its own frame and `Cancel` (Look › Scanning).
- **One code, one machine with every route** (`machine_add`, `Machines::add`, 035): a code of N addresses is saved as one machine with N routes, in the code's order, each with the secret cornercase's code was traded for, in the Keychain under its address. The tokens are all written before the file, which is written once, as for one route (Connection › The order of the writes). Then the app connects; the race picks the route (Which route wins, below). There is no step about routes: before 035 the user added the LAN's URL, then the Tailscale one, and accepted an offer to join them.
- **Pairing with cornercase's code** (058, `crates/core/src/machines/pairing.rs`, `paired_routes` in `src-tauri/src/commands/probe.rs`): cornercase 0.13.78 shows a code of the bridge's format with a pairing code in place of the token, `ws://<first>:<port>/?code=<32 hex>&also=<host>&name=<name>` (why that format: Bridge › The machine code), single use and valid for ten minutes, which the app trades for a secret of the phone's own.
  - **Parsing** (`MachineCode`): the pairing code is its only credential since 059, when `token=` stopped being the second one. It refuses, each with its own message and without repeating the code, a `code=` that is empty or given twice and one with characters outside `[0-9a-f]`; `Display` hides it. A `token=` is a parameter like any other the code does not know: without a `code=` the text has no pairing code (`RouteError::NoCode`, `NO_CODE` in the form), and beside one it is ignored. Rejected (the user, 2026-11-15): a message of its own for a code of the old bridge, which 059 had added, since no user ever had one (Bridge › Retired in 059). The scheme, the host, the port and the path are checked as the bridge's URL was, each with its own message, and the rest (`also=`, IPv6, `name=`) is read with the cases of upstream's own tests (`src/web/phone/code/tests.rs`).
  - **Trading it**: a WebSocket per address of the code to `ws://<host>:<port>/?code=…`, all at once within 10 s (`FuturesUnordered`, as the race), each with `User-Agent: cornercase-mobile/<version> (iOS)` or `(Android)`, which names the phone's row in cornercase's Settings (P4). Rejected: the phone's name, which `UIDevice.name` gives only with an entitlement since iOS 16. The first `{"secret": "<id>.<64 hex>"}` followed by a close 1000 wins and the others are dropped. One code serves one pairing: cornercase checks it before the upgrade without spending it and spends it after, so the losers get `403` or a close 1008, and one dropped after spending it but before its secret went out gives the code back (upstream's `design/phone-app.md`). Replies over 4 KiB are refused.
  - **Its failures**, each its own error and text: `403` or 1008 is `PairingRefused` (the code no longer works: it lasts ten minutes and serves once, so show another in Settings › Remote); 1011 is `PairingFailed` (the machine could not save the pairing); a secret that is not `<hex>.<hex>` is `MalformedSecret`, and nothing is saved; and when no address answers, `NoAnswer` with each address's error and the question whether phone app is on in cornercase and the phone on its network or on Tailscale, since a switch that is off and a machine asleep look the same (nobody listens). An answer wins over silence: one address that answered, with 1011 before a malformed secret before `403`, names the failure.
  - **Never in a message or a log**: neither the code nor the secret. The secret goes to `Secrets` as a route's token, under each cornercase route's key (Identity and secrets › The device's secret), never to `machines.json`, a `Debug` or an error.
  - **Pairing comes first** (P2): `machine_match`, `machine_add` and `machine_merge` still take the code's text, so their IPC did not change. `machine_match` (and `machine_merge`, when it comes alone from `Scan again`) pairs and keeps the secret in `AppState`, in one slot keyed by the code's text, for ten minutes, the code's own life; `machine_add`, which the form calls only after `machine_match`, and `machine_merge` take it from there and clear the slot once saved. A pairing code without a secret in the slot, an offer left open past the ten minutes, is `PairingRefused` on `Add as a new machine`, since the code has lapsed too, and not a saved route's `NoToken`. The WebView never sees it. Why first: the `boot` check needs a connection the machine lets in, and the code would lapse while the user reads an offer. Rejected: matching offline and pairing on accepting, which loses the `boot` check.
  - **The orphan row it can leave**: after pairing, `Back` on the offer, leaving the form or a Keychain write that fails leave the device saved on the machine and the code spent, while the phone never saves the secret: it stays in memory until the form closes (`machine_form_closed`, which `AddMachine::close` calls as `MachineForm` unmounts, and `EditMachine::leave` as the machine's screen does, for a `Scan again` or an `Add route` whose merge failed), it lapses or another code takes its slot. One case is left to the ten minutes: a form closed while `machine_match` is still pairing empties the slot before the secret reaches it, so the secret stays until it lapses; it is never saved, and telling a closed form apart would need a generation in the slot, more code than a secret that lapses unsaved is worth. The machine then lists a phone that will never connect, which the user forgets in Settings › Remote › Phone app; a new code is needed. Accepted: it costs a row, never a secret on disk. `Back` keeps the slot: the field keeps the code, and sending it again takes the secret from there, where pairing again would meet a spent code. cornercase itself leaves no row when it cannot deliver the secret.
  - **Pairing again leaves the old device on the machine** (P5): a phone that scans a new code of a machine it had paired with gets a new secret, and the machine keeps the old row. Forgetting it with `config remove app.<old id>` over `/cli` is the next step (Upstream gaps); Settings forgets it by hand. The new secret goes to every `cli` route of the machine, those the code lists and those learned since (`Machines::merge`): the secret is the device's, not a route's, and a route left with the old one would answer `403`, which says `not paired` (The connection bar) while the others only lag.
- **The same machine** (`crates/core/src/machines/same.rs`, `machine_match`, `machine_merge`, `AddMachine`): before a machine is made, the core compares every route of the code with the saved ones. It returns the first match in this order:
  - **Already saved.** A machine has every route of the code, with the same secret: it is merged like the next two, so nothing is written, the form closes and the toast reads `MacBook already saved: nothing to add.` (CA3). Rejected: an error under the field with the form left open, which CA3 does not ask for and which left the toast's `nothing to add` out of reach. cornercase gives a new secret at each pairing, so its code never matches here: it matches by address. Until 059 a saved bridge route with the code's token matched next (`Token`), since the bridge had one token for all its addresses; it went with the bridge's codes.
  - **A Tailscale address** (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`, the ranges cornercase listens on): an address in the tailnet belongs to one node, so it cannot be another machine.
  - **Every address.** A machine has every address of a code of two or more: a new code of a machine already paired, on the same networks.
  - **One address.** A saved route has one of the code's addresses, a LAN one, with another secret.
  - **`boot`.** The `contract --json` of the code's routes gives the same `boot` as the last one seen for a machine.
  - **Name.** Compared without case and without the spaces at its ends.
  - **The whole address counts**, host and port (059). From 058 to 059 a bridge route and a cornercase route at the same host were the same address for these rules, though their ports differed (8765 and 47682), so a cornercase code of a machine saved with the bridge merged into it; with one kind of route left, that rule went.
  - A tie goes to the first machine in the list. The tokens are compared inside the core, so `Token` never leaves it: `MatchView` names only the machine, its name and what to do.
  - **Merged without asking** (P2): already saved, a Tailscale address and every address cannot be wrong, so `machine_match` answers `merge` and the form calls `machine_merge`. It adds the routes the machine lacks, replaces the token of those it has when it changed, closes the form and says what it did in a toast: `MacBook already saved: 1 route added, token updated.` (also for a new secret of cornercase), or `… nothing to add.`. An address that is already a route of another machine is left to it and counted (`1 route left to another machine`): two machines are never merged into one, which covers a user who saved the LAN and Tailscale as two machines in 027.
  - **Offered** (one LAN address, `boot`, name): a private address repeats between networks, so `192.168.1.20` at home and at the office can be two machines, and a wrong `boot` or name would join them too. Rejected: merging on any address, as the ticket's CA3 said word for word, which 027 had already rejected for the same reason.
  - **Why this order**: already saved and the addresses cannot be wrong and work offline. `boot` changes each time cornercase's server restarts, and is known only for the active machine (`Store::boot`) and for the machines tried in this session, which `AppState` keeps in memory. The name comes last, since a name typed by hand matches by chance more than a `boot` does.
  - **`machine_match` compares first without the network**: a match other than the name is the answer, with `checked: true`, since nothing the machine could say would change it, so the form neither waits up to 5 s on a code that does not answer nor says cornercase could not be asked. Otherwise it tries the code as a machine, with `pick_route`, without saving it or touching the Keychain, and compares again with its `boot`, which comes before the name. If no route answers, it compares without `boot`, and its `checked: false` makes the form say that cornercase did not answer, so it could not be asked which machine it is (since 070, without "on the machine", which would say machine twice).
  - **The offer** (`SameOffer.svelte`) says why it matched and offers `Add its addresses to <name>`, the default, or `Add as a new machine`, and `Back`. Accepting it calls `machine_merge` too, with the code whole: the tokens first, then the file once, an address that is another machine's route left to it, the `Store` started again only when something changed, and the same toast as a merge. Rejected: a command of its own for adding routes, `machine_route_add`, which merged the same way but answered nothing, so an address left to another machine, or one already there, closed the form in silence. Rejected: adding the routes one by one, which wrote the file once per route, so a failure halfway kept half of them, and gave this machine an address of another one too, which then confuses the same-machine check and the routes learned.
    - An address match reads `Update the token of <name>`: the routes are added again, and since a machine's routes are keyed by their address, the token is replaced (Connection › Machines with several routes). That is how a new secret reaches a machine when only its LAN address matched.
    - After a name match, `Add as a new machine` needs another name (D1): the error goes under `Name`.
    - Accepting the offer, or a merge, in Machines (`onrouted`) only closes the form, reloads `machines_list` and tries that machine again when it is not the active one: `machine_merge` already restarts the active machine's `Store`, so the UI neither switches the active machine nor starts it a second time. On the empty screen nothing is active (it shows only when the list could not be read), so there the machine is connected to as if it had just been added.
  - **`Scan again`** (a secret missing, or a phone the machine no longer recognizes, `Not paired`) opens the machine's screen with its `Add route` form already open, whose field takes the code too: a cornercase code is paired first, then the core merges it into that machine, as for the offer: it adds the routes it lacks and replaces the token of those it has. `Add route` (`EditMachine`) calls `machine_merge` as well, closes the form and says what it did in a toast that names the machine alone, since its screen is already open: `Studio: 1 route added.`, `Studio: 1 route left to another machine.` or `Studio: nothing to add.` (`routesText`).
- **Routes learned from the machine** (`src-tauri/src/events.rs`, `Machines::learn`, `Store::learn`, `learned::ask_routes`, 035, 058): a machine saved with one route, or a network that cornercase listens on after the code was scanned would otherwise need its code scanned again.
  - On `Connected { route }`, after `remember`, the forwarder asks once, through the `Store`'s transport, `config pair app --routes --json` (`app-routes`), which answers `{"routes":[{"host","port"}]}`; the new routes are `cli` routes. Until 059 a bridge route asked `--bridge-routes` instead, the argv upstream took as `app-routes` (Bridge). The answer is awaited beside the changes, in the forwarder's own loop, so forwarding them never waits for it; a newer connection's question replaces one still pending.
  - `learned_routes` gives each address the token or secret of the route that won, and drops an address the app could not save. `Machines::learn` adds only the addresses the machine lacks and that no other machine has, and writes the tokens and then the file once; it never removes a route.
  - `Store::learn` hands the new routes to the running `Store`, which adds them to its copy of the machine before its next `pick_route` (a network change, the return to the foreground, a retry). The connection is not cut: the route in use already works, and a new route only matters for the next race. Without this, a phone that leaves the Wi-Fi would race on the LAN alone and fail, though the machine has its Tailscale route saved.
  - When `app-routes` fails, the app writes one line to its log and shows nothing. A failed save writes a line too, and the connection stays.
  - **The screens reload the list on opening** (`onMount` in `src/routes/Machines.svelte` and `src/routes/Machine.svelte`): the list the UI shows is a copy `App.svelte` keeps, reloaded after each change made from the UI, and the routes learned arrive in the background a moment after connecting. Without this, the simulator check below showed a machine's screen with its one route while `machines.json` already had three. Rejected for now: an event when the routes change, listened in `App.svelte`, which 025 and 036 change meanwhile; with it, a screen already open would update too, which today needs leaving and opening it again.
  - Routes the machine no longer announces are neither removed nor marked (P4): removing one would lose a network that is only down for now, and the routes are an advanced option of the machine's screen since 035 (Look › Machines). A `Not announced` mark can come later.
  - **Limit: a route the user removes comes back** at the next connection while cornercase still announces it, since the app keeps no list of removed routes. Accepted for now: removing a route cornercase listens on only makes sense while testing, and a route is removed for good once cornercase no longer listens on that network, or by deleting the machine and adding it again.
  - Turning Tailscale on later: cornercase reads the interfaces every 2 s and listens on a new address on its own, so the next connection learns it. The bridge read them once and needed a restart. Scanning the code again is never needed.
- **Which route wins** when the LAN and Tailscale both answer (`pick_route`, Connection › The race, which 046 changed):
  - Every route starts at once, whatever won before. The LAN wins as soon as it answers; when Tailscale answers first, the LAN still wins if it answers within 150 ms of it, and Tailscale wins over the rest the same way.
  - **Back to the LAN on a network change**: every network change (`design/connection/network.md`, 028) runs the race again, while connected too, and so does the return to the foreground. Leaving the Wi-Fi, the LAN hangs or fails and Tailscale wins; back on it, the LAN answers within the window and takes over from Tailscale. Until 046 the last winner had 300 ms of lead, so the app stayed on Tailscale on the home Wi-Fi while Tailscale answered in time (029). While connected with no such event, the app does not go back to the LAN by itself: there is no race on a timer.
  - **The cost on mobile data**: there the home LAN route usually hangs until the connect timeout, so each race waits the whole window, 150 ms more, before Tailscale wins. Accepted: it is one race per network change or return to the foreground. Until 046 it was 300 ms when the LAN had won last, nothing when Tailscale had.
  - `last_route` is still saved and shown on the machine's screen, but no longer decides the race.
  - **Pending, for the user on an iPhone**: on the home Wi-Fi the bar says `via 192.168.…`; leaving it, Tailscale; back, the LAN again. The simulator can only show the LAN winning, since every address there is the machine's.
- **Names** (`crates/core/src/machines/name.rs`, `checkName` in `src/lib/machineForm.ts`): trimmed, not empty, at most 64 characters, and different from every other machine's name without case and the spaces at its ends.
  - An empty `Name` takes the code's `name=`, cut to 64 characters, and the field's placeholder shows it. When another machine already has that name, it takes the host instead, so the form never fails on a name the user did not type; a host already taken is refused under `Name`, as a typed name is.
  - `machine_match` still gets the code's `name=` (or the name typed), not the host that replaced it: the host is only the new machine's name. Otherwise the match by name could never offer the machine of that name, which is what it is for when the token was rotated, the LAN address changed and `boot` was not seen in this session.
  - The core checks them in `add` and in `rename`, so the file cannot get two equal names by either path. Renaming to its own name, in other capitals, is allowed.
  - The UI repeats the check with the same messages, to say it before a round trip. The core's `name_*` codes go under the `Name` field, like `route_*` under `Machine code` (`fieldOf`).
  - Renaming does not reconnect: the bar takes the name from `machines_list`, which the screen reloads after each change.
- **Removing and ordering routes** (`Machines::remove_route`, `move_route`):
  - Removing writes the file before deleting the token, as removing a machine does, so a failure leaves at most an orphan secret. It forgets `last_route` when that was the route.
  - A machine's last route cannot be removed (`last_route`): a machine without routes could not connect, so the way out is to delete the machine.
  - Moving swaps a route with its neighbour, with buttons rather than dragging. At either end it does nothing.
  - **The order only changes what is shown** (P2): the race tries every route at once and prefers the LAN, then Tailscale (Which route wins, above). So the order changes how the routes are listed and the order of their errors, not which one wins. Rejected for now: letting the first in the list win between two routes of the same kind, which could come later without breaking anything.
- **Changing the active machine's routes reconnects it** (`src-tauri/src/commands/routes.rs`): the `Store` keeps a copy of the machine, so a change it did not see would leave the race on the old routes.
  - Adding a route, or replacing a token, starts the `Store` again (`connection::start`), so the new route joins the race. `machine_merge` does it when a route was added or a token changed, and nothing when there was nothing to add.
  - Routes learned from the machine are the exception: they reach the running `Store` without starting it again (Routes learned from the machine).
  - Removing one starts it again only if the race could be using that route. When the `Store` is connected through another route, it stays as it is; while it connects or retries, it starts again.
  - Moving never reconnects, since the order does not matter (above).
- **The active machine is remembered** (P3, `Machines::activate`, `active`): `machines.json` gains an `active` id, read with `#[serde(default)]`.
  - Format version 1 stays: a file written before has no `active` and reads as none, and nothing in the old format is read differently. Rejected: a version 2, which an older app would refuse to read at all.
  - `connect` saves the machine (`activate`, which writes only when it changes) before starting its `Store`, so the next start connects to it.
  - `machines_list` returns `{ machines, active }` (D3) rather than a flag on each machine. `firstToConnect` takes the saved machine, or the first if it is gone.
  - Removing the active machine clears it. The app then stays in Machines without a connection, or goes to `no-machines` if none is left. It does not connect another machine by itself: choosing one is the user's call.
  - Rejected: moving the active machine to the top of the list, which would undo the order the user chose.
- **Switching** (`latestWins`, `src/lib/join.ts`): a tap on a machine that is not active connects it.
  - A second `connect` for the same machine gets the pending one's promise, which covers a double tap on `Add`.
  - A `connect` for another machine waits for the running one and then runs, unless a newer one has taken its place. So two quick taps on two machines end on the last one tapped.
  - The calls are kept in order in the UI because two `connect`s wait for each other in Rust but may end in either order (`design/architecture.md` › Off the main thread).
  - Rejected: 014's `oneAtATime`, which gave the second tap the first one's promise, so the app stayed on the machine tapped first.
- **Trying the other machines** (`machine_probe`, `src/lib/probes.svelte.ts`, `src/lib/machineRows.ts`): only the active machine has a `Store` (Store › In the app). The others are tried once with `pick_route`, without a `Store`:
  - when Machines opens;
  - when `Check again` is tapped;
  - when a machine stops being active, since it has no result of its own yet.
  - Nothing tries them on a timer: each try opens a connection to every route, and a screen at rest stays quiet.
  - The result (D4): `Answers via <host:port>` if a route wins. Otherwise `Not paired` if any route answered `NotPaired` (058), with `Scan again` and no `Check again`, which could not fix it, first as in the bar (Store › States), so a machine reads the same in both places; `No secret` if every route lacks its secret, which the bar shows as `not_paired` (The connection bar), with `Scan again` beside it, which says the fix (it read `No secret: scan its code again` until the review of 2026-11-15, cut at 390 pt beside its two buttons); and otherwise `No answer`, with each route's error under `Errors by route`.
  - A probe that answers keeps its `boot` for the same-machine check.
  - Rejected: a `Store` per machine, or watching the others in the background, which costs battery and connections for rows nobody is looking at.
- **This device** (`src/lib/thisDevice.svelte.ts`): Machines shows the identity's fingerprint, the 10 hex characters of `identity_fingerprint`, in the monospaced font. If there is no identity, it shows the reason instead (Identity and secrets).
- **Checked on 2026-11-14 for 058** in the iPhone 17 simulator, iOS 27.2 (Xcode 27.2, macOS 26.6.2, Tauri 2.12.5), against cornercase 0.13.78 with its own `HOME`, XDG folders and socket, `phone_app` on and `CORNERCASE_PHONE_ADDRESSES=127.0.0.1`, the code of `config pair app` typed into `Machine code` by XCUITest:
  - **Pairing first** (P2): `Add` traded the code at once (`phone app paired … name="cornercase-mobile/0.1.0 (iOS)"`, and `config pair app` ended with `paired: true`); the code's name was taken by a saved machine, so the field offered the host, and an old machine with a bridge route at `127.0.0.1` matched across kinds (`… is already saved at this address.`). `Add as a new machine` saved `{"kind":"cli","url":"ws://127.0.0.1:47682/"}` with no secret in `machines.json`, and connected: `contract`, `status`, `events` and `config` ran over `/cli`.
