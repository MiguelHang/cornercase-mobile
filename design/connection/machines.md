# Machines

A topic of [Connection](../connection.md): the Machines screen's side of the connection (027). It covers adding a machine from the bridge's code, telling that a code belongs to a machine already saved and merging it, the routes learned from the bridge, which route wins, names, removing and ordering routes, the active machine remembered between starts, switching it, and trying the other machines. How the screens look is in `design/look.md`; the bar's `unauthorized` is in [The connection bar](bar.md).

- **Adding a machine**: scan the bridge's QR code (the `barcode-scanner` plugin, 027) or paste its code, one per Mac since 035. The empty screen's `Add machine` opens a form for the code and a name (Look › Forms); the rest is below.
  - **The code is checked before `machine_add`** (`src/lib/machineForm.ts`): trimmed, it must start with `ws://`, parse and carry a `token=` that is not empty. Each refusal has its own message under the field, so a paste cut short or an `http://` address is caught without a round trip. The core still parses the route; its `route_*` errors also go under the `Machine code` field, any other under the form, which stays open with what was typed.
  - **Sending it** (`AddMachine`, `src/lib/addMachine.svelte.ts`, a class with the form's fields in `$state`, so the steps are tested without a WebView): the form is busy from `machine_add` until the machine is handed over, and stays busy after, since it still shows while its card fades out and a second tap on `Add` would save the same machine twice, which 014 cannot remove. Only a refusal makes it rest again. A rejected IPC call goes under the form with its message, as the toasts tell it.
  - **An empty name takes the code's name, else its host** (Names, below).
  - **Once added**, the app goes to `home` at `Connecting…` (Machines stays open, on top of it), reloads the machines for the bar's name and connects. A `connect` that fails leaves the machine saved and says why in a toast, so that nobody adds it twice.
  - **The last `connect` asked wins** (`latestWins`, Switching, below): a double tap on `Add` or the first load meeting the form connects once, and a machine added while another connects ends up connected.
- **Adding by QR code or by pasting** (`src/lib/ui/UrlField.svelte`, `src/lib/scanner.svelte.ts`): one field, `Machine code`, with `Scan QR code` above it; the forms for adding speak of the machine and its code, not of routes (035). The same field serves `Add machine`, on the empty screen and in Machines, and a machine's `Add route`, so the forms share it rather than copy it. It takes the machine code (Bridge › The machine code) and a URL of one route alike. A code that is read fills the field and is sent at once, along the same path as a pasted one: it is checked with `checkUrl`, then by the core.
  - **The scanner's steps** (`Scanner`, a class with its state in `$state` and the plugin's calls passed in, so the tests drive every path without a camera):
    - It asks for the camera before scanning: `checkPermissions`, then `requestPermissions` if needed. On iOS 14 and later `scan` does not ask by itself; it rejects with "Camera permission denied or not yet requested", after it has already put the camera's view in.
    - Refused, it shows `Open Settings` (`openAppSettings`).
    - Any other failure, such as no camera (the simulator, the desktop) or the plugin's error, shows its message. The field for pasting stays usable under it in both cases.
    - Every way out calls `cancel` in a `finally`: a code read, `Cancel`, or an error. It also takes away `html.scanning`, so the camera's view never stays over the page and the page's ground always comes back.
    - `stop` takes `html.scanning` away itself before it calls `cancel`, rather than waiting for `cancel` to end the pending `scan`, and `UrlField` calls `stop` when it goes away in the middle of a scan (its form closed, its screen left): otherwise the page stayed hidden, the camera on and no `Cancel` in sight.
  - **`windowed: true`**: without it, the plugin's view covers the WebView with no way to close it, since it brings no button. In windowed mode the WebView turns transparent over the camera and the page draws its own frame and `Cancel` (Look › Scanning).
- **One code, one machine with every route** (`machine_add`, `Machines::add`, 035): a code of N addresses is saved as one machine with N routes, in the code's order, each with the code's token in the Keychain under its address. The tokens are all written before the file, which is written once, as for one route (Connection › The order of the writes). Then the app connects; the race picks the route (Which route wins, below). There is no step about routes: before 035 the user added the LAN's URL, then the Tailscale one, and accepted an offer to join them.
- **The same machine** (`crates/core/src/machines/same.rs`, `machine_match`, `machine_merge`, `AddMachine`): before a machine is made, the core compares every route of the code with the saved ones. It returns the first match in this order:
  - **Already saved.** A machine has every route of the code, with the same token: it is merged like the next three, so nothing is written, the form closes and the toast reads `MacBook already saved: nothing to add.` (CA3). Rejected: an error under the field with the form left open, which CA3 does not ask for and which left the toast's `nothing to add` out of reach.
  - **Token.** A saved route has the code's token. The bridge uses one token for all its addresses, so this is the common case, and it needs no network.
  - **A Tailscale address** (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`, the ranges the bridge listens on): an address in the tailnet belongs to one node, so it cannot be another Mac.
  - **Every address.** A machine has every address of a code of two or more: a rotated token (`--new-token`) with the same networks.
  - **One address.** A saved route has one of the code's addresses, a LAN one, with another token.
  - **`boot`.** The `contract --json` of the code's routes gives the same `boot` as the last one seen for a machine.
  - **Name.** Compared without case and without the spaces at its ends.
  - A tie goes to the first machine in the list. The tokens are compared inside the core, so `Token` never leaves it: `MatchView` names only the machine, its name and what to do.
  - **Merged without asking** (P2): already saved, token, a Tailscale address and every address cannot be wrong, so `machine_match` answers `merge` and the form calls `machine_merge`. It adds the routes the machine lacks, replaces the token of those it has when it changed, closes the form and says what it did in a toast: `MacBook already saved: 1 route added, token updated.`, or `… nothing to add.`. An address that is already a route of another machine is left to it and counted (`1 route left to another machine`): two machines are never merged into one, which covers a user who saved the LAN and Tailscale as two machines in 027.
  - **Offered** (one LAN address, `boot`, name): a private address repeats between networks, so `192.168.1.20` at home and at the office can be two Macs, and a wrong `boot` or name would join them too. Rejected: merging on any address, as the ticket's CA3 said word for word, which 027 had already rejected for the same reason.
  - **Why this order**: already saved, token and address cannot be wrong and work offline. `boot` changes each time cornercase's server restarts, and is known only for the active machine (`Store::boot`) and for the machines tried in this session, which `AppState` keeps in memory. The name comes last, since a name typed by hand matches by chance more than a bridge does.
  - **`machine_match` compares first without the network**: a match other than the name is the answer, with `checked: true`, since nothing the bridge could say would change it, so the form neither waits up to 5 s on a code that does not answer nor says the bridge could not be asked. Otherwise it tries the code as a machine, with `pick_route`, without saving it or touching the Keychain, and compares again with its `boot`, which comes before the name. If no route answers, it compares without `boot`, and its `checked: false` makes the form say that the bridge could not be asked which machine it is.
  - **The offer** (`SameOffer.svelte`) says why it matched and offers `Add its addresses to <name>`, the default, or `Add as a new machine`, and `Back`. Accepting it calls `machine_merge` too, with the code whole: the tokens first, then the file once, an address that is another machine's route left to it, the `Store` started again only when something changed, and the same toast as a merge. Rejected: a command of its own for adding routes, `machine_route_add`, which merged the same way but answered nothing, so an address left to another machine, or one already there, closed the form in silence. Rejected: adding the routes one by one, which wrote the file once per route, so a failure halfway kept half of them, and gave this machine an address of another one too, which then confuses the same-machine check and the routes learned.
    - An address match reads `Update the token of <name>`: the routes are added again, and since a machine's routes are keyed by their address, the token is replaced (Connection › Machines with several routes). That is how a token the bridge no longer takes is fixed when only the LAN matched.
    - After a name match, `Add as a new machine` needs another name (D1): the error goes under `Name`.
    - Accepting the offer, or a merge, in Machines (`onrouted`) only closes the form, reloads `machines_list` and tries that machine again when it is not the active one: `machine_merge` already restarts the active machine's `Store`, so the UI neither switches the active machine nor starts it a second time. On the empty screen nothing is active (it shows only when the list could not be read), so there the machine is connected to as if it had just been added.
  - **`Scan again`** (a token rejected or missing) opens the machine's screen with its `Add route` form already open, whose field takes the code too: the core merges the code into that machine, as for the offer: it adds the routes it lacks and replaces the token of those it has. `Add route` (`EditMachine`) calls `machine_merge` as well, closes the form and says what it did in a toast that names the machine alone, since its screen is already open: `Studio: 1 route added.`, `Studio: 1 route left to another machine.` or `Studio: nothing to add.` (`routesText`).
- **Routes learned from the bridge** (`src-tauri/src/events.rs`, `Machines::learn`, `Store::learn`, `learned_routes`, 035): a machine saved with one route before 035, or a bridge restarted on new networks, would otherwise need its code scanned again.
  - On `Connected { route }`, after `remember`, the forwarder asks the bridge `--bridge-routes` (Bridge › The machine code) once, through the `Store`'s transport. The answer is awaited beside the changes, in the forwarder's own loop, so forwarding them never waits for it; a newer connection's question replaces one still pending.
  - `learned_routes` gives each address the token of the route that won, and drops an address the app could not save. `Machines::learn` adds only the addresses the machine lacks and that no other machine has, and writes the tokens and then the file once; it never removes a route.
  - `Store::learn` hands the new routes to the running `Store`, which adds them to its copy of the machine before its next `pick_route` (a network change, the return to the foreground, a retry). The connection is not cut: the route in use already works, and a new route only matters for the next race. Without this, a phone that leaves the Wi-Fi would race on the LAN alone and fail, though the machine has its Tailscale route saved.
  - A bridge from before 035 answers exit 2; the app writes one line to its log and shows nothing. A failed save writes a line too, and the connection stays.
  - **The screens reload the list on opening** (`onMount` in `src/routes/Machines.svelte` and `src/routes/Machine.svelte`): the list the UI shows is a copy `App.svelte` keeps, reloaded after each change made from the UI, and the routes learned arrive in the background a moment after connecting. Without this, the simulator check below showed a machine's screen with its one route while `machines.json` already had three. Rejected for now: an event when the routes change, listened in `App.svelte`, which 025 and 036 change meanwhile; with it, a screen already open would update too, which today needs leaving and opening it again.
  - Routes the bridge no longer announces are neither removed nor marked (P4): removing one would lose a network that is only down for now, and the routes are an advanced option of the machine's screen since 035 (Look › Machines). A `Not announced` mark can come later.
  - **Limit: a route the user removes comes back** at the next connection while the bridge still announces it, since the app keeps no list of removed routes. Accepted for now: removing a route the bridge listens on only makes sense while testing, and a route is removed for good by restarting the bridge without that network, or by deleting the machine and adding it again.
  - Limit: turning Tailscale on after the bridge started needs the bridge restarted (Bridge › Listening on the network › Addresses that come or change), then the next connection learns its address; scanning the code again is never needed.
- **Which route wins** when the LAN and Tailscale both answer (`pick_route`, Connection › The race; nothing about the race changed in 035):
  - With no winner yet (a new machine), every route starts at once and the first to answer `contract` wins: on the same Wi-Fi that is usually the LAN.
  - Otherwise the last winner starts alone and has 300 ms of head start: if it answers within them, it wins; if it fails sooner, the others start at once; past them, the others start and the first to answer wins.
  - So after leaving the Wi-Fi, Tailscale wins and becomes the last winner, and back on the Wi-Fi the app stays on Tailscale while it answers in under 300 ms. Accepted: on the same network Tailscale usually goes direct, so it costs little, and a route that keeps working is not dropped for one a little faster, which would bounce the connection between the two at every race. The LAN takes over when Tailscale is slow or down.
  - Every network change (`design/connection/network.md`, 028) runs the race again, while connected too, and so does the return to the foreground.
- **Names** (`crates/core/src/machines/name.rs`, `checkName` in `src/lib/machineForm.ts`): trimmed, not empty, at most 64 characters, and different from every other machine's name without case and the spaces at its ends.
  - An empty `Name` takes the code's `name=`, cut to 64 characters, and the field's placeholder shows it. When another machine already has that name, it takes the host instead, so the form never fails on a name the user did not type; a host already taken is refused under `Name`, as a typed name is.
  - `machine_match` still gets the code's `name=` (or the name typed), not the host that replaced it: the host is only the new machine's name. Otherwise the match by name could never offer the Mac of that name, which is what it is for when the token was rotated, the LAN address changed and `boot` was not seen in this session.
  - The core checks them in `add` and in `rename`, so the file cannot get two equal names by either path. Renaming to its own name, in other capitals, is allowed.
  - The UI repeats the check with the same messages, to say it before a round trip. The core's `name_*` codes go under the `Name` field, like `route_*` under `Machine code` (`fieldOf`).
  - Renaming does not reconnect: the bar takes the name from `machines_list`, which the screen reloads after each change.
- **Removing and ordering routes** (`Machines::remove_route`, `move_route`):
  - Removing writes the file before deleting the token, as removing a machine does, so a failure leaves at most an orphan secret. It forgets `last_route` when that was the route.
  - A machine's last route cannot be removed (`last_route`): a machine without routes could not connect, so the way out is to delete the machine.
  - Moving swaps a route with its neighbour, with buttons rather than dragging. At either end it does nothing.
  - **The order only changes what is shown** (P2): the race tries every route at once and gives the head start to the last winner (Connection › Machines with several routes). So the order changes how the routes are listed and the order of their errors, not which one wins. Rejected for now: a head start for the first route while there is no `last_route`, which could come later without breaking anything.
- **Changing the active machine's routes reconnects it** (`src-tauri/src/commands/routes.rs`): the `Store` keeps a copy of the machine, so a change it did not see would leave the race on the old routes.
  - Adding a route, or replacing a token, starts the `Store` again (`connection::start`), so the new route joins the race. `machine_merge` does it when a route was added or a token changed, and nothing when there was nothing to add.
  - Routes learned from the bridge are the exception: they reach the running `Store` without starting it again (Routes learned from the bridge).
  - Removing one starts it again only if the race could be using that route. When the `Store` is connected through another route, it stays as it is; while it connects or retries, it starts again.
  - Moving never reconnects, since the order does not matter (above).
- **The active machine is remembered** (P3, `Machines::activate`, `active`): `machines.json` gains an `active` id, read with `#[serde(default)]`.
  - Format version 1 stays: a file written before has no `active` and reads as none, and nothing in the old format is read differently. Rejected: a version 2, which an older app would refuse to read at all.
  - `connect` saves the machine (`activate`, which writes only when it changes) before starting its `Store`, so the next start connects to it.
  - `machines_list` returns `{ machines, active }` (D3) rather than a flag on each machine. `firstToConnect` takes the saved machine, or the first if it is gone.
  - Removing the active machine clears it. The app then stays in Machines without a connection, or goes to `no-machines` if none is left. It does not connect another machine by itself: choosing one is the user's call.
  - Rejected: moving the active machine to the top of the list, which would undo the order the user chose.
- **Switching** (`latestWins`, `src/lib/join.ts`): a tap on a machine that is not active connects it.
  - A second `connect` for the same machine gets the pending one's promise, which covers a double tap on `Add`.
  - A `connect` for another machine waits for the running one and then runs, unless a newer one has taken its place. So two quick taps on two machines end on the last one tapped.
  - The calls are kept in order in the UI because two `connect`s wait for each other in Rust but may end in either order (`design/architecture.md` › Off the main thread).
  - Rejected: 014's `oneAtATime`, which gave the second tap the first one's promise, so the app stayed on the machine tapped first.
- **Trying the other machines** (`machine_probe`, `src/lib/probes.svelte.ts`, `src/lib/machineRows.ts`): only the active machine has a `Store` (Store › In the app). The others are tried once with `pick_route`, without a `Store`:
  - when Machines opens;
  - when `Check again` is tapped;
  - when a machine stops being active, since it has no result of its own yet.
  - Nothing tries them on a timer: each try opens a connection to every route, and a screen at rest stays quiet.
  - The result (D4): `Answers via <host:port>` if a route wins. Otherwise `Token rejected` if any route answered `Unauthorized`, since that one has a fix; `No token: scan its code again` if every route lacks its token; and otherwise `No answer`, with each route's error under `Errors by route`.
  - A probe that answers keeps its `boot` for the same-machine check.
  - Rejected: a `Store` per machine, or watching the others in the background, which costs battery and connections for rows nobody is looking at.
- **This device** (`src/lib/thisDevice.svelte.ts`): Machines shows the identity's fingerprint, the 10 hex characters of `identity_fingerprint`, in the monospaced font. If there is no identity, it shows the reason instead (Identity and secrets).
