# Identity and secrets

A topic of [Connection](../connection.md). The phone's identity, the secret cornercase gives the device, and where they and the routes' tokens are kept: the Keychain on iOS, the Keystore on Android, and how Android's tokens left the file 030 kept them in.

## Identity

- **Identity** (`crates/core/src/identity.rs`): an Ed25519 key pair the phone makes on its first start, to be reused as its iroh identity. Pairing does not use it (the device's secret, below, is cornercase's): in phase 0 the app only makes it, keeps it and writes its fingerprint to the log (task 009). iOS keeps it in the Keychain (009), Android in the Keystore (031).
  - **A seed, not a key**: `Secrets` keeps the 32-byte seed under `identity/ed25519`, the bytes iroh's `SecretKey::from_bytes` takes, so iroh can reuse it as it is. `Identity::load_or_create` reads it, or takes 32 bytes from the system's generator (`getrandom::fill`) and saves them before returning the identity. In the core the seed lives in `Zeroizing` buffers and ed25519-dalek's `SigningKey`, which wipe themselves when dropped; `Identity` has a redacted `Debug`, no `Display` and no `Serialize`, so neither a log nor an error can show it.
  - **`public_key()`** is the public key in base64url without padding, 43 characters. **The fingerprint** is the key's first 5 bytes in hex, 10 characters, what iroh's `fmt_short` shows, so the log and iroh will agree. Rejected: a SHA-256 of the key (`sha2` for a label) and the first characters of the base64url.
  - **A saved seed that is not 32 bytes** is `Error::Identity`, which names neither its length nor its bytes, and is never overwritten: a new identity made without a word would silently break whatever was paired with the old one, just as a machines file that does not parse is never overwritten. If the system gives no random bytes, it is `Error::Random`, and nothing is saved. A failing `get` or `set` is the store's `Error::Secrets`; a failed `set` returns no identity, so nothing uses a key that was not saved.
  - **On start** (`src-tauri/src/identity.rs`, from Tauri's `setup` hook): one line on stderr, `cornercase-mobile: identity <fingerprint>` or `cornercase-mobile: no identity: <error>`, and the app starts either way, keeping the result for `identity_fingerprint`. Loading the machines is the only other work on start.
  - **No race**: `load_or_create` runs once, on start. Two calls at once on an empty store would each save a seed, the last write would win and the other caller would hold a key that is not saved; the app's state keeps that one `Identity` rather than calling it again.
- **The device's secret** (058): pairing with cornercase's code gives the phone a secret of its own, `<id>.<64 hex>`, of which cornercase keeps only a SHA-256, in `apps.json`, and the `<id>` to list and forget the phone (Machines › Pairing with cornercase's code). It is kept as the bridge's token was, a `Token` in `Secrets` under `route/<machine id>/<address>` for each cornercase route of the machine, so the Keychain's `AfterFirstUnlockThisDeviceOnly` and Android's Keystore cover it with no code of their own, and it never reaches the WebView. One pairing, one secret, written once per route; pairing again replaces it on the routes of the new code.
  - **Not the identity**: cornercase tells the phone by its secret, not by a key, so the Ed25519 identity stays unused, kept for iroh.
  - **A backup on another phone, or a reinstall**: the restored phone lacks the secret (`ThisDeviceOnly`), so its routes fail with `NoToken` and `Scan again` pairs it as a new device, the old row staying on the machine until it is forgotten there. On iOS a reinstall leaves the secrets in the Keychain as orphans, as it leaves the tokens (below).
- **Two stores, loaded apart**: `AppState::load` takes the identity's store (`secrets::store`) and the routes' store (`secrets::routes`) separately, so a failing identity does not keep the machines from loading, and a broken tokens file does not cost the identity. iOS and Android pass the same store as both; Android passes its old file for the routes while their move fails (Android's route tokens, below).

## `Secrets` in the Keychain

- **`KeychainSecrets`** (`src-tauri/src/secrets/keychain.rs`, `keychain/ios.rs`) over keyring-core's `Entry`, with service `dev.usecornercase.mobile` and the `Secrets` key as the account, in apple-native-keyring-store's `protected` store, the data protection keychain (the only one iOS has), local rather than iCloud-synchronized (no `cloud-sync`).
  - **`AfterFirstUnlockThisDeviceOnly`**, the `access-policy` modifier of every entry: readable once the phone has been unlocked after it booted, so the app can still read it if it starts or wakes in the background while the phone is locked, and never moved to another phone, by an encrypted backup or by iCloud. A backup restored on another phone makes a new identity, which is the point, and its routes lack their tokens (`NoToken`, in Connection). Rejected: `WhenUnlocked` and its `ThisDeviceOnly` (the crate's default; unreadable in the background while locked), `AfterFirstUnlock` (moves with an encrypted backup), `RequireUserPresence` (Face ID on every start). A start before the first unlock would fail with the warning; the app does not start in the background today.
  - **The policy is set only when an item is made**: a `set` on an item that exists updates its data and keeps its policy (security-framework 3.7 answers `errSecDuplicateItem` with `SecItemUpdate`). The identity is written once, so it does not matter for it; a route's secret is rewritten when the machine's code is scanned again, so changing the policy later means deleting the items first.
  - **The Keychain survives uninstalling the app on iOS**: after a reinstall the identity is the same (good), while 008's route tokens stay behind as orphans, since the machines file goes with the app. Not handled yet.
  - **Errors**: keyring-core's `NoEntry` becomes `Ok(None)` and `Ok(())` (what `Secrets` promises, in Connection); every other error becomes `Error::Secrets` with keyring-core's `Display`, never its `Debug` (`BadEncoding` holds bytes), and `Ambiguous` only says how many items it found.
  - **The platforms with no store**, the hosts that run the tests, get the same `KeychainSecrets` over a store that is missing, so every call fails with "no secret store on this platform yet", for the identity and the routes' tokens alike. No dead code and no `cfg` inside the adapter. The adapter and its errors are tested on Linux CI with keyring-core's `mock` store and its error injection; `ios.rs` only builds the store and its modifier, so CI never compiles it, and `cargo clippy -p cornercase-mobile --target aarch64-apple-ios-sim --all-targets` runs locally.
  - **No entitlements**: the simulator reads and writes the data protection keychain without `keychain-access-groups` (no `errSecMissingEntitlement`, -34018), so `project.yml` is unchanged.
  - **Crates**: `keyring-core` 1 and `apple-native-keyring-store` 1 with `protected`, keyring's maintained line, which lets each entry pick its accessibility. Rejected: `keyring` 3.6 with `apple-native` (the older line, with no way to set the accessibility), `keyring` 4.x (no `apple-native` any more), `rand_core`'s `OsRng` (`rand_core` 0.10, the one ed25519-dalek 3 takes, no longer has it, and the seed is 32 bytes `getrandom` gives directly, as the bridge's token did), `tauri-plugin-stronghold` (a password-protected file, not the Keychain) and a Swift plugin over `SecItemAdd` and `SecItemCopyMatching` (the plan B, not needed).
  - **Checked live** on 2026-11-09 in the iPhone 17 simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5): the first start makes the identity and logs its fingerprint; `xcrun simctl terminate` and a new launch log the same one, three launches in a row; after `xcrun simctl keychain booted reset` the next start logs a new one, which then holds. On iOS, Tauri sends stderr to the unified log, not to `xcrun simctl launch --console-pty`: the line is read with `xcrun simctl spawn booted log show --last 5m --style compact --predicate 'subsystem == "dev.usecornercase.mobile" AND eventMessage CONTAINS "cornercase-mobile: "'`. Not checked yet: an iPhone (it needs a signing team), and the item's accessibility, which `simctl` does not show.

## `Secrets` in the Android Keystore

- **The secrets plugin's store** (`src-tauri/plugins/secrets`, `src-tauri/src/secrets.rs` › `store`): `secrets::store` takes the `Secrets` the plugin manages, and it serves the identity and the routes' tokens, as the Keychain does on iOS. Kotlin encrypts each secret with an AES key that never leaves the Keystore and keeps the result in the app's preferences (`design/architecture/android.md` › The Keystore); why a plugin of our own is in `design/architecture/plugins.md`.
- **An encrypted seed, not an Ed25519 key in the Keystore**: the Keystore makes Ed25519 keys only from Android 13 (API 33), and not on every phone, while `minSdk` is 24; and a key that lives in the Keystore never gives up its bytes, so iroh, which takes the 32-byte seed (A seed, not a key, above), could not use it, and every signature would be a call into Kotlin. AES-GCM is in `AndroidKeyStore` from API 23. So Android keeps the same seed as iOS, encrypted, and the core's `Identity` does not change.
- **The same promises** (`src-tauri/plugins/secrets/src/bridge.rs`): a name the preferences lack is `Ok(None)`, deleting one is `Ok(())`, and the value crosses Tauri's JSON bridge as hex (the core's `secrets::hex`, shared with `FileSecrets`), so any bytes arrive whole, the seed included, with no new crate. Every refusal is `Error::Secrets` with what failed (read, write, delete) and why: one of Kotlin's fixed sentences (a damaged secret, the wrong key, the key gone, the preferences not saved), or Tauri's error reaching the plugin; never the exception's message, the value or the ciphertext. An answer of another shape says only that. The adapter is tested on Linux CI over a fake of the three commands; `android.rs`, which only calls the plugin, and the Kotlin are checked by `cargo clippy --target aarch64-linux-android` and live.
- **A secret that no longer opens** (the Keystore's key lost, which some makers' phones do when the screen lock changes, or the preferences damaged) is `Error::Secrets`, and nothing regenerates it: the identity is `Err` and Machines › This device shows the reason, and a route's token that does not open makes `Machines::load` fail, as a failing Keychain read does on iOS. The remedy is clearing the app's data. Rejected: making a new identity and dropping the tokens that do not open, which would hide the loss; to look at again when iroh uses the identity.
- **Uninstalling the app removes it**, unlike iOS's Keychain: the Keystore's key and the preferences go with the app, so a reinstall makes a new identity. The debug build (`.debug`) and the release one each have their own key, preferences and identity.

## Android's route tokens, from their file to the Keystore

- **030 kept them in a file** (`crates/core/src/secrets/file.rs`): with no Keystore yet, the identity had the missing store, but a route's token needed somewhere to live, or no machine could be added. `FileSecrets` kept them in `route-secrets.json` in Tauri's `app_data_dir`, beside `machines.json`, in plain text inside the app's sandbox: the folder (`0700`) and the file (`0600`, `write_atomically`) were readable only by the app's own user, and backups are off, but root or a debuggable build's `run-as` could read it. Accepted for one task because the token only opened the development bridge, which listened only on the LAN and the tailnet.
- **The move** (`crates/core/src/secrets/migrate.rs`, `src-tauri/src/secrets.rs` › `routes`): on every start, before the machines load, `migrate` reads the whole file, copies each entry into the Keystore's store and removes the file only once every copy is saved. No file is nothing to do; a move logs `cornercase-mobile: moved <n> route secrets into the store`.
  - **A failure keeps the file**: a copy refused, the file unreadable, or not removed. The reason goes to the log as `cornercase-mobile: the route secrets stay in their file: <error>`, which names the step and never a value, and this run reads and writes the tokens in the file, so the machines load and connect; the next start tries again. Rejected: using the Keystore anyway, where the routes would have no token until their codes are scanned again.
  - **Doing it twice is harmless**: `set` overwrites, so a run that dies between two copies, or before removing the file, copies the same values again on the next start. While the move fails, the file is the only store the routes use; a move that fails after copying deletes its copies again (as far as the store lets it), so a machine removed during that run leaves no token behind in the Keystore, and the next start copies the file afresh.
  - **The temporary copy goes too**: `write_atomically` writes `.route-secrets.json.tmp` and renames it, and a 030 killed in between left that copy, with every token in plain text, which only a failed write removed. A move that removes the file removes it too, and so does a start with no file; both best effort, since the file it copied is already gone or never was.
  - **A broken file is left alone**, as `FileSecrets` never overwrites one: the move fails before copying anything, the file stays, and the machines fail to load with its reason, as they did in 030.
  - **The logic lives in the core**, without `cfg`, with `FileSecrets`, and is tested on Linux over `MemorySecrets`: everything moved, no file, a broken file, a store that fails, a file that cannot be removed, a temporary copy left behind. `src-tauri` only picks the file's path and the store and writes the line.
  - **Removing the file does not wipe its blocks** on the flash: the tokens may linger there until overwritten. Accepted: reading them needs root, and they only opened the development bridge, now gone (059).
- **The file** is `{"version": 1, "secrets": {"<key>": "<hex>"}}`: hex, so no new dependency (base64 is in `Cargo.lock` only through others), and keys as `Secrets` names them, `/` included. It keeps the promises of `Secrets` (a missing key or file is `Ok(None)`, deleting one that is not there is `Ok(())`). A file that does not parse, has another shape, an unknown version or a value that is not hex is `Error::Secrets`, which names the mistake (and its line and column) but never the file's text, and is never overwritten. `set` and `delete` read, change and write the whole file atomically, under a `Mutex`, so two writes cannot lose each other's key; they still matter during a run whose move failed.
