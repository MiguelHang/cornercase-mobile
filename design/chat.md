# Chat

The agent's screen a row of the board opens (`src/routes/agent/Agent.svelte`, Board › A row): its header, the agent's last message as markdown, and a field to answer it with text, with a row of keys over it to answer with a key (Keys). Its state lives in `src/lib/chat.svelte.ts` (`Chat`), without markup, so vitest tests it; the commands come in by injection, as in `addMachine.svelte.ts`. Pasted images are 018's.

## Reading the message

- **What is read**: `read --last-message --pane P --json` (`crates/core/src/cli/last_message.rs`, `LastMessage`): the pane, the agent, the text, and `written` and `turn_over` when the agent's record has them. Every field has a default and unknown keys are ignored, so what upstream adds breaks nothing. It is the newest text of the assistant, also halfway through a turn, and nothing older: there is no history to show (Upstream gaps). The fixture (`crates/core/tests/fixtures/control/last-message/`) is that command's output from cornercase 0.13.19.
- **One-shot, beside the queue**: the `last_message` command runs `transport::json` on the transport of the route the `Store` connected on (`Store::transport()`, Connection › Store), as Connection › the ordered queue says for the reads that order nothing. A transcript can hold tens of MB, so a slow read must not hold a key or a send. Without a `Store` or before its first connection it answers `not_connected`.
- **A message that cannot be read** (no message yet, a record not found yet, an agent whose record cornercase does not read, such as Grok) shows cornercase's reason, without its `Error:`, in `--muted` in the message's place. It is the state of the screen until the next read, not the failure of something the user did, so it is not a toast. `Reading its last message…` shows the same way until the first answer. Only cornercase's own refusal (`failed`) takes the message's place: a read lost on the way (the connection dropped, no answer, no machine connected, a call to Rust that throws) keeps the message already shown, and shows its reason only while there is none. Over LTE a read can fail without anything having changed, and the next event or new stream reads again.
- **When it is read again**: once the screen has its row, then on every `pane-status-changed` of its machine with its pane, or with `pane: null`. There is no polling. While an agent works, its message can grow without a status change, and the screen shows it at the next one. Accepted, rather than a read every few seconds over LTE.
  - **The event, not the snapshot**: the forwarder turns each `status` event that names a pane into `pane-status-changed { machine, pane }`, and a `dropped` event into one with `pane: null` ("read again whatever you show"), since the events lost may include this pane's. A new `events` stream is the same loss (a reconnection, the app back from the background, a network change; Board › Since when), so the `Store` sends `Change::Reopened` each time it opens the streams again, never on the first, and the forwarder turns it into `pane: null` too. Otherwise an agent that finished while the phone was locked would show `done` with the snapshot and keep the message from halfway through its turn, since no status event of its pane may come again. Rejected: the UI reading again on `connection-changed` and on coming to the foreground, a second path to the same loss that Rust already knows of. Rust reads nothing and does not know which pane the screen shows. `events` reaches the app about 500 ms before `status --follow`, and an event also shows a status that went and came back between two snapshots, after which the message is a new one.
  - Rejected: Rust reading the message itself on each event and sending it in the event. The forwarder would have to know which pane the screen shows, a state that changes with each tap and races with the reads in flight. Rejected too: the UI reading again when `row.status` changes in `agents-changed`, which comes with the snapshot and misses a status that went and came back.
- **One read at a time, one more at most**: an event during a read asks for one more, however many come, and it starts when the first ends. The reads are numbered, so a late answer never replaces a newer one, and leaving the screen discards the one in flight.

## Answering

- **The field** is a `TextArea` (Look › Forms) that grows with its text up to a maximum and then scrolls. Return adds a line and only `Send` sends: on a phone's keyboard Return is the only way to break a line, and a message sent by mistake cannot be taken back. `Send` rests while the text is blank, while it sends and while the agent is `waiting`.
- **Through the queue**: `send --pane P --enter --timeout 30 -` by `Queue::ask`, with the text as `Stdin::Text`, so it keeps its order with the keys (Keys). On standard input, a text that starts with `-` is not read as an option, and the text never shows in the argv the bridge logs. No message nor log holds it.
- **What comes back**: success empties the field. Otherwise the text stays and a toast says why, since it answers something the user did: cornercase's refusal without its `Error:` (`waiting`, a dialog, a poll, `resuming`, `not confirmed`, a held send that ran out of time), `nothing was sent` for a job the queue skipped, `it may have been sent, but no answer came back` for one that lost its answer, and `no machine is connected` without a queue. cornercase's texts are written for scripts (`answer with cornercase keys`, `or with --force`) and are shown as they are: rewriting them would guess at upstream's words.
- **No optimistic state**: after a confirmed send the header turns `working` only with `agents-changed`, and the message is read again with its event.
- **`--timeout 30`**: upstream holds a send while someone types on the Mac (its `held-sends.md`). With 30 s, a held send ends in `nothing was sent` rather than waiting for ever. Meanwhile the queue is busy, so a key tapped behind it waits up to 30 s (Keys). Accepted. Rejected: 15 s, the least over the 3 s of the Enter and the 10 s of the confirmation, which leaves a held send almost no time; no timeout, which would let a held send stop the queue for good.
- **A false `not confirmed`**: a Codex that works keeps a prompt sent meanwhile in memory and records it after its next tool call, so upstream extends its 10 s confirmation up to `--timeout` (its `confirming-sends.md`). A tool call longer than 30 s then fails with `not confirmed` though Codex takes the prompt later. Accepted. The text stays in the field and the toast says it may not have been submitted, so the user can look before sending it twice. Any `not confirmed` may have reached the agent for the same reason.
- **`waiting` takes no text**: upstream refuses `send` to an agent that asks a question, a permission or a choice, which is answered with a key (Keys). There, `Send` rests under the note `<agent> is asking you something on its screen; answer with the keys.`, and the text typed stays, as gpui's `unready` does. Rejected: sending anyway and showing the refusal, a round trip for nothing.

## Keys

- **The row** (`src/routes/agent/KeyRow.svelte`) sits in the composer over the field, wherever the field is: while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent. It holds `Esc`, `Tab`, `↑`, `↓`, `←`, `→`, `Enter`, `Ctrl-C` and `0–9`, which unfolds the digits. Each button is a name of cornercase's `KEY_NAMES` (`src/lib/keys.ts`, its label, its name for VoiceOver and its key): the keys an agent's menus, permissions and confirmations take, the arrows and `Enter` to move and choose, a digit to choose an option by its number, `Esc` to cancel, `Ctrl-C` to interrupt. `src/lib/keys.ts` holds no markup nor state, so the terminal's row (021) can take its names too.
- **`0` too**, though the task asked for `1`–`9`: upstream closes Claude Code's survey with `keys --pane N 0` (its `confirming-sends.md`), and `send` refuses a pane with the survey open, so without it the phone could not take it away. The digits go `1` to `9`, then `0`, as on a keyboard.
- **Every key in sight**: buttons of 44 px (Look › Touch and motion), with no more width than their label and the arrows drawn as Lucide icons named `Up`, `Down`, `Left` and `Right`; on a phone 393 px wide the row breaks into a second line rather than scrolling sideways. The digits unfold in a row of their own over the keys, behind a button with `aria-expanded`, and stay open after a digit is sent until that button is tapped again, so `↑` or another number can follow without opening them again. Rejected: one row that scrolls sideways, which hides keys out of sight; the arrows on a fixed line of their own; digits that fold on their own after one is sent.
- **`keys`, not `input`**: each tap queues `keys --pane P <key>` by `Queue::ask`, without standard input (`crates/core/src/cli/keys.rs`, the `keys` command of `src-tauri/src/commands/chat.rs`), on the `requests --follow` the sends go through, so keys and sends reach the agent in the order they were tapped. `keys` is upstream's way to answer an agent (`send` refuses `waiting` with `answer with cornercase keys`), its `enter` counts as submitting a turn, and it answers each key, so a key that fails gets a toast with a send's rules (Answering › What comes back), and success shows nothing: the status comes with `agents-changed` and the message with the next read, as after a send. `input` (the typist, Connection › the ordered queue) is someone typing in another window, the terminal's (021), and answers nothing a toast could say. The UI does not wait for a key's answer before sending the next one: `↓ ↓ Enter` tapped fast keep their order in the queue.
- **Only the app's keys reach the argv**: the core takes only the 18 names the app sends and refuses any other (empty, `-x`, `shift+tab`) before anything is queued, so a key can never turn into an option of `keys`.
- **`Ctrl-C` asks for a second tap**: the first one sends nothing; it turns the button to the danger tone with `Tap again to interrupt`, which VoiceOver reads (`aria-live`). A second tap within 3 s sends `ctrl+c` once; after 3 s, or on any other key, it lets go without sending. Two `ctrl+c` in a row quit Claude Code and leave its shell, and the screen turns gone, so one tap must never send it by mistake; a third tap arms it again rather than sending a second one. Rejected: a long press, which WebKit on iOS takes for itself without a click (Look › Touch and motion) and VoiceOver hardly does; a confirmation dialog, one more screen for a key.
- **`Esc` asks for nothing**: in Claude Code it interrupts an agent that works, as `Ctrl-C` does, but never quits it, and two in a row open its rewind. Accepted: it is the key a menu takes to cancel, and a confirmation would slow every menu down.
- **A light tap**: each tap that sends a key, and the one that arms `Ctrl-C`, asks the haptics plugin for `impactFeedback('light')` (`src/lib/haptics.ts`, Architecture › Dependencies), since what a key does often shows only on the Mac. Without the plugin (the desktop, the tests) or when it fails, nothing shows and the key still goes: it is not a failure of what the user did, so there is no toast.
- **Behind a held send** a key waits, as every job behind it does, up to the 30 s of `--timeout 30` (Answering).
- **Nothing to another pane**: a `Chat` gone, or of another machine, sends no key (The screen), and its screen shows no row. `keys` has no `--boot` either (Upstream gaps).

## Markdown

- **A tree, never HTML**: `src/lib/markdown.ts` parses the text with `mdast-util-from-markdown` and GFM (Architecture › Dependencies) and keeps a closed tree of its own: paragraphs, headings, emphasis, strong, strikethrough, inline code, code blocks, lists (with their checkboxes), quotes, GFM tables, breaks and rules. `Markdown.svelte` and `MarkdownNode.svelte` draw it with Svelte's own elements, so nothing goes through `{@html}`, which `svelte/no-at-html-tags` refuses and no comment may silence.
- **Headings one level down**: `#` is an `h2`, `##` an `h3`, and so on up to `h6`, since the agent's title is the `h1` of its screen (Look › Components) and VoiceOver walks a screen by its headings. They all look the same (`.heading`), so only the outline changes.
- **What is not drawn as itself**: raw HTML stays as its text, a link as its words, an image as its `alt`, and a node the tree does not know as its text. An `<a>` in the WebView would take the user out of the app; the CSP already blocks images from elsewhere, but no `<img>` is drawn either. Links that open are left out.
- **Code blocks and tables scroll sideways** inside their own container, the code in `--font-mono`, so the screen itself never does. The text is parsed in the WebView at each read and not virtualised: a message of tens of KB is accepted as it is.

## The screen

- **Above the header**: `Back` and, while it has its row, `Terminal`, both 44 px plain buttons; `Terminal` opens the agent's pane in the passive terminal over the chat (Terminal › Opening it). Gone, the screen offers only `Back to the board`.
- **Header**: the `StatusDot`, the agent's title (`label`, as on the board), its status in words (`statusName` in `src/lib/board.ts`, which also names the dot for screen readers), and the place with the tab, `project › workspace › tab`, from the latest rows.
- **When it was written**: `written` in the board's format (Board › Since when), with its own timer every 30 s; nothing when the record has no time.
- **The field stays at the bottom** (`position: sticky`) on glass, over the safe area, so it can be reached while a long message scrolls. WKWebView scrolls a field that takes focus above the keyboard; the finer fit is 021's and 032's.
- **One `Chat` per opened pane of a machine**, which `App` makes when the route opens it and drops on `Back` (`src/App.svelte`). It lives on under the agent's terminal and under Machines (and a machine) opened from the connection bar over it (`Router.opened` in `src/lib/router.svelte.ts` is `chatOf` of the highest `agent` or `terminal` of the stack, skipping `machines` and `machine`; `chatOf` is the machine and pane of `agent` and of `terminal`'s row, and `App` makes a new `Chat` only when one of the two changes), so coming back keeps the text typed and the message read, and it goes on hearing its events meanwhile. Rejected: a new `Chat` on coming back, which lost the text typed and read the message again; and, for Machines, dropping the `Chat` while it shows, the same loss on a `Back` that changed nothing. Under Machines, switching to another machine or removing the active one leaves the `Chat` gone by the rules below (another machine, or none), and so does a tap on the active machine's own row, which connects it again and turns its rows `null`: accepted, a new connection that may be a restart, rather than a second rule telling a reconnection to the same server from one to a new server. `App` gives it the active machine with the rows of each `agents-changed`, and the `pane-status-changed` events that match its machine and pane (`touches`). A failed send reaches `App` as its reason, for the toast.
- **A `Chat` belongs to the machine its route was opened on**, since pane ids are each server's own (Look › Navigation): once the active machine is another one, or none, it is gone for good, even if the new machine lists a pane with its id, so it never reads or sends to that pane on the new machine. This is the check `openedAgent` made before the chat (027), moved into `Chat.see`, which already decides when the agent is gone; rejected: keeping `openedAgent` beside it, two places deciding the same thing.

## Gone

- **The agent is gone** when a list of rows lacks its pane (the pane was closed, or the agent quit and left its shell), or when the rows turn `null` after the screen had seen its row (a restart, a new `Store`), or when the active machine is not the one it was opened on (The screen). Then it says `This agent is no longer running.` with `Back to the board`, the field goes and the text typed is lost.
- **For good**: a later list with the same pane does not bring it back. After a restart the server may give that id to another agent, and the screen must neither show that agent's text nor send it what was typed for the first one (Upstream gaps › `--boot`).
- **Before the first list** (`null` without having seen the row: connecting, a new `Store`) the screen does not know yet and shows the board's mark (Board › A row).

## Checked live

- **On 2026-11-09** in the iPhone 17 simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5), against the bridge on the LAN and cornercase 0.13.19, with Claude Code 2.1.319, the taps made by XCUITest. A Claude in `done` showed its one sentence with when it was written. An answer that starts with `--`, typed in the field and sent, emptied the field and turned the header to working in the same second; the queue opened its `requests --follow` at that first send. While it worked, the screen kept the old message, since the agent ran a tool first and wrote no text. When it finished, 16 s later, its new message showed within a second of its record's time: a heading, a list with inline code, and a code block wider than the screen that scrolls sideways.
- **Waiting**: asked from the field to put a question with `AskUserQuestion`, the agent turned `waiting` 2 s later, and the screen showed the note over the field, with `Send` resting while text was typed.
- **Gone**: closing its pane on the Mac (`cornercase close --pane`) while it waited turned the screen into `This agent is no longer running.`, the field and its text gone, and `Back to the board` returned to a board without its row.
- **The keyboard**: when the field takes focus, WKWebView scrolls the page so the field, grown to its maximum, stays above the keyboard and its bar, the header out of sight, with a gap between them. It can be reached; the finer fit stays 021's and 032's.
- **Keys, on 2026-11-09** in the iPhone 18 Pro simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5, `tauri-plugin-haptics` and `@tauri-apps/plugin-haptics` 2.4.2), against the bridge on the LAN and cornercase 0.13.19, with Claude Code 2.1.319, the taps made by XCUITest. On its screen, 402 px wide, the row takes two lines: `Esc` to `→`, then `Enter`, `Ctrl-C` and `0–9`. A Claude that asked `Which colour?` with `AskUserQuestion` showed `waiting` and its note; `↓` moved its menu from `1. Red` to `2. Green` on the Mac, the queue opening its `requests --follow` with that first key, and `Enter` chose it: the agent answered `You picked Green.` and the screen showed it, done.
- **`Ctrl-C`**: while the agent wrote a long story, the first tap turned the button red with `Tap again to interrupt`, and the second, a second later, interrupted it once: Claude Code showed `Interrupted · What should Claude do instead?` and stayed open, and the header turned idle. One tap alone on the idle agent let go after 3 s, back to `Ctrl-C`, and Claude Code showed no `again to exit`: nothing was sent.
- **Haptics**: the simulator has no Taptic Engine, so only that nothing fails was checked: every tap sent its key, no toast showed, and the app's log held no error of the plugin. Not felt on an iPhone yet, which needs a signing team.

## Left out

- The history and bubbles with the answers already sent (Upstream gaps), links that open, images inside a message.
- `--force` (sending over a dialog or a poll) and `held --send-now` / `--wait-turn`.
- Keys other than the row's: other combinations (`shift+tab`, `ctrl+o`, `ctrl+r`), function keys, `Backspace` and `Space`, a `Ctrl` that sticks and the keyboard over the terminal, which belong to typing in a terminal (021). Marking a key as sent before its answer.
- Notifications, and reading several panes at once (`read` with several `--pane`).
