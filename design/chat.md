# Chat

The agent's screen a row of the board opens (`src/routes/agent/Agent.svelte`, Board › A row): its header, which stays at the top (The screen), a thread of the conversation as the phone saw it, your sends and the agent's messages as markdown, kept on the phone (Kept on the phone), and a live line of what the agent does (The thread), and a composer to answer it (`src/routes/agent/Composer.svelte`): a rounded capsule with the field for text (Answering) and an icon that opens a row of keys over it to answer with a key (Keys). Its state lives in `src/lib/chat.svelte.ts` (`Chat`), without markup, so vitest tests it; the commands come in by injection, as in `addMachine.svelte.ts`. The thread's rules are pure functions in `src/lib/thread.ts`, with `now` as an argument, as `board.ts` does, and the conversation's in `src/lib/history.ts`. The capsule's `+` attaches images from the phone's photos, which wait on the phone and reach the agent's input with the next send (Attaching an image).

## Reading the message

- **What is read**: `read --last-message --pane P --json` (`crates/core/src/cli/last_message.rs`, `LastMessage`): the pane, the agent, the text, and `written` and `turn_over` when the agent's record has them. Every field has a default and unknown keys are ignored, so what upstream adds breaks nothing. It is the newest text of the assistant, also halfway through a turn, and nothing older, so the conversation is only what the phone read (The thread, Upstream gaps). The fixture (`crates/core/tests/fixtures/control/last-message/`) is that command's output from cornercase 0.13.19.
- **One-shot, beside the queue**: the `last_message` command runs `transport::json` on the transport of the route the `Store` connected on (`Store::transport()`, Connection › Store), as Connection › the ordered queue says for the reads that order nothing. A transcript can hold tens of MB, so a slow read must not hold a key or a send. Without a `Store` or before its first connection it answers `not_connected`.
- **A message that cannot be read** (no message yet, a record not found yet, an agent whose record cornercase does not read, such as Grok) shows cornercase's reason, without its `Error:`, in `--muted` at the end of the thread, above the live line, under the conversation kept, which it never takes away. It is the state of the screen until the next read, not the failure of something the user did, so it is not a toast. `Reading its last message…` shows the same way until the first answer. Only cornercase's own refusal (`failed`) shows there over a message read: a read lost on the way (the connection dropped, no answer, no machine connected, a call to Rust that throws) keeps the message already shown, and shows its reason only while there is none. Over LTE a read can fail without anything having changed, and the next event or new stream reads again.
- **When it is read again**: once the screen has its row, then on every `pane-status-changed` of its machine with its pane, or with `pane: null`.
  - **Every 10 s while it works and shows**: an agent's message grows within a turn without a status change, so while the agent is `working` the screen also reads it every 10 s (`FOLLOW_MS`, `Chat.follow`). Only while the screen is in sight: `Agent.svelte` is mounted only while no terminal nor Machines is over it, and follows only while `document.visibilityState` is `visible` (`whileShown`), so the app in the background, a screen over the chat and an agent `waiting`, `done` or idle read nothing on a timer. The timer asks through One read at a time, so a slow read is never doubled. This reverses 016's choice, no polling, "accepted, rather than a read every few seconds over LTE": on the user's iPhone, on 2026-11-09, a message from before a turn of minutes stayed on the screen, and nobody could tell a working agent from a stuck one (The thread › No news). A read is one `read --last-message`, which upstream reads from the end of the transcript, beside the queue (One-shot), so it holds no key nor send. The status is still not read on a timer: it comes with `agents-changed`. Upstream has no event for a message that grows (Upstream gaps). Rejected: no reads on a timer, with "no news" meaning no status change for 2 min, which would show in nearly every long turn; waiting for an upstream event.
  - **The event, not the snapshot**: the forwarder turns each `status` event that names a pane into `pane-status-changed { machine, pane }`, and a `dropped` event into one with `pane: null` ("read again whatever you show"), since the events lost may include this pane's. A new `events` stream is the same loss (a reconnection, the app back from the background, a network change; Board › Since when), so the `Store` sends `Change::Reopened` each time it opens the streams again, never on the first, and the forwarder turns it into `pane: null` too. Otherwise an agent that finished while the phone was locked would show `done` with the snapshot and keep the message from halfway through its turn, since no status event of its pane may come again. Rejected: the UI reading again on `connection-changed` and on coming to the foreground, a second path to the same loss that Rust already knows of. Rust reads nothing and does not know which pane the screen shows. `events` reaches the app about 500 ms before `status --follow`, and an event also shows a status that went and came back between two snapshots, after which the message is a new one.
  - Rejected: Rust reading the message itself on each event and sending it in the event. The forwarder would have to know which pane the screen shows, a state that changes with each tap and races with the reads in flight. Rejected too: the UI reading again when `row.status` changes in `agents-changed`, which comes with the snapshot and misses a status that went and came back.
- **One read at a time, one more at most**: an event during a read asks for one more, however many come, and it starts when the first ends. The reads are numbered, so a late answer never replaces a newer one, and leaving the screen discards the one in flight.

## Answering

- **The capsule** (`src/routes/agent/Composer.svelte`, how it looks in Look › Components): one rounded box that holds, in this order, `+` (`Attach image`), the keys' icon (`Keys`), the field and a round `Send`, with the buttons at its foot, so as the text grows the capsule rises and the buttons stay under the thumb. Over it, in the composer, the question, the row of keys and the images' thumbnails, in that order. The user asked for it on 2026-11-10 after trying 029 on the iPhone, as the composers of Claude, WhatsApp and Messages are; 016 to 039 had stacked the keys, the chips, the field and a `Send` with its label, which took most of a phone's height while the keys are needed mostly while the agent asks. On a phone of 375 pt the text keeps about 211 px beside three buttons of 44 px, so no fourth button fits there.
- **The field** is a `TextArea` without a frame of its own (`bare`, Look › Forms), since the capsule draws the border and the focus ring, that grows with its text up to a maximum and then scrolls. Return adds a line and only `Send` sends: on a phone's keyboard Return is the only way to break a line, and a message sent by mistake cannot be taken back. `Send` rests while there is neither text nor an image waiting, while it sends, while an image is being attached and while the agent is `waiting`.
- **Through the queue**: `send --pane P --enter --timeout 30 -` by `Queue::ask`, with the text as `Stdin::Text`, so it keeps its order with the keys (Keys). On standard input, a text that starts with `-` is not read as an option, and the text never shows in the argv the bridge logs. No message nor log holds it.
- **What comes back**: `Send` empties the field and takes the images waiting at once, and the thread shows what went as your bubble, `Sending…` (The thread). cornercase's answer turns it `Sent`, or `Not sent:` with the reason, since it answers something the user did: cornercase's refusal without its `Error:` (`waiting`, a dialog, a poll, `resuming`, `not confirmed`, a held send that ran out of time), `nothing was sent` for a job the queue skipped, `it may have been sent, but no answer came back` for one that lost its answer, and `no machine is connected` without a queue. cornercase's texts are written for scripts (`answer with cornercase keys`, `or with --force`) and are shown as they are: rewriting them would guess at upstream's words.
  - **Said by the bubble, not a toast**: the reason stays beside the text it is about, while a toast of 8 s would leave with it and leave the text nowhere. The keys keep their toasts (Keys), and so does attaching an image.
  - **`Retry` and `Edit`**: `Retry` sends the same text again with `Send`'s rules, pasting first the images it took that are not on the Mac yet (Attaching an image › When a paste fails), and rests when `Send` would (another send on its way, an image being attached, `waiting`). `Edit` puts the text back in the field, before what was typed since and apart from it by a blank line, and takes the bubble away. A failed send gives back the images it took, before those attached meanwhile.
  - **One send at a time**: `Send` is busy while a bubble is `Sending…`, and the field still takes text.
  - **The field keeps the keyboard**: `Send` cancels its `mousedown` (`preventDefault`), so the field it empties keeps the focus and the keyboard stays open for the next words (041). Without it, a tap on `Send` took the focus and closed the keyboard. WebKit on iOS moves the focus in the mouse events it makes up after a touch, not on `pointerdown`: cancelling `pointerdown`, as 041's plan said, still closed the keyboard in the simulator, as it did for the terminal's row (Terminal › The row of keys), and cancelling `touchend`, as that row does, would drop the click that sends. A tap with the field unfocused still sends.
  - **The text does not come back**: 029 reported, on the user's iPhone, the text sent showing again in the field, maybe iOS' predictive text committing a pending word after the field emptied. In the simulator with the software keyboard, predictive text and autocorrection (Checked live), the text left with the bubble in the same tap and nothing came back, so nothing else changed: closing the composition before emptying the field (a blur and a focus, which also close and reopen the keyboard, or emptying on `compositionend`), the fix held ready for it, was not needed. The iPhone is checked again by the user.
- **Your send shows at once**: 016 showed nothing until `agents-changed` turned the header `working` and the message was read again with its event, and the field just emptied. On the user's iPhone, on 2026-11-09, that read as no feedback at all: nobody could tell whether the message had gone, nor whether the agent was thinking or stuck. So the text shows as soon as it is tapped, `Sending…` until cornercase answers. It is what the user sent, not a guess at the agent's state, which still comes only from `agents-changed` and the reads.
- **`--timeout 30`**: upstream holds a send while someone types on the Mac (its `held-sends.md`). With 30 s, a held send ends in `nothing was sent` rather than waiting for ever. Meanwhile the queue is busy, so a key tapped behind it waits up to 30 s (Keys). Accepted. Rejected: 15 s, the least over the 3 s of the Enter and the 10 s of the confirmation, which leaves a held send almost no time; no timeout, which would let a held send stop the queue for good.
- **A false `not confirmed`**: a Codex that works keeps a prompt sent meanwhile in memory and records it after its next tool call, so upstream extends its 10 s confirmation up to `--timeout` (its `confirming-sends.md`). A tool call longer than 30 s then fails with `not confirmed` though Codex takes the prompt later. Accepted. The bubble says `Not sent` with that reason, which says it may not have been submitted, so the user can look before `Retry` sends it twice. Any `not confirmed` may have reached the agent for the same reason.
- **`waiting` takes no text**: upstream refuses `send` to an agent that asks a question, a permission or a choice, which is answered with a key (Keys) or an option (The question). There, `Send` rests under the agent's question, or, until its rows come, under the note `<agent> is asking you something on its screen; answer with the keys.`, and the text typed stays, as gpui's `unready` does. Rejected: sending anyway and showing the refusal, a round trip for nothing.

## The thread

- **What it holds** (`src/routes/agent/Thread.svelte`, the bubbles from `threadOf` in `src/lib/thread.ts`): the pane's conversation as the phone saw it, in the order it saw it (`Chat.conversation`, Kept on the phone), then the live line. Your sends are bubbles on the right, the agent's messages markdown with when each was written, and what the phone could not see a line, `Earlier messages are on the Mac`, in `--muted`. The order is the list's: the phone's and the Mac's clocks are never compared. A read whose `text` or `written` differs from the agent's last message kept is a new message; one that grows it (the same `written`, or a text that starts with the kept one) or only ends its turn replaces it in place (`heard` in `src/lib/history.ts`). Asked by the user on 2026-11-10 ("it should look like a chat, not only the last message"); until then the thread held one message of the agent and your last send, and a new send replaced the bubble.
  - Sending while the agent was writing, its message grows after your send and is replaced in place, above your bubble, rather than coming under it as an answer. Accepted: it is one message of the agent, and a new message starting with the old text would be taken for it growing too.
  - **The gap line** goes before a new message of the agent the phone cannot vouch for, and at the start of every conversation kept on the phone, since what came before its first read is on the Mac. The phone vouches from a message it read and from a send of this `Chat` that cornercase confirmed; opening the chat, coming back to the foreground (`Chat.follow`), a `pane-status-changed` with `pane: null` (Reading the message), the agent turning `working` or `shell` with no send of this `Chat` on its way (a prompt from the Mac or another client; a send stops being on its way at the next change of status it sees, so one made into a running turn, which changes nothing, stops counting once that turn ends; only a change between `working` or `shell` and any other status counts, so a send made while `done` still counts after a `done` to `idle`, as the `mark --reviewed` the chat sends itself) and another agent in the pane (`row.agent`) all lose that (`Chat.lose`), so the next new message gets the line. `waiting` to `working` loses nothing: that is the agent going on after an answer, which the phone may have given with the keys or the question's buttons, and a line there would split every question from its answer. Nor does `working` to `shell` or back: `shell` is a turn over with a command still running in the background (Claude Code's `run_in_background`), and `shell` to `working` is the agent waking up by itself when it ends, the same work followed on screen. The limit: a prompt from the Mac while `shell` gets no line. A send confirmed vouches for what follows it, which keeps an answer followed on screen without a line. Never two lines in a row nor one at the end: an `Edit` that would leave one takes it away too. Rejected: telling a gap by comparing `written` with the phone's clock.
  - **Between two reads**: while the agent works the phone reads every 10 s (Reading the message), so a text it wrote and replaced in between is never seen and leaves no line. Accepted: the phone cannot tell it, and cornercase's own history would close it (Upstream gaps).
- **Your bubble** (`src/routes/agent/Sent.svelte`) holds the text and, as chips, the names of the images that went with it; an image alone shows only its chips. Under it, its state: `Sending…` with the spinner, `Sent` with `check`, or `Not sent: <reason>` with `circle-alert` and, while it is live, `Retry` and `Edit` (Answering › What comes back). Its name for VoiceOver is `Your message, <state>`.
  - **Only the last send is live**: the last of your bubbles, while the `Chat` that sent it holds it (`Chat.outgoing`), keeps `Retry` and `Edit`; earlier ones, and every one loaded from the phone, show their state without buttons: their `Chat` and its images are gone, and `Edit` would bring back the text of another visit. A send still `sending` when its `Chat` went (the app killed, `Back` before the answer) shows `Not confirmed: the chat closed before an answer came back` with `circle-alert` (the chat, not the app: after `Back` the app is still open), its name for VoiceOver `Your message, not confirmed`: no answer will come for it, and it may have reached the agent, so it offers no `Retry` that could send it twice. How it looks is in Look › Components.
- **The live line** (`src/routes/agent/AgentLine.svelte`, `agentLine`) ends the thread and comes from `chat.row.status` (`agents-changed`), with no reads of its own:
  - `working`: the orbiting `StatusDot`, `<agent> is working…` and the time since `row.since` in the board's format (Board › Since when);
  - `shell`: the same, with `<agent> is waiting for a background command…`;
  - `waiting`: `<agent> is waiting for your answer`, and the composer keeps its note;
  - `failed`: `<agent> stopped with an error`, in the failure's tone;
  - `done`, `pending`, idle or a status it does not know: no line.

  Without `since`, which is the usual case on a phone after the background or a reconnection, the line has no time.
- **No news**: after `STALL_MS` (120 s) in `working` without news, the line turns `<agent> is working… · no news for N min · Ctrl-C interrupts`, in `--muted`. News is a status change, a read with another text or a confirmed send, timed on the phone's clock from the last one this `Chat` saw, or from when it opened (`Chat.lastNews`), never from `since`, which is often unknown. No alarm colour, haptic nor toast: a long turn is normal, and the next news brings the line back. The clock is the `Chat`'s injected `Clock`, so vitest moves it. It can be told only because the message is read while the agent works (Reading the message › When it is read again): without those reads every long turn would say it after 2 min.
- **One live region**: a single `aria-live="polite"` node in the line holds the send's state (`Sending`, `Sent`, `Not sent: <reason>`, hidden from the eye, since the bubble shows it) and the agent's phrase. The time runs outside it, and with no news so do its minutes and `Ctrl-C interrupts`, so VoiceOver says each change of phrase and not each tick. It stays in the page while the line has nothing to show, so `Sent` is still said to an agent that is done. Rejected: a region for the bubble and one for the line, which could speak at once.
- **A message that grows** is replaced in place: a read never goes back to `Reading its last message…`, so the text grows rather than flashing and the height does not jump. Before each read or bubble that changes the thread, once a message shows, the screen checks whether the page, or the thread's own box while the keyboard is open (The screen › With the keyboard open), is at its end, within 48 px (`atEnd`); if it was, it scrolls to the end once drawn, and otherwise it stays where it is, so reading higher up is never taken away. On opening, the thread goes to its end once the conversation kept draws, even when the first thing drawn is a long message just read; from then on, the rule above. A message with `turn_over === false` ends with `More to come…` in `--faint`, only the agent's last one: an earlier one was followed by others.

## Keys

- **The row** (`src/routes/agent/KeyRow.svelte`) sits in the composer over the thumbnails and the capsule, under the question, while it is open (Behind an icon), and can be opened while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent. It holds `Esc`, `Tab`, `↑`, `↓`, `←`, `→`, `Enter`, `Ctrl-C` and `0–9`, which unfolds the digits. Each button is a name of cornercase's `KEY_NAMES` (`src/lib/keys.ts`, its label, its name for VoiceOver and its key): the keys an agent's menus, permissions and confirmations take, the arrows and `Enter` to move and choose, a digit to choose an option by its number, `Esc` to cancel, `Ctrl-C` to interrupt. `src/lib/keys.ts` holds no markup nor state, so the terminal's row (021) can take its names too.
- **Behind an icon**: the row folds behind `Keys` in the capsule (Lucide's `keyboard`, with `aria-expanded`), and a tap opens or closes it. Its state lives in `Chat` (`keysOpen`, `toggleKeys`), without markup, so it lives on under the terminal and Machines as the rest of the `Chat` does and vitest tests it (`src/lib/chatKeys.test.ts`).
  - **Closed at first, open while the agent asks**: each `Chat` starts with it closed. When the row turns `waiting` (`Chat.see`) it opens on its own, since a key is how a question is answered; when the row leaves `waiting`, it closes on its own only if `waiting` opened it. Opened by hand, for a `Ctrl-C` during `working` say, it stays open; closed by hand during `waiting`, it stays closed until the next `waiting`. Rejected: closing it whenever `waiting` ends, which closes keys the user opened. A `waiting` that comes and goes within a second (The question › Its limit) opens and closes it with the question; accepted, as it follows `row.status` like the question does.
  - **Closing disarms `Ctrl-C`**: an `Again?` that nobody sees must not stay armed for a later tap.
  - **One tap more for `Ctrl-C`**: the line of no news still says `Ctrl-C interrupts` (The thread), and the key is now behind the icon. Accepted; rejected for now: that line opening the keys.
- **`0` too**, though the task asked for `1`–`9`: upstream closes Claude Code's survey with `keys --pane N 0` (its `confirming-sends.md`), and `send` refuses a pane with the survey open, so without it the phone could not take it away. The digits go `1` to `9`, then `0`, as on a keyboard.
- **Every key in sight**: buttons of 44 px (Look › Touch and motion), with no more width than their label and the arrows drawn as Lucide icons named `Up`, `Down`, `Left` and `Right`; on a phone 393 px wide the row breaks into a second line rather than scrolling sideways. The digits unfold in a row of their own over the keys, behind a button with `aria-expanded`, and stay open after a digit is sent until that button is tapped again, so `↑` or another number can follow without opening them again. They start folded; the `initialDigits` prop, which only the tests pass, draws them open, since a server render cannot tap. Rejected: one row that scrolls sideways, which hides keys out of sight; the arrows on a fixed line of their own; digits that fold on their own after one is sent.
- **`keys`, not `input`**: each tap queues `keys --pane P <key>` by `Queue::ask`, without standard input (`crates/core/src/cli/keys.rs`, the `keys` command of `src-tauri/src/commands/chat.rs`, which take a list, each key checked against cornercase's names and an empty list refused (`no key to send`), so a chip of the question sends its arrows in one call: The question › The card), on the `requests --follow` the sends go through, so keys and sends reach the agent in the order they were tapped. `keys` is upstream's way to answer an agent (`send` refuses `waiting` with `answer with cornercase keys`), its `enter` counts as submitting a turn, and it answers each key, so a key that fails gets a toast with a send's reasons (Answering › What comes back), since a key has no bubble, and success shows nothing: the status comes with `agents-changed` and the message with the next read, as after a send. `input` (the typist, Connection › the ordered queue) is someone typing in another window, the terminal's (021), and answers nothing a toast could say. The UI does not wait for a key's answer before sending the next one: `↓ ↓ Enter` keep their order in the queue, which is the order their commands reach `Queue::ask`. Each `invoke` runs as a task of its own on Tauri's multi-threaded runtime, so two within the same instant could swap; taps are tens of ms apart, and a send (Answering) has the same bound. Rejected: chaining the calls in the UI, each `invoke` waiting for the previous one to be queued, which needs a second command (one that queues, one that waits for the answer) for a race no finger makes.
- **Only the app's keys reach the argv**: the core takes only the 18 names the app sends and refuses any other (empty, `-x`, `shift+tab`) before anything is queued, so a key can never turn into an option of `keys`.
- **`Ctrl-C` asks for a second tap**: the first one sends nothing; it turns the button to the danger tone with `Again?`, its name for VoiceOver turns `Tap again to interrupt`, and a live region says it. A second tap within 3 s sends `ctrl+c` once; after 3 s, or on any other key, it lets go without sending. Two `ctrl+c` in a row quit Claude Code and leave its shell, and the screen turns gone, so one tap must never send it by mistake; a third tap arms it again rather than sending a second one. Rejected: a long press, which WebKit on iOS takes for itself without a click (Look › Touch and motion) and VoiceOver hardly does; a confirmation dialog, one more screen for a key.
  - **Same width, said aloud**: the live region is a `.spoken` span beside the rows, not inside the button: the children of a `button` are presentational and its `aria-label` hides them, so VoiceOver could miss a change there. The button keeps its width when armed: `Ctrl-C` and `Again?` share one grid cell (`.steady`) and only the one in use shows, so the row does not wrap again between the two taps and the second one lands where the first did. Rejected: `Tap again to interrupt` as the visible text, about 120 px wider, which could push `Ctrl-C` to the next line under the finger; a fixed `min-width`, a number to keep in step with the font.
- **`Esc` asks for nothing**: in Claude Code it interrupts an agent that works, as `Ctrl-C` does, but never quits it, and two in a row open its rewind. Accepted: it is the key a menu takes to cancel, and a confirmation would slow every menu down.
- **A light tap**: each tap that sends a key, and the one that arms `Ctrl-C`, asks the haptics plugin for `impactFeedback('light')` (`src/lib/haptics.ts`, Architecture › Dependencies), since what a key does often shows only on the Mac. Without the plugin (the desktop, the tests) or when it fails, nothing shows and the key still goes: it is not a failure of what the user did, so there is no toast.
- **Behind a held send** a key waits, as every job behind it does, up to the 30 s of `--timeout 30` (Answering).
- **Nothing to another pane**: a `Chat` gone, or of another machine, sends no key (The screen), and its screen shows no row. `keys` has no `--boot` either (Upstream gaps).

## The question

- **What it shows** (`src/routes/agent/Question.svelte`): while the agent is `waiting`, the composer holds, over the row of keys, the question (a menu of `AskUserQuestion`, a tool's permission, an approval), read from the rows of its screen: as a card laid out to the phone's width when the rows read as one (The card), else as those rows, drawn as the terminal draws them, with a button per numbered option between them and the keys (The fallback). Until the first rows come, and whenever there are none, the note of `waiting` shows instead (Answering). The row of keys stays as it was, under the options: `↑`, `↓` and `Enter` move and choose in the menu, and the card or the block shows the selection move.
- **Read from the screen, as upstream's Telegram does**: cornercase says that an agent waits (`status`, with `dialog: true` while a dialog shows) but not what it asks, and reading the agent's records is not the contract (Upstream gaps). Upstream's own Telegram bot answers the same question from the screen: the last 15 rows of the pane and a button per numbered option (`src/app/messenger/notices.rs`, which calls `messenger::choices` in `src/messenger/mod.rs`, #248). The chat does the same through the public `surface`, so it is no workaround, and the gap is named so that data can replace it.
- **A passive `surface` of its own** (`crates/core/src/terminal/asking.rs`, `Asking`): `surface --tab T --cols 80 --rows 24 --patches`, with no `view`, as the terminal's with its switch off (Terminal › Passive with the switch off): the terminal opens fitted since 043, the question's reader stays passive, so the Mac's PTY keeps its size and `status` shows no `controller` for the phone. `--cols` and `--rows` are required but change nothing without a `view`: two captures of the same moment at 80×24 and at 40×60 had the same lines, with the pane at the PTY's size and all its rows, so the size is a constant and `question_open` takes only the tab and the pane. It runs over the terminal's `Live` and the core's reopening loop (`follow::reopen`, Changes and files › Following the list), with only the pane asked for: when it is not in the frame (closed, moved to another tab), the question is empty (`rows: []`), so the note comes back, never another pane's screen, which the WebView would drop while it kept showing the old question (review of 2026-11-10). Rejected: the terminal's choice (`Shown`, Terminal › One pane on the phone), which falls back to the active pane or the first. Rejected: cropping the rows the terminal's `Update` carries, which holds only the rows that changed, so the pane would be rebuilt again outside the grid; a `view` with the phone's size, which resizes the Mac.
- **Its cost**: a second process on the Mac and the tab's patches over the transport, only while the chat of a `waiting` agent shows; the crop runs on each change and the WebView hears only a question that differs from the last one, at most one `question-changed` per frame of 16 ms (`commands/chat/question.rs`, through the terminal's `by_frame`). As with the terminal, a passive `surface` never counts as seen, so the Mac's notice goes on.

## Attaching an image

- **The button**: `Attach image`, Lucide's `plus` in an icon button of 44 × 44 px, the first in the capsule (Answering › The capsule). It can be tapped while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent, since the image only waits on the phone until the next send. While the picker is open and the image is read, it is busy, with the spinner in place of its icon, and takes no second tap; with 4 images waiting it is disabled (Kept on the phone). Its state lives in `src/lib/attach.svelte.ts` (`Attachments`, one per `Chat`), with its commands injected like the others.
- **The picker**: iOS's `PHPickerViewController`, images only, one at a time, from a plugin of our own (`src-tauri/plugins/photos`; Architecture › Plugins of our own, which also says why not `tauri-plugin-dialog`). It runs out of the app's process and needs no access to the photo library, so there is no permission to ask nor `NSPhotoLibraryUsageDescription`. Cancelling it (its `Cancel`, or a swipe down) does nothing: no toast and no thumbnail.
- **Shrunk on the phone, by the system**: ImageIO makes a thumbnail (`CGImageSourceCreateThumbnailAtIndex`) whose longest side is at most 2,048 px, with its proportions; a smaller image keeps its size. The EXIF orientation is applied, and the image is encoded again from its pixels, so no metadata (the GPS position included) goes to the Mac. PNG when the source is PNG (screenshots, transparency), JPEG at quality 0.85 otherwise, HEIC included. ImageIO reads only what the thumbnail needs, not a 48 MP photo whole. The name that goes is the picker's suggested name with the extension of what was written (`IMG_0042.HEIC` becomes `IMG_0042.jpg`), or `pasted.png` or `pasted.jpg` without one (`crates/core/src/cli/paste_file.rs`). Only an image's extension is replaced (`png`, `jpg`, `jpeg`, `heic`, `heif`, `gif`, `webp`, `tif`, `tiff`, in any case): the picker often suggests a name without one, and a name with dots is kept whole (`Screenshot 2026-11-09 at 10.42.13` becomes `Screenshot 2026-11-09 at 10.42.13.png`, not `… at 10.42.png`).
- **And a small one to show**: from the same source, ImageIO makes a second thumbnail whose longest side is at most 192 px, JPEG at 0.7, a few KB, for the composer (The thumbnails). If it cannot be made, the image still goes, without it. Rejected: 018's chip of text with a `×` added, while the task asked for a thumbnail.
- **The bytes never reach the WebView**: Swift writes both images to the app's temporary folder and answers Rust with their paths, the name and the kind. The `attach(pane)` command (`src-tauri/src/commands/chat/attach.rs`) reads the files and removes them at once, also when one cannot be read. It refuses an empty image, and one over 32 MiB (upstream's `MAX_IMAGE_BYTES`, its own cap). The WebView gets the image's id, name and size and the small thumbnail as a `data:` URL (`thumbnail_url`; the CSP allows `img-src data:`), or `null` for a cancel; never the image.
- **Kept on the phone until `Send`** (041): attaching no longer pastes. The image waits in `AppState` (`src-tauri/src/state/attached.rs`) under its id and its pane, and goes to the Mac only with the next send (Sending). 018 pasted it as it was attached, so its path was in the agent's input before the user had decided to send it, and a path typed into the agent's input cannot be taken back (Upstream gaps). The user asked on 2026-11-10 to remove an image before sending, as Claude and WhatsApp let one do: kept on the phone, its `×` drops it, and the Mac never gets it. It also ends 018's chips that outlived the screen: an image left unsent leaves no path in the agent's input. Accepted, as in Claude and WhatsApp. Rejected: pasting on attach with a `×` that only hides the chip, which sends the image anyway; pasting on attach with a `×` that sends `keys backspace`, a workaround that depends on how each agent shows the path (Claude Code turns it into `[Image #1]`) and on an input the chat cannot see.
  - **Bounded, since it is memory**: at most 4 images per pane (D5 of 041, a limit of memory nobody asked for), after which `+` is disabled, and 64 MiB over all the panes, since a PNG of 2,048 × 2,048 px can weigh 12 MB; past either, `attach` refuses with a toast.
  - **Released** when its `×` removes it (`discard(ids)`), once pasted, when the `Chat` goes (`Back`, the agent gone, another machine; `Chat.leave`, which `App` calls as it drops the `Chat`) and when the WebView starts loading a page (`lifecycle::on_page_load`): a WebView loaded again has lost the ids, and nothing else would release them.

## Markdown

- **A tree, never HTML**: `src/lib/markdown.ts` parses the text with `mdast-util-from-markdown` and GFM (Architecture › Dependencies) and keeps a closed tree of its own: paragraphs, headings, emphasis, strong, strikethrough, inline code, code blocks, lists (with their checkboxes), quotes, GFM tables, breaks and rules. `Markdown.svelte` and `MarkdownNode.svelte` draw it with Svelte's own elements, so nothing goes through `{@html}`, which `svelte/no-at-html-tags` refuses and no comment may silence.
- **Headings one level down**: `#` is an `h2`, `##` an `h3`, and so on up to `h6`, since the agent's title is the `h1` of its screen (Look › Components) and VoiceOver walks a screen by its headings. They all look the same (`.heading`), so only the outline changes.
- **What is not drawn as itself**: raw HTML stays as its text, a link as its words, an image as its `alt`, and a node the tree does not know as its text. An `<a>` in the WebView would take the user out of the app; the CSP already blocks images from elsewhere, but no `<img>` is drawn either. Links that open are left out.
- **Code blocks and tables scroll sideways** inside their own container, the code in `--font-mono`, so the screen itself never does. The text is parsed in the WebView at each read and not virtualised: a message of tens of KB is accepted as it is.

## Gone

- **The agent is gone** when a list of rows lacks its pane (the pane was closed, or the agent quit and left its shell), or when the rows turn `null` after the screen had seen its row (a restart, a new `Store`), or when the active machine is not the one it was opened on (The screen). Then it says `This agent is no longer running.` under the bar and its back button, the field goes, and the text typed is lost; the conversation stays on the phone (Kept on the phone).
- **For good**: a later list with the same pane does not bring it back. After a restart the server may give that id to another agent, and the screen must neither show that agent's text nor send it what was typed for the first one (Upstream gaps › `--boot`).
- **Before the first list** (`null` without having seen the row: connecting, a new `Store`) the screen does not know yet and shows the board's mark (Board › A row).
- **An agent the app just started** has no row yet: `Chat.see` takes `starting` from its route, and until the row comes a list without the pane does not count it as gone, while the screen says `Starting <agent>…` (Starting work › After it starts). Once the row was seen, or on another machine, the rules above hold.

## Kept on the phone

- **Where** (`crates/core/src/history.rs`, `crates/core/src/history/store.rs`, `src-tauri/src/commands/history.rs`): a folder per machine under `history/` in the app's cache folder (`app_cache_dir()`), with `index.json`, `{version: 1, boot, panes}` with the panes from the one written last to the oldest, and a `<pane>.json` per pane, `{version: 1, boot, entries}`, each written whole by Rust with `write_atomically`, as `machines.json` is; never `localStorage`, nor the WebView writing files. The cache rather than the data folder beside `machines.json`: it stays out of iCloud and the device's backups, as the Keychain's entries are `ThisDeviceOnly` and Android has `allowBackup="false"` (Android › Backups), and what the conversations say should not leave the phone. iOS may empty it when space runs short, and the chat then starts again with its gap line, an honest loss. Rejected: the data folder, which iOS backs up.
- **The entries**: `you` (the text, the names of its images, which show as chips, and `sending`, `sent` or `failed` with its reason), `agent` (the text, `written` and `turn_over`) and `gap`, each with an `id` that grows per pane, so a send's new state, `Retry` and `Edit` touch the same entry, and `seen`, the phone's clock when it was kept. The order is the list's, never sorted by `seen`. Not kept: the draft, the images and their thumbnails, and the reads that load, fail or are lost.
- **Caps**: 200 entries and 1 MiB serialized per pane, dropping the oldest and leaving a gap line at the start, never two; 50 panes per machine, dropping the one written longest ago, by the index's order rather than the files' times, which tests cannot trust. The bytes are capped too because messages of tens of KB would make a pane's file several MB, written again at each change.
- **One `boot` per machine**: the index holds the `boot` of the server last seen, and a load or save with another one deletes the machine's folder first, since after a restart a pane's id can name another agent (Gone › For good); a `boot` that comes back finds nothing. A closed pane keeps its file until the caps or a new `boot` drop it: a `Chat` also turns gone when the user switches machines, which must delete nothing.
- **Written whole, in order**: `Chat` hands the whole list to its `History` at each change (`keep`); one `LocalHistory` for the whole app (made in `App.svelte`, not per `Chat`) chains every write and load, so a load waits for the writes before it and a write for the loads before it, also across visits (`Back` and in again), and `open` hands back a `keep` tied to the pane and `boot` it opened, so an old `Chat` never writes where a newer one opened; Rust holds a `Mutex` over the store, which serialises the calls but does not order them. So a slow write never lands after a newer one. Rejected: a `LocalHistory` per `Chat`, whose chain the next visit's load did not wait for. The conversation loads once the row gives its `boot`, and what is sent or read meanwhile applies over what loaded, so a read that comes before the file neither doubles nor gets lost.
- **Failures**: a file that cannot be read, a broken one or one of another version reads as empty, and the next write replaces it, without a toast. A failed read, write or delete goes to the log as `cornercase-mobile: the history was not read: <code>` (`saved`, `removed`), never with the text or an image's name, and stops neither sending nor reading.
- **Behind `History`** (`src/lib/history.ts`): `Chat` loads and keeps the conversation only through it, `open(machine, boot, pane)`, which gives the entries and the `keep(entries)` for that place, injected as its other commands are (`LocalHistory` from `App.svelte`, `fakeHistory` in the tests); no component calls `history_load` or `history_save`. So cornercase's own history can take its place without changing the screen: once `contract` names `read-messages` (Upstream gaps › Conversation history), a `History` over `read --messages --pane P` gives the conversation from cornercase, the Mac's sends included, and what the phone keeps only fills in what cornercase has not given yet (your send while it is `Sending…`, a message that grows), with no gap lines, since cornercase answers for what came before. Not built now: the command does not exist upstream and its format is our draft, so its reader would be tested against a made-up fixture (task 048).
- **Forgotten with its machine**: removing a machine (`machine_remove`) deletes its whole history folder (`release` in `src-tauri/src/commands/machines.rs`), once the machine is gone from the list; a removal that fails to save the list keeps both. Merging a code into a machine (`machine_merge`) only adds routes and tokens to it and removes no machine, so it deletes nothing; two entries for one Mac become one when the user removes the duplicate, which forgets that one's history. Switching the active machine deletes nothing. A failed delete goes to the log as `cornercase-mobile: the history was not removed: <code>`, without a toast, and leaves the folder behind.

## Seen from the phone

- **Opening a `done` agent reviews it**: while the agent's screen or its terminal (passive or fitted) is on top and the page shows, a row in `done` sends `mark --pane P --reviewed` through the ordered queue (`mark_reviewed` in `src-tauri/src/commands/chat.rs`, `crates/core/src/cli/mark.rs`), once per arrival at `done`: on opening, on coming back to the foreground, and when the row turns `done` in sight. Upstream clears the `✓` without a view and without touching sizes, so the board drops its `✓` (out of Done by sections, its status in the tree) by the `status` event the `Store` already follows, with no state of its own (Board › Sections). Asked for in 029: opening is reviewing, with no button; whoever wants a reminder has `pending`.
- **Only `done`**: `--reviewed` also clears `pending`, the mark the user sets by hand, and `pending` wins over `done` in `status`, so a row in any other status sends nothing. A Mac that marks `pending` between the phone reading `done` and the `mark` arriving loses it (Upstream gaps).
- **Where it is watched**: `App.svelte`, not the agent's screen, since with its terminal on top the screen is not mounted. The `Chat` lives on under changes, a diff, files and Machines (The screen), so the watch follows `chatOf` of the top route, which is the chat only while an `agent` or `terminal` is on top, with `whileShown(document, …)` as the screen's other follows. `Chat.watchDone` keeps "marked for this arrival" as the row's `since`, which changes with every change of status (Board), not by time, so opening and the event at once send one, and a new arrival at `done` whose step in between the phone missed (a lost `working`, a reconnection, a whole `status` again) is marked too. A `since` that is filled in (the session showed `done` before the `status` event, Board) or lost (`Dropped`, a reopened stream) is the same arrival: only one time replacing another known time marks again, since a second `mark` of one arrival would go down the queue behind the first and widen the race with a `pending` set on the Mac. The cost: when a `mark` sent with no known `since` fails and the agent reaches `done` again with no status in between seen, that arrival is not tried again.
- **A failure** (no agent cornercase reads in the pane, a closed pane, the transport down, a reconnection that skips it) goes to the app's log, a line `cornercase-mobile: mark --pane P --reviewed failed: <reason>` on stderr written in Rust (the unified log on iOS, `logcat` on Android, as Connection › Network), without a toast; a `console.warn` in the WebView would only show with Web Inspector. It is tried again only on the next arrival at `done` or the next watch.
- **No `--boot`**: `mark --boot` exists since 0.13.30 with no feature naming it, and an older CLI refuses it, so the `mark` goes without, as `send` and `keys` (Upstream gaps › `--boot`).
- **Also with the fitted terminal**: its own view already counts as seen (Terminal › Seen while fitted), so the `mark` is redundant there, and harmless: it only goes for a row in `done`, never one in `pending`. Kept so that one watch covers the chat, the terminal with its switch off and fitted, rather than asking the terminal whether it is fitted.
- **Rejected**: the chat opening a sized `view` of its own to count as seen, which claims the tab and shrinks the Mac's PTY to the phone's width just to read the chat, though the terminal, fitted, does claim it (Terminal › Fitted by default); and doing nothing, which left the `✓` on the Mac and the row in Done after reading it on the phone.
