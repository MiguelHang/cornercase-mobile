# Chat

The agent's screen a row of the board opens (`src/routes/agent/Agent.svelte`, Board › A row): its header, which stays at the top (The screen), a short thread with the agent's last message as markdown, your last send and a live line of what the agent does (The thread), and a field to answer it with text, with a row of keys over it to answer with a key (Keys). Its state lives in `src/lib/chat.svelte.ts` (`Chat`), without markup, so vitest tests it; the commands come in by injection, as in `addMachine.svelte.ts`. The thread's rules are pure functions in `src/lib/thread.ts`, with `now` as an argument, as `board.ts` does. A button beside `Send` pastes an image from the phone's photos into the agent's input (Attaching an image).

## Reading the message

- **What is read**: `read --last-message --pane P --json` (`crates/core/src/cli/last_message.rs`, `LastMessage`): the pane, the agent, the text, and `written` and `turn_over` when the agent's record has them. Every field has a default and unknown keys are ignored, so what upstream adds breaks nothing. It is the newest text of the assistant, also halfway through a turn, and nothing older: there is no history to show (Upstream gaps). The fixture (`crates/core/tests/fixtures/control/last-message/`) is that command's output from cornercase 0.13.19.
- **One-shot, beside the queue**: the `last_message` command runs `transport::json` on the transport of the route the `Store` connected on (`Store::transport()`, Connection › Store), as Connection › the ordered queue says for the reads that order nothing. A transcript can hold tens of MB, so a slow read must not hold a key or a send. Without a `Store` or before its first connection it answers `not_connected`.
- **A message that cannot be read** (no message yet, a record not found yet, an agent whose record cornercase does not read, such as Grok) shows cornercase's reason, without its `Error:`, in `--muted` in the message's place. It is the state of the screen until the next read, not the failure of something the user did, so it is not a toast. `Reading its last message…` shows the same way until the first answer. Only cornercase's own refusal (`failed`) takes the message's place: a read lost on the way (the connection dropped, no answer, no machine connected, a call to Rust that throws) keeps the message already shown, and shows its reason only while there is none. Over LTE a read can fail without anything having changed, and the next event or new stream reads again.
- **When it is read again**: once the screen has its row, then on every `pane-status-changed` of its machine with its pane, or with `pane: null`.
  - **Every 10 s while it works and shows**: an agent's message grows within a turn without a status change, so while the agent is `working` the screen also reads it every 10 s (`FOLLOW_MS`, `Chat.follow`). Only while the screen is in sight: `Agent.svelte` is mounted only while no terminal nor Machines is over it, and follows only while `document.visibilityState` is `visible` (`whileShown`), so the app in the background, a screen over the chat and an agent `waiting`, `done` or idle read nothing on a timer. The timer asks through One read at a time, so a slow read is never doubled. This reverses 016's choice, no polling, "accepted, rather than a read every few seconds over LTE": on the user's iPhone, on 2026-11-09, a message from before a turn of minutes stayed on the screen, and nobody could tell a working agent from a stuck one (The thread › No news). A read is one `read --last-message`, which upstream reads from the end of the transcript, beside the queue (One-shot), so it holds no key nor send. The status is still not read on a timer: it comes with `agents-changed`. Upstream has no event for a message that grows (Upstream gaps). Rejected: no reads on a timer, with "no news" meaning no status change for 2 min, which would show in nearly every long turn; waiting for an upstream event.
  - **The event, not the snapshot**: the forwarder turns each `status` event that names a pane into `pane-status-changed { machine, pane }`, and a `dropped` event into one with `pane: null` ("read again whatever you show"), since the events lost may include this pane's. A new `events` stream is the same loss (a reconnection, the app back from the background, a network change; Board › Since when), so the `Store` sends `Change::Reopened` each time it opens the streams again, never on the first, and the forwarder turns it into `pane: null` too. Otherwise an agent that finished while the phone was locked would show `done` with the snapshot and keep the message from halfway through its turn, since no status event of its pane may come again. Rejected: the UI reading again on `connection-changed` and on coming to the foreground, a second path to the same loss that Rust already knows of. Rust reads nothing and does not know which pane the screen shows. `events` reaches the app about 500 ms before `status --follow`, and an event also shows a status that went and came back between two snapshots, after which the message is a new one.
  - Rejected: Rust reading the message itself on each event and sending it in the event. The forwarder would have to know which pane the screen shows, a state that changes with each tap and races with the reads in flight. Rejected too: the UI reading again when `row.status` changes in `agents-changed`, which comes with the snapshot and misses a status that went and came back.
- **One read at a time, one more at most**: an event during a read asks for one more, however many come, and it starts when the first ends. The reads are numbered, so a late answer never replaces a newer one, and leaving the screen discards the one in flight.

## Answering

- **The field** is a `TextArea` (Look › Forms) that grows with its text up to a maximum and then scrolls. Return adds a line and only `Send` sends: on a phone's keyboard Return is the only way to break a line, and a message sent by mistake cannot be taken back. `Send` rests while the text is blank, while it sends and while the agent is `waiting`.
- **Through the queue**: `send --pane P --enter --timeout 30 -` by `Queue::ask`, with the text as `Stdin::Text`, so it keeps its order with the keys (Keys). On standard input, a text that starts with `-` is not read as an option, and the text never shows in the argv the bridge logs. No message nor log holds it.
- **What comes back**: `Send` empties the field and takes the chips at once, and the thread shows what went as your bubble, `Sending…` (The thread). cornercase's answer turns it `Sent`, or `Not sent:` with the reason, since it answers something the user did: cornercase's refusal without its `Error:` (`waiting`, a dialog, a poll, `resuming`, `not confirmed`, a held send that ran out of time), `nothing was sent` for a job the queue skipped, `it may have been sent, but no answer came back` for one that lost its answer, and `no machine is connected` without a queue. cornercase's texts are written for scripts (`answer with cornercase keys`, `or with --force`) and are shown as they are: rewriting them would guess at upstream's words.
  - **Said by the bubble, not a toast**: the reason stays beside the text it is about, while a toast of 8 s would leave with it and leave the text nowhere. The keys keep their toasts (Keys), and so does attaching an image.
  - **`Retry` and `Edit`**: `Retry` sends the same text again with `Send`'s rules, forced while chips remain, and rests when `Send` would (another send on its way, an image being attached, `waiting`). `Edit` puts the text back in the field, before what was typed since and apart from it by a blank line, and takes the bubble away. A failed send gives back the chips it took, before those attached meanwhile, since their paths are still in the agent's input.
  - **One send at a time**: `Send` is busy while a bubble is `Sending…`, and the field still takes text.
- **Your send shows at once**: 016 showed nothing until `agents-changed` turned the header `working` and the message was read again with its event, and the field just emptied. On the user's iPhone, on 2026-11-09, that read as no feedback at all: nobody could tell whether the message had gone, nor whether the agent was thinking or stuck. So the text shows as soon as it is tapped, `Sending…` until cornercase answers. It is what the user sent, not a guess at the agent's state, which still comes only from `agents-changed` and the reads.
- **`--timeout 30`**: upstream holds a send while someone types on the Mac (its `held-sends.md`). With 30 s, a held send ends in `nothing was sent` rather than waiting for ever. Meanwhile the queue is busy, so a key tapped behind it waits up to 30 s (Keys). Accepted. Rejected: 15 s, the least over the 3 s of the Enter and the 10 s of the confirmation, which leaves a held send almost no time; no timeout, which would let a held send stop the queue for good.
- **A false `not confirmed`**: a Codex that works keeps a prompt sent meanwhile in memory and records it after its next tool call, so upstream extends its 10 s confirmation up to `--timeout` (its `confirming-sends.md`). A tool call longer than 30 s then fails with `not confirmed` though Codex takes the prompt later. Accepted. The bubble says `Not sent` with that reason, which says it may not have been submitted, so the user can look before `Retry` sends it twice. Any `not confirmed` may have reached the agent for the same reason.
- **`waiting` takes no text**: upstream refuses `send` to an agent that asks a question, a permission or a choice, which is answered with a key (Keys) or an option (The question). There, `Send` rests under the agent's question, or, until its rows come, under the note `<agent> is asking you something on its screen; answer with the keys.`, and the text typed stays, as gpui's `unready` does. Rejected: sending anyway and showing the refusal, a round trip for nothing.

## The thread

- **What it holds** (`src/routes/agent/Thread.svelte`, the order from `threadOf` in `src/lib/thread.ts`): one message of the agent at most and your last send, then the live line. Before the answer, the message you answered, your bubble and the line; once the answer comes, your bubble, the answer and the line. The answer is a read whose `text` or `written` differs from the message shown when you sent (`isAnswer`): the phone's and the Mac's clocks are never compared. The message you answered is no longer shown then, since upstream gives only the last one (Upstream gaps), and a new send replaces the bubble.
  - Sending while the agent was writing, its message grows after your send and is taken for the answer. Accepted: it is text written after you sent. An agent that runs tools first leaves your bubble under its old message until it writes.
- **Your bubble** (`src/routes/agent/Sent.svelte`) holds the text and the names of the chips that went with it; an image alone shows only its chips. Under it, its state: `Sending…` with the spinner, `Sent` with `check`, or `Not sent: <reason>` with `circle-alert` and `Retry` and `Edit` (Answering › What comes back). Its name for VoiceOver is `Your message, <state>`. How it looks is in Look › Components.
- **The live line** (`src/routes/agent/AgentLine.svelte`, `agentLine`) ends the thread and comes from `chat.row.status` (`agents-changed`), with no reads of its own:
  - `working`: the orbiting `StatusDot`, `<agent> is working…` and the time since `row.since` in the board's format (Board › Since when);
  - `shell`: the same, with `<agent> is waiting for a background command…`;
  - `waiting`: `<agent> is waiting for your answer`, and the composer keeps its note;
  - `failed`: `<agent> stopped with an error`, in the failure's tone;
  - `done`, `pending`, idle or a status it does not know: no line.

  Without `since`, which is the usual case on a phone after the background or a reconnection, the line has no time.
- **No news**: after `STALL_MS` (120 s) in `working` without news, the line turns `<agent> is working… · no news for N min · Ctrl-C interrupts`, in `--muted`. News is a status change, a read with another text or a confirmed send, timed on the phone's clock from the last one this `Chat` saw, or from when it opened (`Chat.lastNews`), never from `since`, which is often unknown. No alarm colour, haptic nor toast: a long turn is normal, and the next news brings the line back. The clock is the `Chat`'s injected `Clock`, so vitest moves it. It can be told only because the message is read while the agent works (Reading the message › When it is read again): without those reads every long turn would say it after 2 min.
- **One live region**: a single `aria-live="polite"` node in the line holds the send's state (`Sending`, `Sent`, `Not sent: <reason>`, hidden from the eye, since the bubble shows it) and the agent's phrase. The time runs outside it, and with no news so do its minutes and `Ctrl-C interrupts`, so VoiceOver says each change of phrase and not each tick. It stays in the page while the line has nothing to show, so `Sent` is still said to an agent that is done. Rejected: a region for the bubble and one for the line, which could speak at once.
- **A message that grows** is replaced in place: a read never goes back to `Reading its last message…`, so the text grows rather than flashing and the height does not jump. Before each read or bubble that changes the thread, once a message shows, the screen checks whether the page is at its end, within 48 px (`atEnd`); if it was, it scrolls to the end once drawn, and otherwise it stays where it is, so reading higher up is never taken away. A message with `turn_over === false` ends with `More to come…` in `--faint`.

## Keys

- **The row** (`src/routes/agent/KeyRow.svelte`) sits in the composer over the field, wherever the field is: while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent. It holds `Esc`, `Tab`, `↑`, `↓`, `←`, `→`, `Enter`, `Ctrl-C` and `0–9`, which unfolds the digits. Each button is a name of cornercase's `KEY_NAMES` (`src/lib/keys.ts`, its label, its name for VoiceOver and its key): the keys an agent's menus, permissions and confirmations take, the arrows and `Enter` to move and choose, a digit to choose an option by its number, `Esc` to cancel, `Ctrl-C` to interrupt. `src/lib/keys.ts` holds no markup nor state, so the terminal's row (021) can take its names too.
- **`0` too**, though the task asked for `1`–`9`: upstream closes Claude Code's survey with `keys --pane N 0` (its `confirming-sends.md`), and `send` refuses a pane with the survey open, so without it the phone could not take it away. The digits go `1` to `9`, then `0`, as on a keyboard.
- **Every key in sight**: buttons of 44 px (Look › Touch and motion), with no more width than their label and the arrows drawn as Lucide icons named `Up`, `Down`, `Left` and `Right`; on a phone 393 px wide the row breaks into a second line rather than scrolling sideways. The digits unfold in a row of their own over the keys, behind a button with `aria-expanded`, and stay open after a digit is sent until that button is tapped again, so `↑` or another number can follow without opening them again. They start folded; the `initialDigits` prop, which only the tests pass, draws them open, since a server render cannot tap. Rejected: one row that scrolls sideways, which hides keys out of sight; the arrows on a fixed line of their own; digits that fold on their own after one is sent.
- **`keys`, not `input`**: each tap queues `keys --pane P <key>` by `Queue::ask`, without standard input (`crates/core/src/cli/keys.rs`, the `keys` command of `src-tauri/src/commands/chat.rs`), on the `requests --follow` the sends go through, so keys and sends reach the agent in the order they were tapped. `keys` is upstream's way to answer an agent (`send` refuses `waiting` with `answer with cornercase keys`), its `enter` counts as submitting a turn, and it answers each key, so a key that fails gets a toast with a send's reasons (Answering › What comes back), since a key has no bubble, and success shows nothing: the status comes with `agents-changed` and the message with the next read, as after a send. `input` (the typist, Connection › the ordered queue) is someone typing in another window, the terminal's (021), and answers nothing a toast could say. The UI does not wait for a key's answer before sending the next one: `↓ ↓ Enter` keep their order in the queue, which is the order their commands reach `Queue::ask`. Each `invoke` runs as a task of its own on Tauri's multi-threaded runtime, so two within the same instant could swap; taps are tens of ms apart, and a send (Answering) has the same bound. Rejected: chaining the calls in the UI, each `invoke` waiting for the previous one to be queued, which needs a second command (one that queues, one that waits for the answer) for a race no finger makes.
- **Only the app's keys reach the argv**: the core takes only the 18 names the app sends and refuses any other (empty, `-x`, `shift+tab`) before anything is queued, so a key can never turn into an option of `keys`.
- **`Ctrl-C` asks for a second tap**: the first one sends nothing; it turns the button to the danger tone with `Again?`, its name for VoiceOver turns `Tap again to interrupt`, and a live region says it. A second tap within 3 s sends `ctrl+c` once; after 3 s, or on any other key, it lets go without sending. Two `ctrl+c` in a row quit Claude Code and leave its shell, and the screen turns gone, so one tap must never send it by mistake; a third tap arms it again rather than sending a second one. Rejected: a long press, which WebKit on iOS takes for itself without a click (Look › Touch and motion) and VoiceOver hardly does; a confirmation dialog, one more screen for a key.
  - **Same width, said aloud**: the live region is a `.spoken` span beside the rows, not inside the button: the children of a `button` are presentational and its `aria-label` hides them, so VoiceOver could miss a change there. The button keeps its width when armed: `Ctrl-C` and `Again?` share one grid cell (`.steady`) and only the one in use shows, so the row does not wrap again between the two taps and the second one lands where the first did. Rejected: `Tap again to interrupt` as the visible text, about 120 px wider, which could push `Ctrl-C` to the next line under the finger; a fixed `min-width`, a number to keep in step with the font.
- **`Esc` asks for nothing**: in Claude Code it interrupts an agent that works, as `Ctrl-C` does, but never quits it, and two in a row open its rewind. Accepted: it is the key a menu takes to cancel, and a confirmation would slow every menu down.
- **A light tap**: each tap that sends a key, and the one that arms `Ctrl-C`, asks the haptics plugin for `impactFeedback('light')` (`src/lib/haptics.ts`, Architecture › Dependencies), since what a key does often shows only on the Mac. Without the plugin (the desktop, the tests) or when it fails, nothing shows and the key still goes: it is not a failure of what the user did, so there is no toast.
- **Behind a held send** a key waits, as every job behind it does, up to the 30 s of `--timeout 30` (Answering).
- **Nothing to another pane**: a `Chat` gone, or of another machine, sends no key (The screen), and its screen shows no row. `keys` has no `--boot` either (Upstream gaps).

## The question

- **What it shows** (`src/routes/agent/Question.svelte`): while the agent is `waiting`, the composer holds, over the row of keys, the rows of its screen that make the question (a menu of `AskUserQuestion`, a tool's permission, an approval), with a button per numbered option between them and the keys. Until the first rows come, and whenever there are none, the note of `waiting` shows instead (Answering). The row of keys stays as it was, under the options: `↑`, `↓` and `Enter` move and choose in the menu, and the block shows the selection move.
- **Read from the screen, as upstream's Telegram does**: cornercase says that an agent waits (`status`, with `dialog: true` while a dialog shows) but not what it asks, and reading the agent's records is not the contract (Upstream gaps). Upstream's own Telegram bot answers the same question from the screen: the last 15 rows of the pane and a button per numbered option (`src/app/messenger/notices.rs`, which calls `messenger::choices` in `src/messenger/mod.rs`, #248). The chat does the same through the public `surface`, so it is no workaround, and the gap is named so that data can replace it.
- **A passive `surface` of its own** (`crates/core/src/terminal/asking.rs`, `Asking`): `surface --tab T --cols 80 --rows 24 --patches`, with no `view`, as the terminal's (Terminal › Passive by default), so the Mac's PTY keeps its size and `status` shows no `controller` for the phone. `--cols` and `--rows` are required but change nothing without a `view`: two captures of the same moment at 80×24 and at 40×60 had the same lines, with the pane at the PTY's size and all its rows, so the size is a constant and `question_open` takes only the tab and the pane. It runs over the terminal's `Live` and the core's reopening loop (`follow::reopen`, Changes and files › Following the list), with only the pane asked for: when it is not in the frame (closed, moved to another tab), the question is empty (`rows: []`), so the note comes back, never another pane's screen, which the WebView would drop while it kept showing the old question (review of 2026-11-10). Rejected: the terminal's choice (`Shown`, Terminal › One pane on the phone), which falls back to the active pane or the first. Rejected: cropping the rows the terminal's `Update` carries, which holds only the rows that changed, so the pane would be rebuilt again outside the grid; a `view` with the phone's size, which resizes the Mac.
- **Its cost**: a second process on the Mac and the tab's patches over the transport, only while the chat of a `waiting` agent shows; the crop runs on each change and the WebView hears only a question that differs from the last one, at most one `question-changed` per frame of 16 ms (`commands/chat/question.rs`, through the terminal's `by_frame`). As with the terminal, a passive `surface` never counts as seen, so the Mac's notice goes on.
- **The crop** (`crates/core/src/terminal/question.rs`, `cropped`, pure and tested on Linux): drop the empty rows at the end; from the last row with text, take at most `QUESTION_ROWS` (24) rows up; within them, start at the highest rule, a row of only `─━═╌╭╮╰╯┌┐└┘` and spaces as wide as half the pane at least; drop the empty rows at the start. Why: Claude Code 2.1.321 draws on the alternate screen with its content at the top and about half the rows empty under a menu; its menus start under a `─` rule as wide as the pane, and hold rules of their own (before `Chat about this`, `╌` around a permission's command), so the highest one in the window is the right start in every capture. The fixtures (`crates/core/tests/fixtures/control/surface/v1/question/`) are real lines of `surface` with Claude Code 2.1.321 and cornercase 0.13.19: one question, two questions in tabs, a Bash permission (16 rows each) and an agent at work (5 rows, its input box, no options); a folder's path was replaced by `/Users/dev/web-shop`. The trust question of a new folder is `idle` without a dialog and opens nothing.
- **Its limit**: the crop never shows history above its window, so a question taller than 24 rows loses its top, which the terminal still shows; and it is a heuristic over how each agent draws, so a new layout can show too much or too little until a capture adjusts it. The crop does not know whether the screen holds a question: it follows `waiting`, which comes after the menu is drawn and goes after it is gone, so for about a second after an answer the block may show the agent's input box instead (Checked live). Rejected: the last 15 rows as upstream's Telegram takes, which cut the menus of the captures (16 rows) or bring the conversation above a short one.
- **The options** (`options`, as `messenger::choices`): from the cropped rows, bottom up, a row that starts with `1.` to `9.` and a label, once the spaces and the marks `│┃|❯›>▶●○◯` are trimmed, is an option, up to the `1.` and without repeating a number; the rows that continue a long option are not options, so the button of an option that wraps holds its first row only (a permission's `Yes, and always allow access to`, its folder on the next rows). With fewer than two there are no buttons, so a lone numbered line of a message makes none. `Type something.` and `Chat about this` stay, as upstream keeps them.
- **The buttons**: one per option, 44 px high (Look › Touch and motion) and as wide as the composer, `N. label` cut with an ellipsis, named `Option N, label` for VoiceOver. A tap sends `keys --pane P N` through `Queue::ask` as the row's digits do (`Chat.pressOption`, Keys), with the same light tap and the same toast when it fails; a number that is not one digit sends nothing.
- **Drawn as the terminal draws it**: the rows go through the terminal's `Row.svelte` and `style.ts` (`runCss`, the pane's colours), in `--font-mono` at the terminal's 13 px, each row on its line without wrapping, as wide as the longest one with the cell measured as the terminal measures it (a hidden run of 100 `M`, iOS's monospace being wider than the 0.6 em that stands in until it is measured). The block is at most 40 % of the screen's height, scrolls both ways within itself (the page never scrolls sideways) and keeps its end in sight (`anchor` in `touch.ts`, as the terminal over the keys: Terminal › Typing), where the options and the selection are. Rejected: wrapping the rows to the phone's width, which breaks the menus' rules and columns.
- **The composer never covers the bar or the title** (`Agent.svelte`, `.composer`): it is at most the screen's height minus the safe area, the connection bar (`--below`) and `--over-composer` (132 px: the chat's bar, 60 px, the header with the agent's name and state, about 44, and the gaps between them), and scrolls within itself past that. The block is the one part that gives way (`flex: 0 1 auto`), down to three rows, so the options, the keys and the field keep their size and the block scrolls instead. Why: with five buttons, two rows of keys and the field, the composer was taller than the space under the bar on a 390 × 844 phone, and as `position: sticky; bottom: 0` it grew upwards, under the bar, where nothing could scroll it back: a question in tabs lost its row `← ☐ Colour ☐ Size ✔ Submit →` and the header its title (review of 2026-11-10). A constant rather than a measure, since the bar and the header have fixed heights; a bigger text size would need it measured. While the question shows, the thread is under the composer; it comes back when the question goes. Rejected: two columns of buttons, which cut labels of any length at half the width; a row of buttons that scrolls sideways, which hides options.
- **Opened and closed with the screen** (`Chat.watchQuestion`, `src/lib/question.svelte.ts`): `Agent.svelte` watches the question while it is mounted and the page shows (`whileShown`), and the `Chat` opens it while its row is `waiting`, so another status, the agent gone, `Back`, another machine, the background and the terminal, the changes or Machines over the chat close it, and `waiting` again opens it again. It listens to `question-changed` before it opens, so it misses no event, and opens and closes one after the other, in the order asked; an event of another machine, tab or pane, or of an opening already closed, is dropped.
- **A slot of its own**: `question_open(tab, pane)` and `question_close(tab, pane)` keep the task in `Active`'s third slot (Architecture › Commands and events), so closing the question never stops the terminal of the same tab, nor the other way round. The slot is keyed by the tab and the pane: two agents in splits of one tab have a chat each, each with its own queue of opens and closes, so going from one to the other may open the new one before the old one closes; with the tab alone, that late close would end the new question (review of 2026-11-10).
- **No toast**: a `surface` that fails, a line that is not a surface or a lost transport empty the question (`question-changed` without rows), which brings the note back, and a tab that closed sends `closed`; neither is ever a toast. A line that is not a surface also forgets the last question sent, so the next frame sends it again even when the screen did not change, and a menu that stays still comes back (review of 2026-11-10). The question only adds to the keys, which still answer and tell their own failures, and the terminal tells the same failure when it is opened.

## Attaching an image

- **The button**: `Attach image`, a compact plain button of 44 px with Lucide's `image-plus` and that name for VoiceOver, sits between the field and `Send` (`src/routes/agent/Agent.svelte`). It shows where the keys do: while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent, since upstream's `paste-file` has none of `send`'s safeguards (a waiting agent, a dialog, the survey) and pastes into whatever is there, as a person dropping a file on the Mac would. Rejected: hiding it while the agent is `waiting`. While the picker is open and the image goes, it is busy, with the spinner in place of its icon, and takes no second tap. Its state lives in `src/lib/attach.svelte.ts` (`Attachments`, one per `Chat`), with its command injected like the others.
- **The picker**: iOS's `PHPickerViewController`, images only, one at a time, from a plugin of our own (`src-tauri/plugins/photos`; Architecture › Plugins of our own, which also says why not `tauri-plugin-dialog`). It runs out of the app's process and needs no access to the photo library, so there is no permission to ask nor `NSPhotoLibraryUsageDescription`. Cancelling it (its `Cancel`, or a swipe down) does nothing: no toast and no chip.
- **Shrunk on the phone, by the system**: ImageIO makes a thumbnail (`CGImageSourceCreateThumbnailAtIndex`) whose longest side is at most 2,048 px, with its proportions; a smaller image keeps its size. The EXIF orientation is applied, and the image is encoded again from its pixels, so no metadata (the GPS position included) goes to the Mac. PNG when the source is PNG (screenshots, transparency), JPEG at quality 0.85 otherwise, HEIC included. ImageIO reads only what the thumbnail needs, not a 48 MP photo whole. The name that goes is the picker's suggested name with the extension of what was written (`IMG_0042.HEIC` becomes `IMG_0042.jpg`), or `pasted.png` or `pasted.jpg` without one (`crates/core/src/cli/paste_file.rs`). Only an image's extension is replaced (`png`, `jpg`, `jpeg`, `heic`, `heif`, `gif`, `webp`, `tif`, `tiff`, in any case): the picker often suggests a name without one, and a name with dots is kept whole (`Screenshot 2026-11-09 at 10.42.13` becomes `Screenshot 2026-11-09 at 10.42.13.png`, not `… at 10.42.png`).
- **The bytes never reach the WebView**: Swift writes the image to the app's temporary folder and answers Rust with its path, name and kind. The `attach(pane)` command (`src-tauri/src/commands/chat/attach.rs`) reads the file and removes it at once, also when it cannot be read. It refuses an empty image, and one over 32 MiB (upstream's `MAX_IMAGE_BYTES`, its own cap), before anything is queued. The WebView gets only `paste-file`'s answer, or `null` for a cancel.
- **Through the queue**: `paste-file --pane P --name=<name> --json -` by `Queue::ask`, with the image as `Stdin::Bytes`, so it reaches the agent after the keys and sends tapped before it, as a command of its own (Connection › the ordered queue, Upstream gaps). `--name=` is glued to its value, so a name that starts with `-` is not read as an option. The answer `{pane, path, bytes}` is read leniently (`Pasted`: defaults, unknown keys ignored), and its fixture is cornercase 0.13.19's output. On the Mac, upstream keeps the file in a folder of its own and types `<path> ` into the agent's input, without Enter; it removes the file with its pane or after 7 days, so the app removes nothing there.
- **The chip**: each image pasted shows over the field as a chip with its file's name and its size in binary units (`1.5 MiB`, as the 32 MiB cap). The name is the one in upstream's `path`, cleaned to ASCII, which is what the agent sees; a long one is cut with an ellipsis and the size always shows. A chip is text: there is no preview (Left out). The chips go with the next send that succeeds and with the row's next `Enter` that succeeds (those that were there when it started), and when the agent is gone: after them the path is no longer in the agent's input, so `Send` goes plain again and no chip stands for nothing. Other keys leave the chips, `Esc` included: what a key does to the input depends on the agent (Claude Code empties it only on a second `Esc`), and the chat cannot see the input, so a chip that outlives its path costs one forced send at most. They stay under the terminal and under Machines, as the `Chat` does, while the path stays in the agent's input. Leaving the screen drops the `Chat` and its chips but not the path in the agent's input: back on the screen, `Send` goes plain and upstream holds it until the paste lapses, 60 s without input, so it ends in `nothing was sent` with no chip to say why (Upstream gaps); `Enter` on the row submits the path alone. Rejected for now: keeping the chips by machine and pane outside the `Chat`, which would also have to follow the agent's input across screens it cannot see. While an image is being attached, `Send` and the row's `Enter` rest (`Chat.canSend`, `Chat.canPressKey`) and send nothing: its `paste-file` is already in the queue, so they would submit its path too, while its chip, which comes after they counted, would stay for a path no longer in the input. The other keys still go, as they leave the chips. An image attached while a send is on its way keeps its chip: its `paste-file` is queued after the send, so its path reaches the input after that turn. Rejected: waiting for the attaching to end before counting the chips, which turns the tap into one that acts seconds later, after an upload of up to 32 MiB, with nothing on the button to say it is pending.
- **`Send` forced while a chip is there**: upstream types the path through what a person's paste goes through, so the pane counts as drafting and a plain `send` is held until that draft lapses, 60 s without input, while the chat's `--timeout 30` ends first in `nothing was sent` (Upstream gaps). So while a chip is there, `Send` sends `send --pane P --force --enter --timeout 30 -`: the text joins the path in the agent's input and both go in one turn. With the field empty, `Send` is enabled too and sends `keys --pane P enter`, which submits the image alone. After a send or the row's `Enter` that succeeds, `Send` is plain again. `--force` skips upstream's holds and its refusal over a dialog or a poll, but still waits for another send's Enter. The chat keeps its own `waiting` rule, since `Send` rests while the agent asks. A bounded exception to Left out: the draft it passes is the one the phone just pasted. Rejected: `Send` as it was, with the chip asking to tap `Enter`, which sends the image and the question as two turns; typing the text with `input` and then `keys enter`, which confirms no turn, so a text that did not go would show no toast.
- **What fails is a toast and leaves no chip**: the picker's own refusals (no screen to show it on, already open, a photo that cannot be loaded, read, decoded or written, and off iOS `only the iOS app has a photo picker`), an empty image, one over 32 MiB, and what a send's failures say (Answering › What comes back): cornercase's refusals without their `Error:` (`busy`, `not-found`, `malformed`), the refusal of a CLI on the Mac older than its server that lacks `paste-file`, `nothing was sent`, `it may have been sent, but no answer came back` and `no machine is connected`. A server without `paste-file` cannot connect at all, since `REQUIRED` names it (Connection › The contract).

## Markdown

- **A tree, never HTML**: `src/lib/markdown.ts` parses the text with `mdast-util-from-markdown` and GFM (Architecture › Dependencies) and keeps a closed tree of its own: paragraphs, headings, emphasis, strong, strikethrough, inline code, code blocks, lists (with their checkboxes), quotes, GFM tables, breaks and rules. `Markdown.svelte` and `MarkdownNode.svelte` draw it with Svelte's own elements, so nothing goes through `{@html}`, which `svelte/no-at-html-tags` refuses and no comment may silence.
- **Headings one level down**: `#` is an `h2`, `##` an `h3`, and so on up to `h6`, since the agent's title is the `h1` of its screen (Look › Components) and VoiceOver walks a screen by its headings. They all look the same (`.heading`), so only the outline changes.
- **What is not drawn as itself**: raw HTML stays as its text, a link as its words, an image as its `alt`, and a node the tree does not know as its text. An `<a>` in the WebView would take the user out of the app; the CSP already blocks images from elsewhere, but no `<img>` is drawn either. Links that open are left out.
- **Code blocks and tables scroll sideways** inside their own container, the code in `--font-mono`, so the screen itself never does. The text is parsed in the WebView at each read and not virtualised: a message of tens of KB is accepted as it is.

## Gone

- **The agent is gone** when a list of rows lacks its pane (the pane was closed, or the agent quit and left its shell), or when the rows turn `null` after the screen had seen its row (a restart, a new `Store`), or when the active machine is not the one it was opened on (The screen). Then it says `This agent is no longer running.` under the bar and its back button, the field goes, and the text typed and your bubble are lost.
- **For good**: a later list with the same pane does not bring it back. After a restart the server may give that id to another agent, and the screen must neither show that agent's text nor send it what was typed for the first one (Upstream gaps › `--boot`).
- **Before the first list** (`null` without having seen the row: connecting, a new `Store`) the screen does not know yet and shows the board's mark (Board › A row).
- **An agent the app just started** has no row yet: `Chat.see` takes `starting` from its route, and until the row comes a list without the pane does not count it as gone, while the screen says `Starting <agent>…` (Starting work › After it starts). Once the row was seen, or on another machine, the rules above hold.

## Left out

- The history: the agent's older messages and your sends before the last one (Upstream gaps). Links that open, images inside a message.
- `--force` (sending over a dialog or a poll), except while an image waits (Attaching an image), and `held --send-now` / `--wait-turn`.
- Chips that outlive the screen: an image attached and left unsent is forgotten with the `Chat`, while its path stays in the agent's input (Attaching an image › The chip).

- Keys other than the row's: other combinations (`shift+tab`, `ctrl+o`, `ctrl+r`), function keys, `Backspace` and `Space`, a `Ctrl` that sticks and the keyboard over the terminal, which belong to typing in a terminal (021). Marking a key as sent before its answer.
