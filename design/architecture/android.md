# Android

A topic of [Architecture](../architecture.md). The same app on Android (030): the Gradle project `tauri android init` writes, what was changed in it by hand and why (the keyboard's insets, 032, included), how the Keystore keeps the secrets (031), where the emulator finds Vite and the Mac, and what was checked live. What the secrets are, and how the route tokens left the file 030 kept them in, is in `design/connection/identity.md`.

## The project

- **`src-tauri/gen/android` as `android init` wrote it** (Tauri CLI 2.12.4), in git like `gen/apple` (Native projects in git): the Gradle project, `MainActivity.kt`, the resources and the launcher icons. The icons are not the template's: `pnpm tauri icon src-tauri/icons/icon.json` writes them from the mark (`design/look/launch.md` › App icon), the classic `mipmap-*` PNGs, the adaptive `mipmap-anydpi-v26/ic_launcher.xml` and its background colour, `values/ic_launcher_background.xml`, and the template's `res/drawable/ic_launcher_background.xml` (a green grid) and `res/drawable-v24/ic_launcher_foreground.xml` (the robot) were removed, since nothing referenced them. A later `android init` writes the template's icons and drawables again: run `pnpm tauri icon src-tauri/icons/icon.json` after it and delete the two drawables, and the launch's resources must be kept (The launch, below): `values/colors.xml`, `values/themes.xml`, the new `values-v31/themes.xml` and `drawable/launch_mark.xml`, with `values-night/themes.xml` deleted. Besides the icons and those, only four files are changed by hand: `app/src/main/AndroidManifest.xml` (permissions, `networkSecurityConfig`, `allowBackup`, `dataExtractionRules`), the two new `res/xml/network_security_config.xml` and `res/xml/data_extraction_rules.xml`, and `MainActivity.kt`, which lifts the WebView above the keyboard (032): with `enableEdgeToEdge()` and `targetSdk` 37 the window no longer shrinks for the keyboard and neither wry nor Tauri apply the keyboard's insets, so `interactive-widget=resizes-content` had nothing to resize and the keyboard covered the page. A listener of the window's insets on `android.R.id.content` pads its bottom by the keyboard's height and hands its children the insets without it, so the WebView shrinks to what is left and its bottom safe area is 0 while the keyboard is up, since the keyboard already covers the navigation bar (Terminal › Typing). The activity also declares `android:windowSoftInputMode="adjustResize"`, for API 24 to 29 (the app's `minSdk` is 24): there `WindowInsetsCompat` reports the keyboard's insets only to a window that asks for `adjustResize`, and without them the keyboard would cover the page again; from API 30 the insets come all the same, and from Android 15 edge-to-edge ignores the flag, so on API 37 it changes nothing (checked on 2026-11-10 in the emulator of Checked live, with the flag in the merged manifest: with GBoard open over a field of the Add machine form the WebView is 1,517 px tall of 2,400, and 2,400 again after back, so the page shrinks once and is not padded twice). Unchecked on an API 24–29 device or AVD. Rejected: `adjustResize` alone, without the listener, which edge-to-edge ignores from Android 15; working the height out in JavaScript (`env(keyboard-inset-height)`, the VirtualKeyboard API). A later `android init` would write the template's `MainActivity.kt` again, so this one has to be kept. `init` changed nothing outside `gen/android`.
- **What stays out of git**: what the two `.gitignore` files `init` writes leave out, which is what Gradle, the Tauri CLI and the Rust build write and what belongs to one Mac (`build`, `.gradle`, `local.properties`, `.idea` caches, `.cxx`, `key.properties`, `.tauri`, `tauri.settings.gradle`; in `app/`, `src/main/**/generated`, `src/main/jniLibs/**/*.so`, `src/main/assets/tauri.conf.json`, `tauri.build.gradle.kts`, `proguard-tauri.pro` and `tauri.properties`), plus the root's `/src-tauri/gen/**/build/`. After `pnpm tauri android dev`, `git status` is clean (checked on 2026-11-10).
- **`dev.usecornercase.mobile`** is the `applicationId` and the `namespace`, from `identifier` in `tauri.conf.json`; a debug build is `dev.usecornercase.mobile.debug` (`bundle.android.debugApplicationIdSuffix`), so a debug build and a release one can live on the same phone.
- **`minSdk` 24** (Android 7.0), pinned in `tauri.conf.json` › `bundle.android.minSdkVersion`, so a later `init` keeps it. It is Tauri's default and the floor of the plugins the app uses (barcode-scanner 2.5.3 and haptics 2.4.2 ask for 24); it covers almost every phone in use, the WebView is updated through the Play Store rather than with the system, and nothing 031 or 032 needs asks for more: `AndroidKeyStore` has AES-GCM since API 23. Rejected: 26 (fewer old phones to test, nothing the app uses) and 28 (cleartext off by default, which the network security config already says).
- **Permissions**: `INTERNET`, `CAMERA` (the QR scanner, which declares it too; twice does no harm) and `ACCESS_NETWORK_STATE` (032's `ConnectivityManager`). The scanner asks for the camera at run time, the first time it opens.
- **Targets**: `rust-toolchain.toml` lists only `aarch64-linux-android`, which runs on the arm64 emulator of an Apple Silicon Mac and on phones, so rustup brings it with the toolchain as it does the iOS ones, and CI downloads one target more, not four. `android init` also adds `armv7-linux-androideabi`, `i686-linux-android` and `x86_64-linux-android` to the local rustup, which only a release build for every ABI needs.

## The launch

What Android shows between the tap on the icon and the WebView's launch layer (055; the layer itself and why it waits are in `design/look/launch.md`).

- **A dark window on every API**: `values/colors.xml` › `ground` (`#FF0B0C0E`, the WebView's `--glass`) is the theme's `android:windowBackground`. The template's theme, `Theme.Material3.DayNight.NoActionBar` with nothing of its own, painted the window and Android 12's splash light while the phone was in light mode.
- **Android 12's splash**, in `values-v31/themes.xml`: `android:windowSplashScreenBackground` is `ground` and `android:windowSplashScreenAnimatedIcon` is `res/drawable/launch_mark.xml`, the mark as a vector of three rectangles on a canvas of 288 dp (the size of a splash icon without an icon background), drawn at `u = 8` dp and centred, so it is 96 dp wide like the layer's 96 CSS px, and the splash centres it in the whole window as the layer does. Its farthest corner is about 68 dp from the centre, inside the 96 dp circle the splash keeps. Rejected: `@mipmap/ic_launcher_foreground`, the adaptive icon's PNG, whose mark is sized for a canvas of 108 dp, so it would come out at another size than the layer's.
- **One theme, two definitions**: `values/themes.xml` holds `Base.Theme.cornercase_mobile` with the window's background, and `Theme.cornercase_mobile` inherits it twice, plainly in `values/` and with the splash in `values-v31/`. The template's `values-night/themes.xml`, the same theme again, was deleted: Android picks a resource's folder by its night qualifier before its API level, so a night definition would win over `values-v31` and the splash would lose its colour and mark in dark mode. `DayNight` already follows the system without it.
- **Below API 31** the window is dark and there is no mark until the WebView paints its layer: the splash of Android 12 has no backport without `androidx.core:core-splashscreen`, a new dependency that would also hold the splash with `setKeepOnScreenCondition`, which the layer already does.

## Cleartext

- **`network_security_config.xml`**: `base-config cleartextTrafficPermitted="false"`, and cleartext only to `localhost` and `127.0.0.1` (Vite, below) and to `ts.net` with its subdomains (Tailscale's MagicDNS names). The `ts.net` entry only matters to the WebView, which reaches nothing there today (below); it is kept so a MagicDNS dev host would load. Nothing allows cleartext everywhere, in debug or in release. Rejected: `cleartextTrafficPermitted="true"` in `base-config`, the quick way to make `android dev` work.
- **No IP ranges**: a `<domain>` is a host name, and an IP address matches only whole, so "the private ranges and Tailscale's" cannot be written in that file. Listing the machines' addresses one by one would break on the next DHCP lease.
- **The file does not govern `ws://`**: Android's `NetworkSecurityPolicy` is applied by the Java stacks and the WebView, not by native sockets, and the WebSocket to cornercase's `/cli` is opened by tokio-tungstenite in Rust (All networking in Rust). What it guards is the WebView, whose CSP already lets it reach nothing but the app and Tauri's IPC (A strict CSP).
- **The boundary is cornercase's `/cli`**: it listens only on the machine's private LAN and Tailscale addresses, never on a public one (upstream's `design/phone-app.md` › Where it listens), and the phone's secret travels only there. A guard in Rust that refuses `ws://` routes outside those ranges would make the phone hold the line too; it is a feature of its own, left for a task apart.
- **`usesCleartextTraffic` is kept as the template wrote it** (`${usesCleartextTraffic}`, `true` in debug): from API 24 a `networkSecurityConfig` makes Android ignore it, so the file above decides in both builds. `debug-overrides` cannot help: it only takes trust anchors, not cleartext.

## Backups

- **`android:allowBackup="false"`**: `machines.json` and the preferences that hold the sealed secrets live in the app's data folder, and must not leave the phone in a cloud backup or through `adb backup`. Since 031 no token is in plain text there (030's `route-secrets.json` is moved and removed on the first start, and with it the temporary copy a write cut short could have left beside it), and a sealed secret copied to another phone would not open without this one's Keystore key; the machines' names and addresses still would leave, so backups stay off. From Android 12, with the template's `targetSdk` 37, `allowBackup="false"` no longer stops a device-to-device transfer, so `data_extraction_rules.xml` excludes every domain from both `cloud-backup` and `device-transfer`. Below Android 12, `allowBackup` alone is enough, so there is no `fullBackupContent`.

## The Keystore

How the secrets plugin (`src-tauri/plugins/secrets/android/`, `design/architecture/plugins.md`) keeps a secret. Why a sealed seed and not a key in the Keystore: `design/connection/identity.md`.

- **One AES-256 key in `AndroidKeyStore`**, for encrypting and decrypting only, GCM without padding, made on the first `set` and found by its alias afterwards; a `get` never makes one. It cannot be exported: no call returns its bytes, and on a phone with a TEE they never leave it. The Keystore makes the 12-byte IV of every encryption (a key made this way refuses one from the caller), so an IV is never reused by mistake. GCM's tag also says whether a sealed secret was changed.
- **The secret's name as associated data**: the name goes into GCM as AAD, so a value moved to another name, by hand or by a bug, does not open (wrong key, rather than the other secret's bytes).
- **The app's own preferences** (`MODE_PRIVATE`), one entry per secret: its name, and a format byte (`1`), the IV and the ciphertext with its tag, in Base64 (Android's `android.util.Base64`). The format byte costs one byte now and lets a later key or algorithm (StrongBox, a rotation) tell the old entries apart; an entry with another byte, or too short to hold the IV and the tag, is damaged. The names, `identity/ed25519` and `route/<machine>/<address>`, are in clear, as they are in `machines.json`: they are the AAD and say nothing secret. **`commit()`, not `apply()`**: when `set` or `delete` answers, the change is on disk, as the adapters of the other platforms promise; `commit()` blocks for a few milliseconds, which the caller does anyway, since `run_mobile_plugin` waits.
- **No `setUnlockedDeviceRequired`**: the app reconnects while the screen is locked (a network change, the return of a stream), and with it the key could not be used then. The preferences live in the credential-encrypted storage, which Android opens at the first unlock after a boot, and the key lives in a Keystore that never moves to another phone: together that is iOS's `AfterFirstUnlockThisDeviceOnly` (Identity and secrets › The Keychain). The app does not run before the first unlock (it is not `directBootAware`).
- **No user authentication** (`setUserAuthenticationRequired`, biometrics): a fingerprint at every start or reconnection, for a seed and development tokens. **No StrongBox** (`setIsStrongBoxBacked`, API 28+): slower per operation, missing on many phones and in the emulator, where it could not be tested, and the TEE is enough for what the key protects.
- **A lost key** (some makers' phones drop Keystore keys when the screen lock is changed or removed) is an error, never a quiet new identity: a `get` of a secret whose key is gone fails, and so does a later `set` (a new machine): a key is made only while the preferences hold no sealed secret, so the error keeps saying the key is gone, rather than a new key under the same alias sealing the new secrets while the old ones fail with the wrong key. The remedy is clearing the app's data (`design/connection/identity.md` › A secret that no longer opens).
- **Threads**: `Secrets` is called from `setup` and from async commands on tokio's workers; each call goes to Kotlin, which keeps no state but the key it found, under `@Synchronized`, and two `commit()`s on the same preferences are serialized by Android.

## The release build

- **R8 keeps ML Kit's registrars** (`app/proguard-rules.pro`). The release build shrinks the code with R8, and the QR scanner reads codes with ML Kit, which finds its parts by reflection: a `ComponentRegistrar` named in the manifest, built through its empty constructor. R8 saw no caller of those constructors and removed them, so ML Kit started without its barcode client and every scan failed at once with "Attempt to invoke virtual method 'java.lang.Class java.lang.Object.getClass()' on a null object reference", while debug builds, which do not shrink, scanned. Two rules keep them: every `ComponentRegistrar`'s empty constructor, and the constructors of `com.google.mlkit`. Found by the first people to try a release APK on 2026-11-15, reproduced in the emulator with that APK (ML Kit's `ComponentDiscovery` warned "Could not instantiate …BarcodeRegistrar"), and checked there after the rules: no warning, and the scanner opens the camera. Rejected: turning off R8 for release, a larger APK for one library's reflection.
- **Try a release build before giving it to anyone**: `pnpm tauri android build --apk`, signed with `apksigner`, then open the scanner. The emulator is enough for this kind of fault: it shows at the first scan, before any code is read.
- **The APK people download** is built, aligned and signed by `.github/workflows/release.yml` on a `v*` tag, with the release keystore from the repository's secrets, and waits in a draft GitHub Release for that check (`design/releases.md`).

## Running it

- **Vite through `adb reverse`**: `pnpm tauri android dev` publishes port 1420 on the device with `adb reverse` and loads `http://localhost:1420/`, without `TAURI_DEV_HOST` (CLI 2.12.4), so `localhost` in the network security config is enough and hot reload works. The CLI leaves the `adb reverse` behind when it stops.
- **The emulator reaches the Mac** at its LAN address (through the emulator's outgoing NAT) or its Tailscale address, which are the ones cornercase's code holds. Not `10.0.2.2`, the Mac's loopback seen from the emulator: cornercase does not listen on loopback, and a `127.0.0.1` in a code is, in the emulator, the emulator itself. The code goes into the form by `adb shell input text` (cut into short pieces, below) or the emulator's clipboard, not scanned.

## Checked live

On 2026-11-10, in an arm64 emulator (Pixel 8 profile, image `android-37.0;google_apis;arm64-v8a`, Android 17, API 37), emulator 37.2.13, Tauri 2.12.5 and its CLI 2.12.4, NDK 29.0.14206865, JDK 17:

- `pnpm tauri android dev` builds, installs `dev.usecornercase.mobile.debug`, loads the UI from Vite, and a change to a `.svelte` file shows without a reload.
- The bridge's code, typed into the form, adds the machine; it connects through the Mac's Tailscale address and shows the live board.
- With 030, `machines.json` and `route-secrets.json` are in the app's data folder, readable only by its user (`-rw-------`), with one key per route. After `am force-stop` and a new start the machine is there and connects again without the code.
- With 030, Machines › This device shows "no secret store on this platform yet" in place of the fingerprint, and the machines load all the same.
- The scanner asks for the camera and opens; Cancel goes back. Its viewfinder stays black in the emulator: CameraX binds, but the emulated camera never opens (the AVD has no front camera, and CameraX's check of the lenses fails), so no code was scanned there.
- Not checked: a real phone, over USB or Wi-Fi and through Tailscale (the ticket's own check, left to the user), scanning a real code, and the release build.
- Seen and left for later: the status bar's dark text on the dark background. The WebView that stayed scrolled after the keyboard hid, until the next tap, was the keyboard covering the page; with the insets above (032) the page shrinks instead and is never scrolled (checked on 2026-11-10 in the same emulator, Terminal › Typing).

The Keystore (031), on 2026-11-10 in the same emulator and versions (system build CE2A.260420.051.A3), with debug APKs built by `pnpm tauri android build --debug --apk`, after which `git status` is clean:

- **The update from 030**: 030 installed, a machine added from the bridge's code, with three routes (the LAN, and Tailscale's IPv4 and IPv6) and so three tokens in `route-secrets.json`. Once 031 is installed over it, the first start logs `moved 3 route secrets into the store` and then the identity's fingerprint; the machine connects without the code, `route-secrets.json` is gone and `machines.json` stays.
- **The identity**: its fingerprint is in logcat and in Machines › This device. It is the same after `am force-stop` and a new start (with no second move), and after a cold boot (`adb reboot`), after which the machine connects again. After `adb uninstall` and a new install it is another one.
- **The preferences** (`run-as … cat shared_prefs/cornercase-secrets.xml`, `-rw-rw----`, which is what `MODE_PRIVATE` gives) hold only the identity and the three tokens, each Base64 that decodes to binary; the bridge's token appears neither in clear nor in hex. Only the names are readable.
- **The format and the refusals**: a fresh install seals the identity as 93 bytes, the format byte `1`, the IV, the 32-byte seed in hex and the tag, and finds the same fingerprint after a restart. With the preferences changed by hand (`run-as`), an entry of 20 bytes or one whose first byte is `2` says the secret is damaged, one whose last byte was changed says the key cannot open it, and an entry without the format byte (the first build of 031) is damaged. With a sealed route in the preferences before the first start, so no key yet, the identity's `set` says the key is gone and makes no key.
- **The temporary copy**: with `route-secrets.json` and `.route-secrets.json.tmp` written by hand, the start moves the one token and both files are gone; with only the temporary copy, it is gone after the start.
- **The cost**: reading a secret takes tens of milliseconds (the identity's line came 30 to 110 ms after its read began, after a reboot and after a force-stop; the first writes, which make the key, about 80 ms). Loading the machines reads one token per route, so a few routes add a fraction of a second at most to the start.
- Not checked: a real phone, the case the Keystore changes most between makers (StrongBox or not, a key lost when the screen lock changes), left to the user; a move that fails, which the core's tests cover; and the release build.

The launch (055), on 2026-11-13 in the same emulator (1,080 × 2,400 at 420 dpi), Tauri 2.12.5 and its CLI 2.12.4, with a debug APK built by `pnpm tauri android build --debug --apk --target aarch64`, a saved machine whose bridge was down, and each cold start (`am force-stop`, then `am start`) recorded with `adb shell screenrecord`:
