# Plugins of our own

A topic of [Architecture](../architecture.md). Native code goes into Tauri plugins of our own, each a crate of the workspace in `src-tauri/plugins/` with its Swift or Kotlin, while Rust keeps the logic: `network` on iOS and Android, `photos` on iOS, `secrets` on Android, `keyboard` on iOS.

- **Why a plugin**: a plugin is how Tauri 2 builds Swift and Kotlin into the app, with a stub on the other platforms so Linux CI compiles everything else; the logic stays in Rust, and the native code only reports or does what only the system can. None has a JavaScript API, commands or permissions: the WebView never sees them, except the keyboard's top that `keyboard` dispatches as an event. Their cost is native code that CI does not test.

## `network`

- **`src-tauri/plugins/network`** is the first, a crate with a Swift package in `ios/` that hears `NWPathMonitor` and, since 032, an Android library in `android/` whose Kotlin hears `ConnectivityManager`, each handing every network to a callback of the app (`design/connection/network.md`). The debounce is in the core; the plugin only reports.
- **One Rust for both phones**: the channel and the `watch` call are `mobile.rs`; `ios.rs` and `android.rs` only register the native class, so the two phones cannot drift.
- Rejected, and kept as plan C: noticing the change from Rust without native code, as upstream does in `src/host/network.rs`, asking every ~2 s for the source address the system would use toward each route, through a `UdpSocket::connect` that sends nothing. It polls (it wakes the phone every 2 s instead of hearing an event), knows neither the kind of network nor its cost, and with Tailscale up its `utun` interface keeps an address with no network underneath, so it never sees `none`.

## `photos`

- **`src-tauri/plugins/photos`** is the second: iOS's photo picker (`PHPickerViewController`) and the shrinking of the image chosen with ImageIO, in Swift, which hands Rust a file in the app's temporary folder, and, since 041, a second one, a thumbnail of at most 192 px for the chat's composer, as `thumbnailPath` (`Picked`'s optional `thumbnail_path`, so an answer without it still reads) (`design/chat/attaching.md`). It is registered on every platform, not under `#[cfg(mobile)]`: off iOS its stub answers that only the iOS app has a photo picker, so the `attach` command builds and is tested on Linux CI (Android has no picker yet: none of 030–032 brought one). Like `network`, it has no JavaScript API nor permissions, so neither the image's bytes nor its path ever reach the WebView.
- Rejected for the photos: Tauri's `tauri-plugin-dialog` (its image picker) with the `image` crate shrinking in Rust. Its picker copies the file as it is, and most photos of an iPhone's camera are HEIC, which `image` does not read and Claude does not take, so they would end in a refusal; it leaves the copy in Caches without removing it; the WebView calls it, so the path goes through JavaScript and needs a permission in `capabilities/`; and decoding a 48 MP photo whole in Rust takes about 190 MB of RGBA, where ImageIO's thumbnail reads only what the smaller image needs. ImageIO also applies the EXIF orientation and writes no metadata, with no new Rust dependency.

## `secrets`

- **`src-tauri/plugins/secrets`** is the third, and the first in Kotlin: an Android library module in `android/` with `get`, `set` and `delete`, which seals each secret with a non-exportable AES key of `AndroidKeyStore` and keeps it in the app's preferences (`design/architecture/android.md` › The Keystore). The plugin manages a `SecretStore`, a `Secrets` over those three commands (`src/bridge.rs`), which the app takes in `setup`; off Android its stub manages one that fails with "no secret store on this platform yet", so it is registered on every platform, like `photos`, and the app builds and is tested on Linux CI. Rust does the encoding and the errors, which CI tests; Kotlin only seals, opens and saves. The WebView never sees a secret. Why the identity is a sealed seed: `design/connection/identity.md`.
- **Called from `setup`**: `run_mobile_plugin` hands the command to Android's thread and blocks until Kotlin answers, and the app reads the identity and the routes' tokens that way in its own `setup`, after the plugin's. It works, and adds tens of milliseconds to the start (Android › Checked live); loading them later, after `RunEvent::Ready`, was the fallback and was not needed.
- Rejected for the secrets: AndroidX's `EncryptedSharedPreferences` (`security-crypto`), the ticket's plan B, which Google deprecated in 2025 in favour of the platform's APIs and the Keystore used directly, and a new AndroidX library for what a few dozen lines of `javax.crypto` do; `tauri-plugin-stronghold`, a file sealed with a password the app would have to keep somewhere, the same problem again, with no Keystore; JNI by hand from Rust (the `jni` crate on `ndk-context`'s `JavaVM` and `Context`), every Keystore and `Cipher` call written with string signatures that only fail at run time, and a new crate, where Tauri's plugin already gives a compiled Kotlin class with the app's `Context`.

## `keyboard`

- **`src-tauri/plugins/keyboard`** is the fourth, iOS only and with no commands, and does two things with the WKWebView Tauri hands it (`load(webview:)`) (`design/chat.md` › The screen):
  - It takes away the bar WKWebView shows over the keyboard for every field (‹ › and ✓), which the chat does not need. WebKit has no setting for it: its content view (`WKContentView`) answers `inputAccessoryView` with that bar, so the plugin gives that one view a subclass made at run time whose `inputAccessoryView` is `nil` (`object_setClass`), the way Capacitor's Keyboard plugin and Ionic do.
  - **Only in the chat** (review of 2026-11-15): on every `keyboardDidShow` it asks the page whether its keys follow the finger, `document.documentElement.dataset.keyboard === 'follows'` through `evaluateJavaScript`, which the chat (`Agent`) sets while it is mounted (`followKeys`, `src/lib/keyboardTop.svelte.ts`) and takes away when it leaves. With that answer it sets `keyboardDismissMode` on each `UIScrollView` under the webview, its own and those WebKit makes for the boxes that scroll, which appear and go as the page changes, hence each time rather than once: `.interactive` in the chat, `.none` elsewhere, since the same scroll views outlive a change of screen. It keeps the answer until `keyboardDidHide`, and only with it holds the thread (below) and, on `keyboardDidHide`, blurs the page's focused element with `evaluateJavaScript`, since a keyboard taken down by the finger leaves the field focused, and a tap on a focused field does not open the keys again. Why only the chat: the chat alone moves with the keys (`dropped`); the terminal, the board's search and the forms keep their column's height until the keys are gone, so a drag would leave a gap between them and the falling keys, and the terminal takes its focus back to its own field (`typist`). The `keyboardtop` events still go out everywhere, and only the chat listens to them. Rejected: the whole app, which would change the terminal and the forms, never tried on the phone, for what only the chat needs.
  - It tells the page where the keys begin while they move: a view of zero width from the webview's top to its `keyboardLayoutGuide`, which UIKit moves with the keys, the finger's drag included, dispatches a `keyboardtop` `CustomEvent` (its `detail` the top in points, CSS pixels) whenever its height changes, and `null` once the keys have shown (not once they have gone, so the last line holds until the page sees them gone). It is the one thing a plugin hands the page, through `evaluateJavaScript`, since WebKit does not move `visualViewport` during an interactive dismissal. Rejected: reading the drag in JavaScript and guessing the keys' place from the finger, which drifts from where UIKit puts them.
  - It holds the chat's thread still while the keys leave: from `keyboardDidShow` it knows where the keys rest, and while the guide is lower than that it pins the `contentOffset` of every scroll view being dragged (`isDragging`) through KVO, putting it back each time the pan moves it, until the keys come back up or go. Rejected: stopping the scroll from the page (`overflow: hidden` on the thread during the drag), which WebKit applies only after a round trip to the web process, so the thread would slip for a few frames each time, and which would end the pan.
- It is registered on every platform, like `photos`: off iOS it adds nothing, and Android has neither the bar nor the interactive dismissal.
- **Its risk**: the content view's class name is WebKit's own, not public, so a WebKit that renamed it would bring the bar back; the plugin then finds no content view and does nothing, rather than fail. The scroll views are UIKit's public type, whatever WebKit names their subclass. Rejected: CSS or JavaScript, which cannot reach the bar, since it is UIKit's, not the page's; and a swizzle of `inputAccessoryView` on every `WKContentView` of the process, which touches more than this app's webview.
