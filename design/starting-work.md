# Starting work

New work on the Mac from the phone: an agent with a prompt, in a workspace that is already open or in its own worktree (tasks 023 and 045), or an agent or a flow on an issue of any connected tracker (tasks 024, 045 and 047). Code: `crates/core/src/cli/agents.rs` (`account list --check --json`), `crates/core/src/cli/start.rs` (the argv and the ids that answer), `src-tauri/src/commands/start.rs`, `src/lib/startForm.svelte.ts` and `src/routes/start/`; for the issues, `crates/core/src/cli/issues.rs` (their argv and answers), `src-tauri/src/commands/issues.rs`, `src/lib/issueSweep.ts` (which trackers to list and how their lists join), `src/lib/issues.svelte.ts` and `src/routes/issues/`; for the flows, `crates/core/src/cli/flows.rs`, `src-tauri/src/commands/flows.rs`, `src/lib/flowStart.svelte.ts` and `src/routes/start/FlowPicker.svelte`. Upstream's `StartArgs` and `NewWorkspaceArgs` (`src/cli/args.rs`) and gpui's `src/sidebar/forms/agents.rs` were read on `main` on 2026-11-09; upstream's `issue` commands (`src/cli/args/issue.rs`, 0.13.28) and gpui's issues panel (`src/panels/issues/`) on 2026-11-10, and upstream's `App::issue_sources`, `App::places` (`src/app/trackers.rs`) and `design/issues.md` on 2026-11-10 for task 045; `flow list --json` and `flow run --json` were run against 0.13.31 on 2026-11-10 for task 047 (the fixtures `flow-list/0.13.31/` and `flow-run/0.13.31/`).

## Where the choices come from

- **The workspaces are the session's**, as the `Store` last read them (`start_projects`, `StartChoices { boot, projects }` with `ProjectChoice { id, name, workspaces }` and `WorkspaceChoice { id, name }`): the names the Mac shows (`custom_name`, else `name`, for both), in the session's order. No call of its own, so they show at once. The picker lists them flat as `<project> › <workspace>`, the label the board's rows and upstream's places use; with none, it says `No workspace is open on this Mac.` and `Start` rests.
- **Which workspace is chosen** (045): opened from an agent, that agent's (Starting from an agent), while the session has it; else the last one an agent was started in from the app while it runs, if the session still has it on the same `boot`; else the only one; else none, and sending says `Choose a workspace` under the field. The same memory as the agent's, so nothing is kept after the app closes. The id is kept with the `boot` it was read on, and taken only while the `Store` gives that boot: upstream gives pane, tab and workspace ids again from 1 on every start, `restart` and updates included, so after one the same id may name another workspace, and `start` takes no `--boot` to refuse it. Rejected: the id alone, which "while the session has it" lets through when the new run gives it to another workspace (review of 2026-11-10); and matching the workspace by its label across boots, which two workspaces of the same name defeat.
- **The agents are cornercase's**: `account list --check --json` through the queue (`installed_agents`), its `agents` field, only those with `installed: true`, in cornercase's order. The app keeps no list of agents, so one cornercase adds shows up without a release of the app. An absent `agents` (a server with `account-list` but older than cornercase-terminal#543) reads as none installed. The rest of the answer (providers, accounts, paths) is not read, and the fixture keeps only `agents`.
- **They load apart**: `account list --check` runs each account's status command when accounts were added (up to 20 s each, upstream's `design/accounts-and-profiles.md`), so the projects and the other fields can be filled while the agents load. The agents' picker says it is reading, shows cornercase's reason with `Try again` when it fails, and says when none is installed, which holds `Start`.
- **Which agent is chosen**: the first installed one (claude comes first in cornercase's order), then the last one started from the app while it runs, if it is still installed. Rejected: the `agent` of `config --json`, another call with a large answer, useless when it is `auto`; and no default, one more tap almost every time.
- **The model is free text**, optional: cornercase says nothing of the models each agent takes (Upstream gaps), and a list in the app would go stale.
- **After a server restart** (a new `boot` while the screen is open) the choices are read again, since ids belong to one run of the server and `start` takes no `--boot`. The chosen workspace is emptied even when its id is still there, as that id may now name another workspace, and gives way to the only one, else to none (the last used is of the old boot); an issue's chosen place is emptied too, its ids being of the old boot as well. The places of an issue's form come with the issue, of the old boot as well, so after a restart its `Where` lists none and says `cornercase restarted: go back to the issue to see where it can start.`, and `Start` sends nothing: going back to the issue and `Start` again gives them anew. Rejected: reading the places again from the form, one more call for a rare case, and keeping them, as an id of the old boot may now name another workspace or project (ids of every level come from one counter). Every other field stays. The boot is the `Store`'s, given with the projects: every restart makes the `Store` connect again, so each time the connection comes back to `connected` the screen reads the projects (the session, no call to the Mac) and, when their boot changed or the last read of the agents failed (such as one cut off by the dropped connection), the agents. Rejected: the boot of the board's rows, which is missing while no agent runs, the usual case before the first one starts; and reading the agents again on every return to `connected` after a read that worked, which comes with every return to the foreground and runs `account list --check` for nothing.

## Starting an agent

- **`start <agent> --workspace <id> [--model=<model>] --prompt=<prompt> --placed --json`**, through the ordered queue (`Queue::ask`): the agent starts in a new tab of the chosen workspace, which the screen says under the picker. Values are trimmed, and an empty model is not sent.
- **`Own worktree`**, a switch under the workspace, off by default: on, it shows `Branch`, which must be named (`Name the branch`), and sends **`start <agent> --project <the workspace's project> --worktree=<branch> …`**, a new worktree and workspace on that branch, made from the workspace's project. There is no project picker apart: the workspace already says which project. Both starts, and an issue's, are one `Place` in `crates/core/src/cli/start.rs`, `Workspace { workspace }` (`--workspace`) or `Worktree { project, branch }` (`--project`, `--worktree=`), so the argv of each is built in one spot. Rejected (P1, the user on 2026-11-10): dropping `Own worktree` too. An agent in its own worktree has a row, so the phone opens its chat, terminal, changes and files like any other; only a workspace without an agent was of no use from the phone (No workspace without an agent).
- **`--x=value` and `--` before a positional**, so a value that starts with `-` (a prompt such as `--help me`, a branch, a workspace's name) is not read by clap as an option.
- **Always an explicit agent**: without one, `start` uses `auto`, the agent the caller runs in, which means nothing from a phone.
- **`--placed`** answers once the tab is open (`project`, `workspace`, `tab`, `pane`, an optional `warning`), before the project's setup runs and the agent is typed. Without it, `start` waits for the agent to take the prompt, and a folder's trust question would hold the queue, and every send behind it, until someone answers it.
- **No `--focus`**: gpui sends it because it is the window; whoever uses the phone is seldom at the Mac, and moving the window under someone who is would surprise them.
- **The prompt travels as one argument** of the argv, inside the JSON line of `requests --follow`, with no limit of the app's own. Should the bridge or a later `/cli` limit the size of an argv, `--prompt-file -` with the prompt on standard input is the way out, which the queue already carries.
- **The ids answer is read leniently** (`Started`, `#[serde(default)]`), with fixtures of 0.13.19 in the shape of upstream's `control::Ids`, with made-up ids.

## No workspace without an agent

- **Task 023's `Workspace` action, `new-workspace --project <id> [--worktree] --json -- <name>`, left in 045**, with its form, its command, its `Workspace <name> created` toast and its line in `contract::REQUIRED`. A workspace without an agent has no row, and the phone opens a workspace only through an agent's row (the terminal needs the row; `Changes` and `Files` sit in the agent's header), so what it made could not be seen or used from the phone, as the user found on his iPhone (029, 2026-11-10). An agent is now started in a workspace that is open already (`start --workspace`) or in its own worktree. The bridge's allowlist keeps `new-workspace`, since it mirrors upstream's commands, not the app's (Bridge).

## The screen

- **A screen of its own, `start`, pushed over the board** by the board's `Start` button, or over an agent by its `New agent` (Starting from an agent), both resting while the connection is not `connected` (Look › Navigation). Rejected: the ticket's sheet from the bottom, since the prompt always opens the keyboard and WKWebView covers what is fixed at the bottom (Look › Forms).
- **Two actions, `Agent` and `Issue`**, two buttons with `aria-pressed` (`Segmented`, which the issue's `Agent` and `Flow` share) that switch between two forms (`AgentForm`, `ShowIssues`), each with its own button; until 045 a third, `Workspace` (No workspace without an agent). One `StartForm` holds them, and the issue's form (`IssueForm`) when Start opens with an issue, which hides the actions. `Issue` only says what it shows and opens the issues of every project (From an issue).
- **Checked before sending**, each error under its field: a workspace, an agent, a prompt that is not only spaces, a branch with `Own worktree`; for an issue, where it starts and an agent, or a flow (With a flow). A server is not asked what the phone can tell.
- **While it sends**, the button shows the spinner and `Starting…`, the fields rest, and nothing can send again. Outside `connected`, the buttons rest and a line says that what was typed stays until the app connects.
- **A refusal keeps everything typed** and shows cornercase's reason over the button, its stderr without `Error:` (`CommandError::reason`), not only in a toast: `--worktree` in a folder that is not a repository's root, for one, which the session cannot tell beforehand.
- **`Unanswered` is never retried**: the line may have run. It says that the agent may have started, and to look before trying again. A job the queue skipped (`Skipped`, its line never written, after a reconnection) is `not_sent`, `nothing was sent`, as in the chat: it surely did not run, so sending again is safe. The pickers say `cornercase did not answer.` when reading the agents or the workspaces is left unanswered.

## Starting from an agent

- **`New agent`** (icon `plus`, named for VoiceOver), the fourth icon of the agent's bar after `Terminal`, `Changes` and `Files` (Chat › The header stays at the top), pushes `start` with the agent's workspace (`{ name: 'start', machine, workspace }`), which the form chooses before reading the session (`StartForm.prefer`); it rests outside `connected` like the board's `Start`. It is the usual case from a phone: another agent beside the one being followed, on the same code. `Back` returns to the agent.
- **In the bar, not in the large header** (P3): measured on 2026-11-10 (Chat › The header stays at the top), the four icons leave the compact line 146 pt on a 390 pt phone and 131 pt on a 375 pt one, so a title is cut short (`Fix the l…`) but nothing overlaps, and the button is in reach while the thread scrolls. Rejected: a button under the title in the large header, which scrolls away with it.

## After it starts

- **The agent's screen is all that stays over the board** (`router.settle`, `{ name: 'agent', machine, pane, starting: true }`, on the start route's `machine`), so `Back` goes to the board and not to a form already sent, nor to the issue and the list it came from (From an issue). Started from the board, the form was the only screen over it, as 023's start screen did when it replaced the top route; started from an agent, that agent's screen goes too, and is a tap away on the board. A `warning` in the answer shows as an `info` toast. `Back` still works while it sends; if the start screen is no longer on top when the answer comes, only a toast says it started (`<agent> started`), so the answer never closes or replaces a screen opened since.
- **`Starting <agent>…`** with the spinner, until the pane's row comes in `agents-changed`: at the answer, the pane holds no agent yet, and the rows list only panes with one. Without it, the screen would say `This agent is no longer running.` at the first list (Chat › Gone). While it starts, a list without the pane does not count it as gone; once its row was seen, the usual rules hold, and another machine still ends it. Rejected: staying on the form until the row comes, with a limit, since a project's setup can take minutes and the form would be held all that time.
- **No limit on the wait**: if the agent never starts (its setup fails, its command is not found), the screen keeps saying it starts, and `Back` goes to the board, where the tab's shell shows no row.
- **The agent's name is kept by `App`**, the last one started, since the route says only `starting`.

## From an issue

Task 024: the issues of the trackers cornercase has connected, one issue read, and an agent started on it with `start --issue`; task 045 made the list every project's and moved the project to where the agent starts. cornercase writes the agent's prompt from the issue, names its branch and makes the worktree; the tokens stay in cornercase on the Mac.

- **The way in is Start's `Issue`** (024's P1): its form has a line, `See the issues of every project and pick one to start an agent on it.`, and `Show issues`, which pushes `issues` over Start. Until 045 it had a project's picker. Rejected: an `Issues` button on the board beside `Start`, a second way into the same screen that would crowd the board's bar.
- **What the project does to `issue list`** (read in upstream's `App::issue_sources` and `Source::in_repository` on 2026-11-10): only GitHub and GitLab issues belong to a project, those of the repository of its folder (`repository: true` in `issue sources`). Shortcut, Linear, Jira, Plane and Asana are the account's, and `issue list --project` gives the same list for every project. On the user's Mac only Shortcut was connected (GitHub was `failing`), so 024's picker changed nothing in the list: "no se está filtrando" (029, 2026-11-10).
- **Every issue, and the place when starting** (045's P2): the list holds the issues of every connected tracker, each row says its tracker and, for GitHub and GitLab, its project (`GitHub · shop`, by the session's names), and where the agent works is chosen on the issue's form (Where). Rejected: a real filter, a project's picker only for GitHub and GitLab with the account's trackers listed beside it, two ways of listing on one screen, and on the user's Mac a picker that would still filter nothing; and keeping the picker with a note that it filters only GitHub and GitLab, which explains a control that does nothing instead of removing it. The project matters where it changes something: the folder the agent works in.
- **The trackers first**: `issue sources --project <id> --json` for each project of the session (`start_projects`, as Start reads them), one-shot on the transport, as `files`, at most four at a time (`limited` in `src/lib/issueSweep.ts`); they need no network on the Mac. A read that fails for any project fails the whole read, with its reason and `Try again`. Each tracker shows once (`standing`): connected if some project has it connected, else as in the project where it misses least, one in a repository first, so `repository` shows only when no project's folder has one. With none `connected` in any project, the list gives way to `No issue tracker is connected` and, per tracker, what it misses (`missing`) or why it fails (`reason`), and how to fix it on the Mac: a missing `repository` (the folder is not in a git repository or, for GitLab, its remote is not on the GitLab server) by opening a folder of the right repository as the project, which no setting fixes; anything else, or a failure, for GitHub by signing in to `gh` in the project's folder (a `gh` without a session comes as `failing` with its reason, not in `missing`), for the rest in cornercase's Settings › Issues; `Check again` reads them again. The app has no field for a token: trackers are connected on the Mac. A tracker that is `failing` while others list says its reason above the rows.
- **What is listed** (`toList`): each account's tracker that is connected, once, with the first project that has it connected; GitHub and GitLab once per project that has them connected. Each is one **`issue list --project <id> --source=<src> [--closed] [--assignee me] [--cached] --json`**, at most four at a time, and the rows show as each answer comes. Open issues by default, `Closed too` adds `--closed`, `Mine` adds `--assignee me`, and with more than one tracker connected a row of trackers lists only the one chosen. A tracker that is no longer connected after a new read of the trackers drops back to all of them. Rejected: filtering by a given person (`issue people`), more than the phone needs. With the user's Mac (25 projects and more), that is one call per account's tracker plus one per project with GitHub or GitLab connected, twice (cached, then live): Upstream gaps asks for one call.
- **The lists join** (`gathered`): an issue that comes twice, by its `url` (one repository opened as two projects, or a checkout and its copy), shows once, with the first project; without a `url`, by tracker, key and project. `#12` of two repositories differs in `url` and shows twice, each with its project. The newest `updated_at` first, by the instant it names, ties in the order they came: each tracker writes it its own way (Jira with an offset such as `+0100`, GitLab and Linear with milliseconds, GitHub without), so as text a list of several trackers came out of order. An offset without a colon gets one before parsing, as JavaScriptCore does not promise to read it; a time that cannot be read counts as the oldest. Upstream orders one tracker's list the same way (`parse_time`).
- **Cached first, then live** (P3): each list is asked twice, `--cached` and then without it, as gpui does, since the trackers' APIs and `gh` take seconds. The cached answer shows at once only when it holds issues, so an empty cache never wipes what is shown; the live one replaces it and ends the bar's spinner. Rejected: only live, a blank screen for seconds on each filter.
- **A partial answer is an answer**: `issue list` exits 3 when a tracker failed, after printing the whole JSON, read with `transport::partial_json` as `files` (Changes and files › The commands). The rows that came are shown, with a line per tracker that failed, its name and its first error, once, also when it failed in every project.
- **The search is the phone's**: `issue list` takes no query (Upstream gaps), so the field keeps the rows whose key, title or labels hold every word typed, without case and without asking again. Rejected: sending the words as a filter, which no tracker command takes.
- **No pages**: upstream gives at most 100 issues per tracker (`LIMIT`) and no way to ask for more. When a tracker gave that many, a line says that it has more and to narrow the filters, with no number the app would have to invent.
- **Answers that come late are dropped**: each read of the trackers and each round of lists counts its asks, so one that arrives after a newer filter, or after the screen is left, changes nothing; one that names another project than the one asked neither. A failed read keeps the rows under its reason and `Try again`, which reads the trackers again when their read is what failed, and otherwise only the list.
- **Read again when the connection comes back** to `connected` (also after a server restart, since each one makes the `Store` connect again), the list from its trackers and the issue too. They take no boot: the `Store`'s boot reaches only the start screen's choices, and the reconnection already covers a restart.
- **The issue is `issue read --project <id> --source=<src> --json -- <key>`**, with the row's project (for an account's tracker, the one it was listed with) and always with the row's tracker, since `#12` can be GitHub's and GitLab's, and the key after `--`, so one that starts with `-` is no option. Its head says its state, key, author and age, title, labels and branch; its body and its comments (P4), oldest first, are drawn with the chat's `Markdown`, so links and images stay text (Chat › Markdown). Rejected: only the body, which leaves out what was said since, often where the context is. It shows `Reading the issue…` while it reads, and cornercase's reason with `Try again` when it fails.
- **Each screen keeps its state while its route is in the stack** (`Router.latest`), so going back from the issue to the list, or from the form to the issue, reads nothing again; leaving the screen stops it, and an answer for it is dropped.
- **`Start` on the issue opens Start with the issue** (`start` with `issue`, its project when it is a repository's, its places and the workspace Start was opened with): its form shows the issue's key, its project when it has one, and its title, then `Where`, the branch for a new worktree, the agent's picker (the rule of Where the choices come from) and the model, empty. There is no prompt field: `start` refuses a prompt with an issue, and cornercase writes it. The prompt it will use (`prompt` of `issue read`) shows last in a closed `details`, read-only (P5), so the user knows what the agent gets. Rejected: hiding it, since it cannot be edited.
- **Where** (045), a picker of the places of `issue sources` (`places`: the same list in every project's answer, kept once by project and workspace). Upstream's rule (`App::places`, the Mac's issues dialog's own): a project whose folder is a repository's root gives one place, a new worktree of it (`worktree: true`), and none of its workspaces; any other project gives each of its open workspaces, a new tab there (`worktree: false`). A GitHub or GitLab issue lists only its project's places, since upstream looks the issue up in the repository of the project it starts in; an account's issue lists them all. Each option says what it makes: `<project> › <workspace> · new tab`, or `<project> · new worktree on <branch>`, with the branch typed or else the issue's (`· new worktree` when there is neither).
- **Which place is chosen**: the workspace Start was opened with (Starting from an agent) when it is among the places; else, for a GitHub or GitLab issue, the new worktree of its project, cornercase's usual way, whose branch closes the issue when its pull request merges; else the only place if there is one, for an account's issue or for a GitHub or GitLab one whose project is not a repository's root and has one workspace open (review of 2026-11-10: it asked for a tap on `Where` with nothing to choose); else none, and sending says `Choose where to start`.
- **`Branch` only for a new worktree**, filled with the issue's, editable, with a note that the agent works in its own worktree on it, or in a new tab in the project's folder when that folder is not the root of a git repository; when the issue has no branch, `Left empty, cornercase names the branch.` A new tab has no branch and says `The agent starts in a new tab there.` Upstream names an issue's branch per project (`App::issue_branch`, its template), so for an account's issue the branch shown is the one of the project it was listed with; left as it is, no `--worktree=` goes and cornercase names it for the place's project.
- **`start <agent> (--workspace <id> | --project <id>) --issue=<key> --source=<src> [--worktree=<branch>] [--model=<model>] --placed --json`**, through the ordered queue as a start with a prompt, with the same `Starting…`, refusals and `Unanswered` (Starting an agent): `--workspace` for a workspace's place, `--project` for a new worktree. `--worktree=` goes only with a new worktree and a branch that differs from the issue's: without it cornercase uses the issue's branch, as gpui sends it. `--worktree` is not a switch: it takes the branch's name.
- **After it starts, the agent's screen is all that stays over the board** (P2), as above: `Back` goes to the board, not to the issue nor the list. Rejected: back to the issue, which would leave a form already sent one step below and a list that is often stale.

### With a flow

Task 047, from the user's iPhone (029, 2026-11-10): "cuando arrancas una issue, que te permita elegir un flow para lanzarla". A flow is a team of agents with roles (an orchestrator, a coder, a reviewer…) that cornercase sets up and runs; `flow run --issue` starts one on an issue, as the Mac's issues dialog does.

- **`Agent` or `Flow`** above `Where` (`Who works`, the same `Segmented` as Start's actions), on `Agent` when the form opens, which is the form as it was. `Flow` shows only when the issue has a place with a new worktree and the flows of that place's project came with at least one, or their read failed, so the picker can say cornercase's reason with `Try again`. While they are read it does not show, so nothing shows only to be taken away; once chosen it stays. Rejected (P3): a second button on the issue, `Start a flow`, as the Mac has, another way into the same form.
- **Only new worktrees**: a flow always works in a worktree of its own (upstream has no flow in an open workspace) and is refused in a project whose folder is not a repository's root. So in `Flow`, `Where` lists only the places with `worktree: true`, with the same labels, and the place chosen follows Which place is chosen within them; each mode keeps its own choice, so going back to `Agent` gives back its place. Without such a place `Flow` does not show: that, and not a project without flows, is what usually hides it, as cornercase's built-ins come with any agent installed.
- **The list is `flow list --project <id> --json`**, one-shot on the transport as `issue sources`, not through the queue: it makes nothing on the Mac, so it need not wait behind a start. It is read as the form opens, for the project of the place `Flow` would take (else the first new worktree), so that `Flow` can be offered, and again for each project the place moves to; each list is kept by project while the form lives and dropped after a server restart, as the places are. An answer for a place left meanwhile changes nothing. Only `flows` is read (`name`, `description`, `roles` with `role` and `agent`, `problems`, `default`), in cornercase's order, which is the user's; `broken` and `hidden` are not listed.
- **Each option** says `<name> · N agents · <description>`; one with `problems` (an agent that is not installed, a name one of the user's flows takes) says its first problem instead and cannot be chosen, a disabled `option`. Under the picker, the chosen flow's team, `role · agent`, the orchestrator first.
- **Which flow is chosen**: the last one started from the app while it runs, if it is still listed and without problems; else cornercase's `default`, without problems; else the first without problems; else none, and sending says `Choose a flow` under the picker.
- **No agent and no model**: each role brings its own, set in the flow on the Mac. The prompt cornercase will use shows folded and read-only, as for an agent, since `flow run --issue` writes it from the issue as `start --issue` does (P1). Rejected: a field for `--prompt`, which replaces the issue's prompt rather than adding to it and needs the feature `flow-issue-prompt`, while the agent's form has none either (Left out).
- **`flow run --project <id> --issue=<key> --source=<src> [--worktree=<branch>] --json -- <name>`**, through the ordered queue as a start, with the same `Starting…`, refusals and `Unanswered` (Starting an agent): `--worktree=` only when the branch differs from the issue's, values after `=`, and the name, which may hold spaces (`Full issue`) or start with `-`, after `--`, as it is `flow run`'s only positional. It answers once the tabs exist, after git has made the worktree and before the setup and the agents, so the queue waits only for git. `Unanswered` says that the flow may have started, and to look at the board before trying again. Refusals seen on 0.13.31, each shown over the button: a branch checked out in the project's own folder, a branch whose workspace already runs a flow, a flow with problems, a built-in the user deleted. A branch that starts with `-` reaches git as an option and comes back as `unknown switch`, a confusing reason for a name git refuses anyway.
- **The orchestrator is the agent that starts**: of the answer's `members` (read leniently), the one whose `role` is `orchestrator`, else the first, gives the `Started` a start gives, with its pane and its agent's name, and the run's `note` as its `warning`; an answer without members is a read error. So the app does what After it starts says: the orchestrator's screen with `Starting <agent>…` until its row comes, then `Back` to the board, where it carries its team folded under it (Board). Rejected (P2): landing on the board, another way than Start's. The orchestrator starts last, after the project's setup and the other members (upstream's `launch_run` holds its launch until theirs), so its row comes later than a lone agent's. Meanwhile each member is an agent whose `parent` is a pane without one yet, so the board shows it as a root until the orchestrator's row comes (Board › Tree and folding); `status` already gives that pane its `role`, which the board does not read for this.

## The trust question

- With `accept_trust_prompts` off, cornercase's default, an agent in a new worktree (a new folder) asks first whether to trust it, and the prompt waits for the answer. It is answered from the phone with Enter in the chat's keys (017) or in the terminal (021); until those exist, the agent's screen has `Terminal` (020, passive), which shows the question but cannot answer it. `--placed` keeps it from holding the queue.
