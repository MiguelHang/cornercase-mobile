# Starting work

New work on the Mac from the phone: an agent with a prompt, in its own worktree when a branch is given, or a workspace without one (task 023), or an agent on an issue of the project's trackers (task 024). Code: `crates/core/src/cli/agents.rs` (`account list --check --json`), `crates/core/src/cli/start.rs` (the argv and the ids that answer), `src-tauri/src/commands/start.rs`, `src/lib/startForm.svelte.ts` and `src/routes/start/`; for the issues, `crates/core/src/cli/issues.rs` (their argv and answers), `src-tauri/src/commands/issues.rs`, `src/lib/issues.svelte.ts` and `src/routes/issues/`. Upstream's `StartArgs` and `NewWorkspaceArgs` (`src/cli/args.rs`) and gpui's `src/sidebar/forms/agents.rs` were read on `main` on 2026-11-09; upstream's `issue` commands (`src/cli/args/issue.rs`, 0.13.28) and gpui's issues panel (`src/panels/issues/`) on 2026-11-10.

## Where the choices come from

- **The projects are the session's**, as the `Store` last read them (`start_projects`, `StartChoices { boot, projects }` with `ProjectChoice { id, name }`): the name the Mac shows (`custom_name`, else `name`), in the session's order. No call of its own, so they show at once; with one project, it is chosen.
- **The agents are cornercase's**: `account list --check --json` through the queue (`installed_agents`), its `agents` field, only those with `installed: true`, in cornercase's order. The app keeps no list of agents, so one cornercase adds shows up without a release of the app. An absent `agents` (a server with `account-list` but older than cornercase-terminal#543) reads as none installed. The rest of the answer (providers, accounts, paths) is not read, and the fixture keeps only `agents`.
- **They load apart**: `account list --check` runs each account's status command when accounts were added (up to 20 s each, upstream's `design/accounts-and-profiles.md`), so the projects and the other fields can be filled while the agents load. The agents' picker says it is reading, shows cornercase's reason with `Try again` when it fails, and says when none is installed, which holds `Start`.
- **Which agent is chosen**: the first installed one (claude comes first in cornercase's order), then the last one started from the app while it runs, if it is still installed. Rejected: the `agent` of `config --json`, another call with a large answer, useless when it is `auto`; and no default, one more tap almost every time.
- **The model is free text**, optional: cornercase says nothing of the models each agent takes (Upstream gaps), and a list in the app would go stale.
- **After a server restart** (a new `boot` while the screen is open) the choices are read again, since ids belong to one run of the server and `start` takes no `--boot`. A chosen project that is gone is emptied; every other field stays. The boot is the `Store`'s, given with the projects: every restart makes the `Store` connect again, so each time the connection comes back to `connected` the screen reads the projects (the session, no call to the Mac) and, when their boot changed or the last read of the agents failed (such as one cut off by the dropped connection), the agents. Rejected: the boot of the board's rows, which is missing while no agent runs, the usual case before the first one starts; and reading the agents again on every return to `connected` after a read that worked, which comes with every return to the foreground and runs `account list --check` for nothing.

## Starting an agent

- **`start <agent> --project <id> [--worktree=<branch>] [--model=<model>] --prompt=<prompt> --placed --json`**, through the ordered queue (`Queue::ask`). Values are trimmed, and an empty model or branch is not sent. With a branch, the agent works in a new worktree on it; without one, it starts in a new tab in the project's folder, which the screen says under the branch.
- **`--x=value` and `--` before a positional**, so a value that starts with `-` (a prompt such as `--help me`, a branch, a workspace's name) is not read by clap as an option.
- **Always an explicit agent**: without one, `start` uses `auto`, the agent the caller runs in, which means nothing from a phone.
- **`--placed`** answers once the tab is open (`project`, `workspace`, `tab`, `pane`, an optional `warning`), before the project's setup runs and the agent is typed. Without it, `start` waits for the agent to take the prompt, and a folder's trust question would hold the queue, and every send behind it, until someone answers it.
- **No `--focus`**: gpui sends it because it is the window; whoever uses the phone is seldom at the Mac, and moving the window under someone who is would surprise them.
- **The prompt travels as one argument** of the argv, inside the JSON line of `requests --follow`, with no limit of the app's own. Should the bridge or a later `/cli` limit the size of an argv, `--prompt-file -` with the prompt on standard input is the way out, which the queue already carries.
- **The ids answer is read leniently** (`Started`, `#[serde(default)]`), with fixtures of 0.13.19 in the shape of upstream's `control::Ids`, with made-up ids.

## Creating a workspace

- **`new-workspace --project <id> [--worktree] --json -- <name>`**: the project, the name and the `Own worktree` switch, whose name is then the branch. It has no agent, so there is no row and no screen to open: the app says `Workspace <name> created` in an `info` toast and goes back to the board. Rejected: staying on the form to create another or to start an agent there, which needs `start --workspace` (left out).

## The screen

- **A screen of its own, `start`, pushed over the board** by the board's `Start` button, which rests while the connection is not `connected` (Look › Navigation). Rejected: the ticket's sheet from the bottom, since the prompt always opens the keyboard and WKWebView covers what is fixed at the bottom (Look › Forms).
- **Three actions, `Agent`, `Workspace` and `Issue`**, three buttons with `aria-pressed` that switch between three forms (`AgentForm`, `WorkspaceForm`, `ShowIssues`), each with its own button. One `StartForm` holds them, so the project chosen in one is the others' too. `Issue` only picks the project and opens its issues (From an issue).
- **Checked before sending**, each error under its field: a project, an agent, a prompt that is not only spaces, a workspace's name. A server is not asked what the phone can tell.
- **While it sends**, the button shows the spinner and `Starting…` (or `Creating…`), the fields rest, and nothing can send again. Outside `connected`, the buttons rest and a line says that what was typed stays until the app connects.
- **A refusal keeps everything typed** and shows cornercase's reason over the button, its stderr without `Error:` (`CommandError::reason`), not only in a toast: `--worktree` in a folder that is not a repository's root, for one, which the session cannot tell beforehand.
- **`Unanswered` is never retried**: the line may have run. It says that the agent may have started, or the workspace may exist, and to look before trying again. A job the queue skipped (`Skipped`, its line never written, after a reconnection) is `not_sent`, `nothing was sent`, as in the chat: it surely did not run, so sending again is safe. The pickers say `cornercase did not answer.` when reading the agents or the projects is left unanswered.

## After it starts

- **The agent's screen is all that stays over the board** (`router.settle`, `{ name: 'agent', machine, pane, starting: true }`, on the start route's `machine`), so `Back` goes to the board and not to a form already sent, nor to the issue and the list it came from (From an issue). Started from the board, the form was the only screen over it, as 023's start screen did when it replaced the top route. A `warning` in the answer shows as an `info` toast. `Back` still works while it sends; if the start screen is no longer on top when the answer comes, only a toast says it started (`<agent> started`, `Workspace <name> created`), so the answer never closes or replaces a screen opened since.
- **`Starting <agent>…`** with the spinner, until the pane's row comes in `agents-changed`: at the answer, the pane holds no agent yet, and the rows list only panes with one. Without it, the screen would say `This agent is no longer running.` at the first list (Chat › Gone). While it starts, a list without the pane does not count it as gone; once its row was seen, the usual rules hold, and another machine still ends it. Rejected: staying on the form until the row comes, with a limit, since a project's setup can take minutes and the form would be held all that time.
- **No limit on the wait**: if the agent never starts (its setup fails, its command is not found), the screen keeps saying it starts, and `Back` goes to the board, where the tab's shell shows no row.
- **The agent's name is kept by `App`**, the last one started, since the route says only `starting`.

## From an issue

Task 024: a project's issues, from the trackers cornercase has connected for it, one issue read, and an agent started on it with `start --issue`. cornercase writes the agent's prompt from the issue, names its branch and makes the worktree; the tokens stay in cornercase on the Mac.

- **The way in is Start's third action, `Issue`** (P1): its form has only the project's picker and `Show issues`, which pushes `issues` over Start for that project. Rejected: an `Issues` button on the board beside `Start`, a second way into the same screen that would crowd the board's bar, where the start screen already has the project's picker.
- **The trackers first**: `issue sources --project <id> --json`, one-shot on the transport, as `files`. With none `connected`, the list gives way to `No issue tracker is connected` and, per tracker, what it misses (`missing`) or why it fails (`reason`), and how to fix it on the Mac: a missing `repository` (the folder is not in a git repository or, for GitLab, its remote is not on the GitLab server) by opening a folder of the right repository as the project, which no setting fixes; anything else, or a failure, for GitHub by signing in to `gh` in the project's folder (a `gh` without a session comes as `failing` with its reason, not in `missing`), for the rest in cornercase's Settings › Issues; `Check again` reads them again. The app has no field for a token: trackers are connected on the Mac. A tracker that is `failing` while others list says its reason above the rows.
- **The list is `issue list --project <id> [--source=…] [--closed] [--assignee me] [--cached] --json`**: open issues of every connected tracker by default, `Closed too` adds `--closed`, `Mine` adds `--assignee me`, and with more than one tracker connected a row of trackers adds `--source=`. A tracker that is no longer connected after a new read of the trackers drops back to all of them. Rejected: filtering by a given person (`issue people`), more than the phone needs.
- **Cached first, then live** (P3): each list is asked twice, `--cached` and then without it, as gpui does, since the trackers' APIs and `gh` take seconds. The cached answer shows at once only when it holds issues, so an empty cache never wipes what is shown; the live one replaces it and ends the bar's spinner. Rejected: only live, a blank screen for seconds on each filter.
- **A partial answer is an answer**: `issue list` exits 3 when a tracker failed, after printing the whole JSON, read with `transport::partial_json` as `files` (Changes and files › The commands). The rows that came are shown, with a line per tracker that failed, its name and its error, once.
- **The search is the phone's**: `issue list` takes no query (Upstream gaps), so the field keeps the rows whose key, title or labels hold every word typed, without case and without asking again. Rejected: sending the words as a filter, which no tracker command takes.
- **No pages**: upstream gives at most 100 issues per tracker (`LIMIT`) and no way to ask for more. When a tracker gave that many, a line says that it has more and to narrow the filters, with no number the app would have to invent.
- **Answers that come late are dropped**: each read of the trackers and each list counts its asks, so one that arrives after a newer filter, or after the screen is left, changes nothing; one for another project neither. A failed read keeps the rows under its reason and `Try again`, which reads the trackers again when their read is what failed, and otherwise only the list.
- **Read again when the connection comes back** to `connected` (also after a server restart, since each one makes the `Store` connect again), the list from its trackers and the issue too. They take no boot: the `Store`'s boot reaches only the start screen's choices, and the reconnection already covers a restart.
- **The issue is `issue read --project <id> --source=<src> --json -- <key>`**, always with the row's tracker, since `#12` can be GitHub's and GitLab's, and the key after `--`, so one that starts with `-` is no option. Its head says its state, key, author and age, title, labels and branch; its body and its comments (P4), oldest first, are drawn with the chat's `Markdown`, so links and images stay text (Chat › Markdown). Rejected: only the body, which leaves out what was said since, often where the context is. It shows `Reading the issue…` while it reads, and cornercase's reason with `Try again` when it fails.
- **Each screen keeps its state while its route is in the stack** (`Router.latest`), so going back from the issue to the list, or from the form to the issue, reads nothing again; leaving the screen stops it, and an answer for it is dropped.
- **`Start` on the issue opens Start with the issue** (`start` with `issue`): its form shows the issue's key, project and title, the agent's picker (the rule of Where the choices come from), the model, empty, and the branch, filled with the issue's, editable, with a note that the agent works in its own worktree on it, or in a new tab in the project's folder when that folder is not the root of a git repository. There is no prompt field: `start` refuses a prompt with an issue, and cornercase writes it. The prompt it will use (`prompt` of `issue read`) shows under the branch in a closed `details`, read-only (P5), so the user knows what the agent gets. Rejected: hiding it, since it cannot be edited. The project is the list's, not a picker.
- **`start <agent> --project <id> --issue=<key> --source=<src> [--worktree=<branch>] [--model=<model>] --placed --json`**, through the ordered queue as a start with a prompt, with the same `Starting…`, refusals and `Unanswered` (Starting an agent). `--worktree=` goes only when the branch differs from the issue's: without it cornercase uses the issue's branch, as gpui sends it. `--worktree` is not a switch: it takes the branch's name.
- **After it starts, the agent's screen is all that stays over the board** (P2), as above: `Back` goes to the board, not to the issue nor the list. Rejected: back to the issue, which would leave a form already sent one step below and a list that is often stale.

## The trust question

- With `accept_trust_prompts` off, cornercase's default, an agent in a new worktree (a new folder) asks first whether to trust it, and the prompt waits for the answer. It is answered from the phone with Enter in the chat's keys (017) or in the terminal (021); until those exist, the agent's screen has `Terminal` (020, passive), which shows the question but cannot answer it. `--placed` keeps it from holding the queue.

## Left out

- `--machine`, `--mode`, `--effort`, a tab's `--name`, profiles and accounts (`--profile`), `queue add` and flows, also with an issue (`queue add --issue`, `flow run --issue`).
- For issues: connecting a tracker or keeping a token on the phone, people to filter by (`issue people`), the workspace's name from the issue (`--workspace-name`), a prompt of the user's own with the issue (Upstream gaps), and opening the issue in the phone's browser or copying its link.
- Going back from the issues to Start opens a new form, on `Agent` and without the project chosen.
- Opening the terminal of a workspace without an agent: the `terminal` route needs an agent's row.
