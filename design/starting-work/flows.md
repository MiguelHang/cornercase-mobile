# With a flow

A topic of [Starting work](../starting-work.md): `Agent` or `Flow`, only new worktrees, the list of flows, each option, which flow is chosen, no agent and no model, an account per agent of the team, the argv of `flow run`, the orchestrator as the agent that starts.

Task 047, from the user's iPhone (029, 2026-11-10): "cuando arrancas una issue, que te permita elegir un flow para lanzarla". A flow is a team of agents with roles (an orchestrator, a coder, a reviewer…) that cornercase sets up and runs; `flow run --issue` starts one on an issue, as the Mac's issues dialog does.

- **`Agent` or `Flow`** above `Where` (`Who works`, the same `Segmented` as Start's actions), on `Agent` when the form opens, which is the form as it was. `Flow` shows only when the issue has a place with a new worktree and the flows of that place's project came with at least one, or their read failed, so the picker can say cornercase's reason with `Try again`. While they are read it does not show, so nothing shows only to be taken away; once chosen it stays. Rejected (P3): a second button on the issue, `Start a flow`, as the Mac has, another way into the same form.
- **Only new worktrees**: a flow always works in a worktree of its own (upstream has no flow in an open workspace) and is refused in a project whose folder is not a repository's root. So in `Flow`, `Where` lists only the places with `worktree: true`, with the same labels, and the place chosen follows Starting work › From an issue › Which place is chosen within them; each mode keeps its own choice, so going back to `Agent` gives back its place. Without such a place `Flow` does not show: that, and not a project without flows, is what usually hides it, as cornercase's built-ins come with any agent installed.
- **The list is `flow list --project <id> --json`**, one-shot on the transport as `issue sources`, not through the queue: it makes nothing on the Mac, so it need not wait behind a start. It is read as the form opens, for the project of the place `Flow` would take (else the first new worktree), so that `Flow` can be offered, and again for each project the place moves to; each list is kept by project while the form lives and dropped after a server restart, as the places are; until the user goes back to the issue nothing is read, `Try again` included, since the places' project ids belong to the server that went away and could name another project. An answer for a place left meanwhile changes nothing. Only `flows` is read (`name`, `description`, `roles` with `role` and `agent`, `problems`, `default`), in cornercase's order, which is the user's; `broken` and `hidden` are not listed.
- **Each option** says `<name> · N agents · <description>`; one with `problems` (an agent that is not installed, a name one of the user's flows takes) says its first problem instead and cannot be chosen, a disabled `option`. A name two flows share (one of the project's named like a built-in or one of the user's, which cornercase lists with `… is also named X and runs instead`) shows once, the first listed, with names compared as cornercase compares them, trimmed and in any case (`same_name`): `flow run -- <name>` starts that one, and a name is the option's value and key. Under the picker, the chosen flow's team, `role · agent`, the orchestrator first.
- **Which flow is chosen**: the last one started from the app while it runs, if it is still listed and without problems; else cornercase's `default`, without problems; else the first without problems; else none, and sending says `Choose a flow` under the picker.
- **No agent and no model**: each role brings its own, set in the flow on the Mac; only the accounts are chosen (below). The prompt cornercase will use shows folded and read-only, as for an agent, since `flow run --issue` writes it from the issue as `start --issue` does (P1). Rejected: a field for `--prompt`, which replaces the issue's prompt rather than adding to it and needs the feature `flow-issue-prompt`, while the agent's form has none either (Starting work › Left out).
- **An account per agent of the team** (task 052): under the team, a picker `<agent> account` for each agent of the roles (`roles[].agent`, once, in the roles' order, neither empty nor `auto`) that has added accounts, with the rules of Starting work › Where the choices come from › Which account is chosen; an agent that is no account's `provider` (opencode, grok) has none, and a flow whose team has none shows none. Choosing another flow makes them again; the choices are the agent's, so a flow with the same agent comes with the one made, here or in `Agent`, which the picker shows. `flow run` takes `--account=<agent>=<account>` for each that differs from its default, in the team's order. Rejected (P1 of 052): a `Profile` picker (`--profile`), as upstream keeps profiles for scripts and its flow dialog offers an account per agent, the user has none, and `--account` overriding `--profile` would make two controls that step on each other.
- **`flow run --project <id> --issue=<key> --source=<src> [--worktree=<branch>] [--account=<agent>=<account>…] --json -- <name>`**, through the ordered queue as a start, with the same `Starting…`, refusals and `Unanswered` (Starting work › Starting an agent): `--worktree=` only when the branch differs from the issue's, values after `=`, and the name, which may hold spaces (`Full issue`) or start with `-`, after `--`, as it is `flow run`'s only positional. It answers once the tabs exist, after git has made the worktree and before the setup and the agents, so the queue waits only for git. `Unanswered` says that the flow may have started, and to look at the board before trying again. Refusals seen on 0.13.31, each shown over the button: a branch checked out in the project's own folder, a branch whose workspace already runs a flow, a flow with problems, a built-in the user deleted. A branch that starts with `-` reaches git as an option and comes back as `unknown switch`, a confusing reason for a name git refuses anyway.
- **The orchestrator is the agent that starts**: of the answer's `members` (read leniently), the one whose `role` is `orchestrator`, else the first, gives the `Started` a start gives, with its pane and its agent's name, and the run's `note` as its `warning`; an answer without members is a read error. So the app does what Starting work › After it starts says: the orchestrator's screen with `Starting <agent>…` until its row comes, then `Back` to the board, where it carries its team folded under it (Board). Rejected (P2): landing on the board, another way than Start's. The orchestrator starts last, after the project's setup and the other members (upstream's `launch_run` holds its launch until theirs), so its row comes later than a lone agent's. Meanwhile each member is an agent whose `parent` is a pane without one yet, so the board shows it as a root until the orchestrator's row comes (Board › Tree and folding); `status` already gives that pane its `role`, which the board does not read for this.
