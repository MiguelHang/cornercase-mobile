# The machine code

A topic of [Bridge](../bridge.md): what the bridge prints on stdout for the app to add the Mac, the code that carries every address it listens on, and `--bridge-routes`, which tells the app those addresses once it is connected (task 035). What the app does with them is in [Connection › Machines](../connection/machines.md).

- **One machine, one code**: adding a Mac means adding one machine, not one route per network. Before 035 the bridge printed a block and a QR code per listener, and the user scanned the LAN's, then the Tailscale one, and got two machines unless the app's offer joined them (027). Now the bridge prints one block for the whole Mac, and the app saves one machine with every route and picks the fastest on its own.
- **What is printed** (`bridge/src/qr.rs`, `block`), on stdout:
  - a heading with the Mac's name and its networks, `MacBook Pro — LAN (en0), Tailscale (utun9)`, each kind and interface once;
  - the machine code as text, for pasting;
  - **one** QR code of exactly that text (The QR code, below);
  - after a blank line, one line per listener with its kind, interface and its URL of one route, `LAN (en0)  ws://192.168.1.20:8765/?token=…`, without a QR code: for `websocat` and for debugging, and still accepted by the app as a code of one route.
  - With `--loopback` the code holds only `127.0.0.1` and the heading's network is `loopback`. An IPv6 address goes in brackets in the URLs (`ws://[fd7a:115c:a1e0::1]:8765/?token=…`), as URLs write it. The logs on stderr did not change.
- **Why stdout**: the logs go to stderr and never hold the token; the block is the only output with it, so it goes apart, where it can be read without the logs. The cost: redirecting stdout to a file leaves the token in that file.
- **The QR code**: `qrcode` at error correction level L, as upstream's `src/ui/remote_access.rs`, drawn with `▀`, the top module as the foreground and the bottom one as the background, in fixed colours of the 256 palette (16 black, 231 white) so the terminal's theme cannot invert it, with a quiet zone of 4 modules on every side; each line ends by resetting the colours. It does not adapt to the terminal's width (its size, below).
- **The format** (`crates/core/src/machines/code.rs`, `MachineCode`): `ws://<first>:<port>/?token=<token>&also=<host>&also=<host>&name=<name>`.
  - `<first>` is the first listener, in the bridge's order (LAN before Tailscale, then by address); each `also=` is another listener's host alone. An IPv6 address goes in brackets in the authority, as URLs write it, and without them in `also=`: `:` is valid in a query and `[` `]` are not.
  - The port is the authority's: the bridge listens on one port on every address (Listening on the network › One port), so `also=` needs none. A code whose hosts would need different ports cannot be written.
  - `name=` is the Mac's name in UTF-8, every byte but the unreserved ones (`A`–`Z`, `a`–`z`, `0`–`9`, `-`, `.`, `_`, `~`) percent-encoded, so spaces, accents, `&`, `#`, `%` and emoji go and come back whole. It is optional, and cut to 64 characters, the app's longest name.
  - Parsing refuses, each with its own message: an empty `also=`, one that is neither an IPv6 address nor a host name, two `name=`, and a name whose encoding is broken or is not UTF-8. A host repeated is kept once. The token and the rest are checked as `Route::parse` checks a URL (Connection › Machines with several routes), with the same code.
  - `MachineCode::new` takes the first address, so a code without one cannot be made; with no address to listen on the bridge still exits with `no LAN or Tailscale address to listen on` before it prints anything.
  - **The type lives in the core** and the bridge builds its code with it, rather than in `qr.rs` as the task first said: one format, its round trip tested in one place (`code/tests.rs`), and no copy for jscpd. The bridge already depends on `cornercase-core` for the protocol.
- **Why a `ws://` URL with `also=` and `name=`** (P1): it is compatible both ways. An app from before 035 runs it through `Route::parse`, which ignores the parameters it does not know, and saves the first route, the LAN's, which works as before. The new app takes a URL of one route, the ones of today and the debugging lines, as a code of one route without a name. It reuses `Route::parse`'s address and token, and it fits in the QR code. Rejected: a scheme of our own, `cornercase://machine?…`, cleaner and good for a deep link, but an older app refuses it and `checkUrl` would change; JSON in the QR code, bigger, not a URL to paste, refused by an older app too.
- **The size of the QR code**, measured on 2026-11-09 with `qrcode` 0.14.1 at level L, its quiet zone included: LAN and Tailscale's IPv4 with `MacBook Pro de Miguel` is 127 characters, 49 columns by 25 rows; with Tailscale's IPv6 as well, 172 characters, 57 by 29; three addresses, port 65535 and a name of 64 characters, 239 characters, 65 by 33. A test keeps that last one within 80 columns. Limit: every character of a name outside ASCII takes 6 to 12 in the code, so a long name of accents or emoji can pass 80 columns; Mac names are short, and the code still does not adapt to the terminal's width.
- **The Mac's name** (P5, `bridge/src/name.rs`): `scutil --get ComputerName`, the name in System Settings › General › Sharing (`MacBook Pro de Miguel`), since it is the one the user recognises. If it fails or is empty, the host name from `uname` without `.local`; with neither, the code has no `name=` and the heading only the networks. The app puts it in `Name`'s place unless the user typed one or another machine already has it (Connection › Machines). Rejected for now: a `--name` option, which can come later without changing the format.
- **`--bridge-routes`** (P3, `bridge/src/server/connection.rs`, `BridgeRoutes` in `crates/core/src/protocol.rs`): an argv of exactly `["--bridge-routes"]` is answered by the bridge itself, before the allowlist, with one `stdout` line `{"routes":[{"host":"192.168.1.20","port":8765},…]}`, the addresses it listens on, and `{"exit":0}`. Nothing runs, and the log says `<peer> asks for its routes`.
  - Only after the token, like any command: a connection without it never gets this far (WebSocket server).
  - The answer has no token: the app gives the new routes the token of the route it is connected through.
  - Anything else that starts with `-`, `--bridge-routes` with an argument included, is still refused by the allowlist with exit 2. So a bridge from before 035 answers `--bridge-routes` with a `stderr` line and exit 2, and the app logs one line and shows nothing.
  - **Why an argv** (P3 a): it changes neither the protocol nor the `Transport` trait; the app asks with `transport::json`, as for any one-shot command. Rejected: a new message, `{"routes": true}`, which changes the strict parser and the transport; a header in the handshake's `101`, which would need the `Transport` to hand out headers.
  - Upstream's `/cli` would need an equivalent for the app to stop needing the bridge (Proposal for upstream, task 033).
- **Turning Tailscale on after the bridge started** needs the bridge restarted, not the code scanned again: the bridge reads its interfaces once (Listening on the network › Addresses that come or change), and once restarted it answers `--bridge-routes` with the new address, which the app adds at its next connection. A `bind` that fails ends the bridge whole, so the code never holds an address nobody listens on.
- **Dependencies**: no `percent-encoding` crate, though it is already in `Cargo.lock` through others: encoding the unreserved set and decoding take a few lines in `code.rs`. `rustix` gains its `system` feature for `uname`, the host name without `unsafe` or `libc`, as for the signals.
