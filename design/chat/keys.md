# Keys

A topic of [Chat](../chat.md): the row behind an icon, which keys and how they go, `Ctrl-C` asking for a second tap, `Esc`, the light tap, a key behind a held send.

- **The row** (`src/routes/agent/KeyRow.svelte`) sits in the composer over the thumbnails and the capsule, under the question, while it is open (Behind an icon), and can be opened while the screen has its row and the agent is not gone, also while it is `waiting` and while a text is sent. It holds `Esc`, `Tab`, `↑`, `↓`, `←`, `→`, `Enter`, `Ctrl-C` and `0–9`, which unfolds the digits. Each button is a name of cornercase's `KEY_NAMES` (`src/lib/keys.ts`, its label, its name for VoiceOver and its key): the keys an agent's menus, permissions and confirmations take, the arrows and `Enter` to move and choose, a digit to choose an option by its number, `Esc` to cancel, `Ctrl-C` to interrupt. `src/lib/keys.ts` holds no markup nor state, so the terminal's row (021) can take its names too.
- **Behind an icon**: the row folds behind `Keys` in the capsule (Lucide's `keyboard`, with `aria-expanded`), and a tap opens or closes it. Its state lives in `Chat` (`keysOpen`, `toggleKeys`), without markup, so it lives on under the terminal and Machines as the rest of the `Chat` does and vitest tests it (`src/lib/chatKeys.test.ts`).
  - **Closed at first, open while the agent asks**: each `Chat` starts with it closed. When the row turns `waiting` (`Chat.see`) it opens on its own, since a key is how a question is answered; when the row leaves `waiting`, it closes on its own only if `waiting` opened it. Opened by hand, for a `Ctrl-C` during `working` say, it stays open; closed by hand during `waiting`, it stays closed until the next `waiting`. Rejected: closing it whenever `waiting` ends, which closes keys the user opened. A `waiting` that comes and goes within a second (Chat › The question › Its limit) opens and closes it with the question; accepted, as it follows `row.status` like the question does.
  - **Closing disarms `Ctrl-C`**: an `Again?` that nobody sees must not stay armed for a later tap.
  - **One tap more for `Ctrl-C`**: the line of no news still says `Ctrl-C interrupts` (Chat › The thread), and the key is now behind the icon. Accepted; rejected for now: that line opening the keys.
- **`0` too**, though the task asked for `1`–`9`: upstream closes Claude Code's survey with `keys --pane N 0` (its `confirming-sends.md`), and `send` refuses a pane with the survey open, so without it the phone could not take it away. The digits go `1` to `9`, then `0`, as on a keyboard.
- **Every key in sight**: buttons of 44 px (Look › Touch and motion), with no more width than their label and the arrows drawn as Lucide icons named `Up`, `Down`, `Left` and `Right`; on a phone 393 px wide the row breaks into a second line rather than scrolling sideways. The digits unfold in a row of their own over the keys, behind a button with `aria-expanded`, and stay open after a digit is sent until that button is tapped again, so `↑` or another number can follow without opening them again. They start folded; the `initialDigits` prop, which only the tests pass, draws them open, since a server render cannot tap. Rejected: one row that scrolls sideways, which hides keys out of sight; the arrows on a fixed line of their own; digits that fold on their own after one is sent.
- **`keys`, not `input`**: each tap queues `keys --pane P <key>` by `Queue::ask`, without standard input (`crates/core/src/cli/keys.rs`, the `keys` command of `src-tauri/src/commands/chat.rs`, which take a list, each key checked against cornercase's names and an empty list refused (`no key to send`), so a chip of the question sends its arrows in one call: The question › The card), on the `requests --follow` the sends go through, so keys and sends reach the agent in the order they were tapped. `keys` is upstream's way to answer an agent (`send` refuses `waiting` with `answer with cornercase keys`), its `enter` counts as submitting a turn, and it answers each key, so a key that fails gets a toast with a send's reasons (Chat › Answering › What comes back), since a key has no bubble, and success shows nothing: the status comes with `agents-changed` and the message with the next read, as after a send. `input` (the typist, Connection › the ordered queue) is someone typing in another window, the terminal's (021), and answers nothing a toast could say. The UI does not wait for a key's answer before sending the next one: `↓ ↓ Enter` keep their order in the queue, which is the order their commands reach `Queue::ask`. Each `invoke` runs as a task of its own on Tauri's multi-threaded runtime, so two within the same instant could swap; taps are tens of ms apart, and a send (Chat › Answering) has the same bound. Rejected: chaining the calls in the UI, each `invoke` waiting for the previous one to be queued, which needs a second command (one that queues, one that waits for the answer) for a race no finger makes.
- **Only the app's keys reach the argv**: the core takes only the 18 names the app sends and refuses any other (empty, `-x`, `shift+tab`) before anything is queued, so a key can never turn into an option of `keys`.
- **`Ctrl-C` asks for a second tap**: the first one sends nothing; it turns the button to the danger tone with `Again?`, its name for VoiceOver turns `Tap again to interrupt`, and a live region says it. A second tap within 3 s sends `ctrl+c` once; after 3 s, or on any other key, it lets go without sending. Two `ctrl+c` in a row quit Claude Code and leave its shell, and the screen turns gone, so one tap must never send it by mistake; a third tap arms it again rather than sending a second one. Rejected: a long press, which WebKit on iOS takes for itself without a click (Look › Touch and motion) and VoiceOver hardly does; a confirmation dialog, one more screen for a key.
  - **Same width, said aloud**: the live region is a `.spoken` span beside the rows, not inside the button: the children of a `button` are presentational and its `aria-label` hides them, so VoiceOver could miss a change there. The button keeps its width when armed: `Ctrl-C` and `Again?` share one grid cell (`.steady`) and only the one in use shows, so the row does not wrap again between the two taps and the second one lands where the first did. Rejected: `Tap again to interrupt` as the visible text, about 120 px wider, which could push `Ctrl-C` to the next line under the finger; a fixed `min-width`, a number to keep in step with the font.
- **`Esc` asks for nothing**: in Claude Code it interrupts an agent that works, as `Ctrl-C` does, but never quits it, and two in a row open its rewind. Accepted: it is the key a menu takes to cancel, and a confirmation would slow every menu down.
- **A light tap**: each tap that sends a key, and the one that arms `Ctrl-C`, asks the haptics plugin for `impactFeedback('light')` (`src/lib/haptics.ts`, Architecture › Dependencies), since what a key does often shows only on the machine. Without the plugin (the desktop, the tests) or when it fails, nothing shows and the key still goes: it is not a failure of what the user did, so there is no toast.
- **Behind a held send** a key waits, as every job behind it does, up to the 30 s of `--timeout 30` (Chat › Answering).
- **Nothing to another pane**: a `Chat` gone, or of another machine, sends no key (Chat › The screen), and its screen shows no row. `keys` has no `--boot` either (Upstream gaps).

## Checked live

- **Keys, on 2026-11-09** in the iPhone 18 Pro simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5, `tauri-plugin-haptics` and `@tauri-apps/plugin-haptics` 2.4.2), against the bridge on the LAN and cornercase 0.13.19, with Claude Code 2.1.319, the taps made by XCUITest. On its screen, 402 px wide, the row takes two lines: `Esc` to `→`, then `Enter`, `Ctrl-C` and `0–9`. A Claude that asked `Which colour?` with `AskUserQuestion` showed `waiting` and its note; `↓` moved its menu from `1. Red` to `2. Green` on the Mac, the queue opening its `requests --follow` with that first key, and `Enter` chose it: the agent answered `You picked Green.` and the screen showed it, done.
- **`Ctrl-C`**: while the agent wrote a long story, the first tap turned the button red with `Tap again to interrupt`, and the second, a second later, interrupted it once: Claude Code showed `Interrupted · What should Claude do instead?` and stayed open, and the header turned idle. One tap alone on the idle agent let go after 3 s, back to `Ctrl-C`, and Claude Code showed no `again to exit`: nothing was sent. The button showed `Tap again to interrupt` then; its `Again?` of the same width and the live region beside the rows came after, and are not checked live yet.
- **Haptics**: the simulator has no Taptic Engine, so only that nothing fails was checked: every tap sent its key, no toast showed, and the app's log held no error of the plugin. Not felt on an iPhone yet, which needs a signing team.
