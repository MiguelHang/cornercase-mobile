# Connection

Follows cornercase-gpui's `design/connection.md`: the command line is the only contract, streams, an ordered queue, one `Store`.

- **Transport behind a trait** (`crates/core/src/transport.rs`): `run(&self, argv, stdin, out) -> BoxFuture<'_, Result<Exit, Error>>`, where `stdin` is a `BoxStream<'static, Stdin>` whose end is the command's end of input, `out` a boxed `Sink<Out, Error = Closed>` that gets the stdout and stderr lines in the order they arrive, and `Exit` the code and the stderr gathered. `--follow` streams and commands that read stdin fit. The bridge is the first implementation; SSH, iroh and Cloudflare come later as new transports, without touching the callers.
  - **Usable as `dyn`, `Send` and `Sync`**: a boxed future, stream and sink rather than a native `async fn` and generics, so task 008 can mix routes of different transports, 012 can keep the winning route's as an `Arc<dyn Transport>`, and the futures run on a multi-threaded runtime. The trait names no runtime: tokio stays inside the bridge transport and the output sink. Rejected: `async fn` in the trait with a generic `Store<T: Transport>` (the whole core generic, and one kind of route at a time); the `async-trait` crate (a dependency for what `futures-util`'s `BoxFuture` already gives).
  - **Input as text or bytes**: `Stdin::Text` is a line, `Stdin::Bytes` raw bytes, for `paste-file -` (task 018). Rejected: lines only, widened by 018, which would change the trait under every transport.
  - **The output sink** has its own unit error, `Closed`, and is built with `sink::unfold` over a tokio `mpsc` sender (no `tokio-util`). A sink that refuses a line means the app no longer listens: the command ends as on a cancel and `run` returns `OutputClosed`, apart from `Dropped`, so the `Store` (012) does not reconnect for something the app did itself.
  - **Cancelling is dropping the future**: it drops the connection, since nothing is spawned that would keep it, and the bridge then ends the command and its group (`design/bridge.md`).
  - **`Exit.stderr` keeps the last 64 KiB**, its lines joined with `\n`, never cutting a character: a `--follow` alive for hours must not grow without bound, and an error message needs only the end; every line also goes to `out` as it comes. Rejected: no limit.
  - **A code other than 0 is not a transport error**: `run` returns it in `Exit`, the bridge's 128 + signal and −1 as they are. On top, `output` gathers the stdout lines joined with `\n` and keeps the code and the stderr apart, and `json` turns a code other than 0 into `Failed` and output that does not parse into `Json`, which names the kind of mistake and its line and column but never the text, since output can hold secrets. `json` adds nothing to the argv: the caller passes `--json`. `output`'s sink drops the stderr lines instead of queueing them, since it keeps only `Exit.stderr`: the 64 KiB bound holds there too.
- **Errors told apart** (`crates/core/src/error.rs`): `Unauthorized` (a 401: the app says the token is wrong, and scanning the QR again fixes it, not retrying), `Rejected` (another HTTP status), `Timeout` (no upgrade within the connect timeout), `Connect` (TCP or the upgrade failed, with the system's reason and never the URL or the token; an error without a system code, which is how a name that does not resolve fails (std's lookup, tokio's empty list), says "the address could not be resolved or reached", since its text may hold the host and its kind alone, "uncategorized error", tells the user nothing), `Dropped` (the connection ended before `exit`, or went silent), `Protocol` (a message that is not one of the bridge's, a binary frame or one over the limits: a bug on one side, not the network) and `OutputClosed`. `Dropped` is one variant for a close, a reset, the end of the stream and the bridge stopping (1001), since 008 and 012 retry the same way in every case; telling 1001 apart can come later without breaking anything. The transport's `Debug` shows only its config, not the URL with its token.
- **No retries in the transport**: it makes one attempt. Retrying, trying another route and reconnecting are for its callers (008, 012), which know whether a command can run twice.
- **The bridge transport** (`transport/bridge.rs`), `ws://` only, without TLS, like the bridge:
  - **Connect timeout of 3 s by default**, configurable, over TCP and the WebSocket upgrade together, so task 008 tries routes fast: an address of another network often never answers rather than refusing.
  - **Nagle off** (`disable_nagle`): input goes as small messages, one per keystroke or line (017, the terminal's `input`), and with Nagle each one that follows an unacknowledged one waits for the other side's delayed ACK, tens to hundreds of ms over Tailscale or LTE. The bridge does not set `nodelay` either, but its output comes in bigger lines.
  - **Frames and messages of up to 7 × 16 MiB**, the bridge's, since a 16 MiB line in JSON is bigger than tungstenite's defaults (`design/bridge.md` › Size of the output).
  - **Input in pieces under 1 MiB**: `Stdin::Bytes` is cut so that each `stdin_base64` message, JSON included, fits the 1 MiB the bridge reads (`LARGEST_MESSAGE`); the command reads the pieces one after the other.
  - **Sending and reading at once**, in the same future, so a command that answers before it has read all its input never blocks the exchange. When `exit` comes first, the rest of the input is dropped. A failed send is not reported on its own: the reading side then meets the close or the reset and decides the error, so a broken connection is always `Dropped`.
  - **Ping and backpressure**: tungstenite answers the bridge's Ping only while it reads, and reading waits while `out` waits. An `out` that stays slow for 45 s gets the connection cut by the bridge, and `run` ends with `Dropped`. Wanted: a client that does not read holds a command and its output (`design/bridge.md` › Ping as a control frame).
  - **Silence timeout of 45 s by default**, configurable, the bridge's own: a half-open connection (the Mac asleep or off the network without a FIN or a RST, a NAT entry that expired) never fails on its own, since the client does not write while it reads and keepalive is off, so a `--follow` would wait forever and the `Store` (012) would stay connected with stale data. The bridge pings every 15 s, so 45 s without any frame (a Ping included) is a dead link, and `run` ends with `Dropped`, which 012 retries. Only the wait for the next frame counts: a slow `out` is the bridge's to cut, as above.
  - **Close after `exit`**: the client answers the bridge's Close and waits for the end of the connection for up to 500 ms, so the bridge sees a normal close and not a broken connection; anything after `exit` is ignored. The result can thus come up to 500 ms after `exit`.
- **`FakeTransport`** (`transport/fake.rs`, only in the core's tests): answers by exact argv with canned lines and a code, a canned error, or a script that gets the input stream and the output sink. An argv it has no answer for fails like a command that is not found, `Failed` with code 127 and `no answer is scripted for [...]` as its stderr, not a panic, so a test names what it forgot. Rejected: an `Unscripted` variant of the real `Error`, dead code outside the tests. It becomes public behind a `test-util` feature only when `src-tauri` needs it, so as not to leave dead code.
- **Tests against the real bridge** (`crates/core/tests/bridge.rs`): the bridge runs inside the test, through its `test-util` helpers, with a fake `cornercase`. They are integration tests and not unit tests: the dev-dependency makes a cycle (core → bridge → core), and in the core's unit tests the bridge's `cornercase-core` would be a second copy whose types do not match. An IPv6 URL (`[::1]`) is not tested: the test server listens on 127.0.0.1 only.
- **Machines with several routes** (`crates/core/src/machines.rs`, `machines/`): a machine is a Mac the phone reaches, with its bridge, saved by the app; not the `machines` of cornercase's `status` (the machines its server links), which the `Store` (012) ignores. Each has routes (phase 0: bridge URLs, e.g. LAN and Tailscale). The first route that answers wins; routes are tried again on a network change and when the app returns to the foreground (012, 013, 028), which is calling `pick_route` again.
  - **A route is an enum tagged by `kind`**, `{"kind": "bridge", "url": "ws://host:port/"}`, so SSH, iroh and Cloudflare come as new variants without changing the file. Only `Bridge` exists today, so that no variant is dead code.
  - **`Route::parse`** takes exactly what the bridge prints, `ws://<host>:<port>/?token=<token>`, with IPv4, IPv6 in brackets or a host name, after trimming the spaces around it (a pasted URL often brings a `\n`). The scheme is matched in any case, and other query parameters are ignored. A URL without a port takes 80, ws's own, since that is what it says; the bridge always prints its port. It refuses, each with its own message: a scheme other than `ws` (it says only `ws://` works, since the bridge has no TLS), a user name or a password before the host (the bridge never prints one, and dropping it without a word would accept a URL that is not the bridge's), an empty host, a port that is not a number from 1 to 65535, a path other than `/` (empty included: the bridge answers 404), no token, an empty one or two of them, a token with characters outside base64url (the bridge compares the text without decoding it, so `=`, `+` or `%2F` never match), and text that is not a URL. No message holds the URL or the token. Parsed with tungstenite's `http::Uri`, already in the core, and a little code of its own for the port and the token. A saved address is read back only in the form the app writes, `ws://host:port/`.
  - **The token is a secret**: it goes to `Secrets` (`crates/core/src/secrets.rs`, key → bytes, `Send + Sync` and synchronous like keyring-core; meant also for 009's seed; the Keychain one is 009's), never to the file, under `route/<machine id>/<address>`. The address is the key, so a machine's routes never repeat one: adding a route at an address it already has replaces its token, which is how scanning the QR again after the bridge's `--new-token` works. `Token` has a redacted `Debug`, no `Display` and no `Serialize`, so neither `Debug`, an error nor the file can show it. Only `Route::parse` makes a token outside the core: `Token::new` and `BridgeUrl`'s fields are `pub(crate)`, so another crate cannot put a token with `&`, `#` or spaces in the URL.
  - **What `Secrets` promises** (and 009's Keychain must keep): a missing key is `Ok(None)` for `get` and `Ok(())` for `delete`, never an error; 009 maps keyring-core's `NoEntry` to them (Identity, below). Otherwise a phone restored from a backup, whose Keychain lacks the tokens, could not load its machines, and removing one would fail after the file had already forgotten it. `MemorySecrets`, the tests' store, behaves the same.
  - **A route whose token is missing is kept**, without a token, and fails in `pick_route` with `NoToken` without touching the network: the app says to scan the bridge's code again, the same remedy as for a wrong token. That is the case of a backup restored on another phone, whose Keychain (`ThisDeviceOnly`, 009) lacks the tokens. Rejected: dropping the route on load, or failing the whole load (what the user set up would be lost).
  - **The file** (`JsonFileStore`, behind the `MachineStore` trait, so 013 picks the path and the tests a temp dir) is `{"version": 1, "next_id", "machines": [...]}`, each machine with its id, name, routes without tokens and `last_route` as an address. A missing file is an empty list. An unknown version or a file that does not parse is `Error::Store` and is never overwritten, since that would lose the machines; what to do then is for the caller (013). Its message names the kind of mistake, its line and column, never the file's text.
  - **Atomic write**: a temporary file in the same folder (`.<name>.tmp`), `sync_all`, then `rename`, so a crash or a failed write leaves the previous file whole; a failed step removes the temporary file. It uses `std::fs` on the runtime's thread: a few KB, not worth a blocking task.
  - **Ids from a counter**, `next_id` in the file, never reused, so a new machine never picks up a deleted one's secrets. Loading raises it past the highest saved id, so a file edited by hand or written by a bug cannot make `add` give an id twice. Rejected: random ids, which would make the tests not deterministic (`getrandom` is in the core since 009, for the identity's seed only).
  - **The order of the writes** (`Machines`, `machines/registry.rs`, over a `MachineStore` and `Secrets`): adding writes the secret before the file, removing the file before the secrets. A failure in between leaves at most an orphan secret, never a saved route without its token. A change is written to a copy of the list first, and kept in memory only once the file is saved, so a failed write spends no id. An id the list lacks is `Error::UnknownMachine` and an address the machine has no route to `Error::UnknownRoute`, not `Store`, which says the disk failed.
  - **The race** (`pick_route`, `machines/pick.rs`): every route with a token runs `contract --json` through `transport::json` in a `FuturesUnordered` (the last winner first, below), within one deadline counted from the start that covers connecting and answering. The first that succeeds wins; the others are dropped, which cancels them, and the bridge ends their `contract` (`design/bridge.md`). It returns the route, its transport and the `contract` JSON, so 010 and 012 do not ask again. When none wins, `AllFailed` holds each route's error in the order of the routes, `Timeout` for those still running at the deadline; a machine without routes fails at once, without the network.
  - **The deadline is 5 s**, above the bridge transport's `connect_timeout` of 3 s, so that a slow network connects and still has time to answer; both are configurable (`PickConfig`, `BridgeConfig`).
  - **The last winner goes first**, with a head start of 300 ms (configurable): the others wait for it to end or for the head start, whichever comes first, so a route that fails at once does not delay them. The LAN answering quickly keeps winning over a slower Tailscale route, and a saved route that has become slow still loses to a fast one. A `last_route` that is no longer among the routes gives no head start. `pick_route` saves nothing: its caller (012) keeps the winner with `Machines::remember`, which writes the file only when it changed.
  - **Success** is the transport without error, code 0 and JSON that parses; `pick_route` does not read it (010 does). An old cornercase without `contract` loses with `Failed` and its stderr, which `contract::outdated` turns into `Outdated` (The contract, below).
  - **`bridge_transports(BridgeConfig)`** is the factory `pick_route` takes for bridge routes: a `BridgeTransport` per route, on its URL with the token.
  - Rejected: `select_ok`, which keeps only the last error; routes one after the other, starting with the last winner (an address of another network that never answers would cost its whole connect timeout); every route at once with the last winner only breaking ties (a fast Tailscale route would take over from the LAN); dropping routes without a token (above).
- **Adding a machine**: scan the bridge's QR code (the official `barcode-scanner` plugin) or paste its URL.
- **Identity** (`crates/core/src/identity.rs`): an Ed25519 key pair the phone makes on its first start, to be reused as its iroh identity. The bridge does not use it: in phase 0 the app only makes it, keeps it and writes its fingerprint to the log (task 009). Android's Keystore comes with 030 and 031.
  - **A seed, not a key**: `Secrets` keeps the 32-byte seed under `identity/ed25519`, the bytes iroh's `SecretKey::from_bytes` takes, so iroh can reuse it as it is. `Identity::load_or_create` reads it, or takes 32 bytes from the system's generator (`getrandom::fill`) and saves them before returning the identity. In the core the seed lives in `Zeroizing` buffers and ed25519-dalek's `SigningKey`, which wipe themselves when dropped; `Identity` has a redacted `Debug`, no `Display` and no `Serialize`, so neither a log nor an error can show it.
  - **`public_key()`** is the public key in base64url without padding, 43 characters in the alphabet of the bridge's token. **The fingerprint** is the key's first 5 bytes in hex, 10 characters, what iroh's `fmt_short` shows, so the log and iroh will agree. Rejected: a SHA-256 of the key (`sha2` for a label) and the first characters of the base64url.
  - **A saved seed that is not 32 bytes** is `Error::Identity`, which names neither its length nor its bytes, and is never overwritten: a new identity made without a word would silently break whatever was paired with the old one, just as a machines file that does not parse is never overwritten. If the system gives no random bytes, it is `Error::Random`, and nothing is saved. A failing `get` or `set` is the store's `Error::Secrets`; a failed `set` returns no identity, so nothing uses a key that was not saved.
  - **On start** (`src-tauri/src/identity.rs`, from Tauri's `setup` hook): one line on stderr, `cornercase-mobile: identity <fingerprint>` or `cornercase-mobile: no identity: <error>`, and the app starts either way. Nothing else runs on start.
  - **No race**: `load_or_create` runs once, on start. Two calls at once on an empty store would each save a seed, the last write would win and the other caller would hold a key that is not saved; whoever keeps the identity later (013) keeps one `Identity` rather than calling it again.
- **`Secrets` in the Keychain** (`src-tauri/src/secrets.rs`, `secrets/ios.rs`): `KeychainSecrets` over keyring-core's `Entry`, with service `dev.usecornercase.mobile` and the `Secrets` key as the account, in apple-native-keyring-store's `protected` store, the data protection keychain (the only one iOS has), local rather than iCloud-synchronized (no `cloud-sync`).
  - **`AfterFirstUnlockThisDeviceOnly`**, the `access-policy` modifier of every entry: readable once the phone has been unlocked after it booted, so the app can still read it if it starts or wakes in the background while the phone is locked, and never moved to another phone, by an encrypted backup or by iCloud. A backup restored on another phone makes a new identity, which is the point, and its routes lack their tokens (`NoToken`, above). Rejected: `WhenUnlocked` and its `ThisDeviceOnly` (the crate's default; unreadable in the background while locked), `AfterFirstUnlock` (moves with an encrypted backup), `RequireUserPresence` (Face ID on every start). A start before the first unlock would fail with the warning; the app does not start in the background today.
  - **The policy is set only when an item is made**: a `set` on an item that exists updates its data and keeps its policy (security-framework 3.7 answers `errSecDuplicateItem` with `SecItemUpdate`). The identity is written once, so it does not matter for it; 008's tokens are rewritten when the bridge's code is scanned again, so changing the policy later means deleting the items first.
  - **The Keychain survives uninstalling the app on iOS**: after a reinstall the identity is the same (good), while 008's route tokens stay behind as orphans, since the machines file goes with the app. Not handled yet.
  - **Errors**: keyring-core's `NoEntry` becomes `Ok(None)` and `Ok(())` (what `Secrets` promises, above); every other error becomes `Error::Secrets` with keyring-core's `Display`, never its `Debug` (`BadEncoding` holds bytes), and `Ambiguous` only says how many items it found.
  - **Other platforms** get the same `KeychainSecrets` over a store that is missing, so every call fails with "no secret store on this platform yet": Android until 030 and 031, and the hosts that run the tests. No dead code and no `cfg` inside the adapter. The adapter and its errors are tested on Linux CI with keyring-core's `mock` store and its error injection; `ios.rs` only builds the store and its modifier, so CI never compiles it, and `cargo clippy -p cornercase-mobile --target aarch64-apple-ios-sim --all-targets` runs locally.
  - **No entitlements**: the simulator reads and writes the data protection keychain without `keychain-access-groups` (no `errSecMissingEntitlement`, -34018), so `project.yml` is unchanged.
  - **Crates**: `keyring-core` 1 and `apple-native-keyring-store` 1 with `protected`, keyring's maintained line, which lets each entry pick its accessibility. Rejected: `keyring` 3.6 with `apple-native` (the older line, with no way to set the accessibility), `keyring` 4.x (no `apple-native` any more), `rand_core`'s `OsRng` (`rand_core` 0.10, the one ed25519-dalek 3 takes, no longer has it, and the seed is 32 bytes `getrandom` gives directly, as for the bridge's token), `tauri-plugin-stronghold` (a password-protected file, not the Keychain) and a Swift plugin over `SecItemAdd` and `SecItemCopyMatching` (the plan B, not needed).
  - **Checked live** on 2026-11-09 in the iPhone 17 simulator (iOS 27.2, Xcode 27.2, macOS 26.6.2, Tauri 2.12.5): the first start makes the identity and logs its fingerprint; `xcrun simctl terminate` and a new launch log the same one, three launches in a row; after `xcrun simctl keychain booted reset` the next start logs a new one, which then holds. On iOS, Tauri sends stderr to the unified log, not to `xcrun simctl launch --console-pty`: the line is read with `xcrun simctl spawn booted log show --last 5m --style compact --predicate 'subsystem == "dev.usecornercase.mobile" AND eventMessage CONTAINS "cornercase-mobile: "'`. Not checked yet: an iPhone (it needs a signing team), and the item's accessibility, which `simctl` does not show.
- **The contract** (`crates/core/src/cli/contract.rs`, `cli/contract/`): what the app needs from the Mac's cornercase is checked against the `contract --json` that `pick_route` already brings back, never against a minimum cornercase version, so a build of upstream `main` works and what is missing is named.
  - **Reading it**: `Descriptor` (`from_value` for `pick_route`'s JSON, `FromStr` for text) takes `version`, `contract`, `boot`, `operations` (`name`, `available`, `reason`), `features` and `streams` (`name`, `version`). A key that is absent takes its default and a key it does not know is ignored, so what upstream adds breaks nothing. A value of the wrong shape is `Json`, which names the kind of mistake, its line and column, never the text (`transport::json_error`, shared rather than copied).
  - **The contract number**: the app knows `CONTRACT = 1`. A higher number is `ContractTooNew { server, app }`, which says to update the app: the old side is the app, and cornercase raises the number only for a change that breaks clients. `contract = 0`, which is also what an absent key reads as, is `Outdated`: every server that has `contract` sends 1 (since cornercase-terminal#283), so a descriptor without it is not one to trust.
  - **`REQUIRED`**: three typed lists, every name checked against cornercase 0.13.19 (`Command::NAMES`, `FEATURES`, `describe`), each entry for the task that uses it.
    - 25 operations: `status`, `watch`, `app`, `events` (012, 015: `status --json`, `status --follow`, `status --app --follow`, `events`); `last-message`, `send` (016: `read --last-message`, `send`); `keys` (017); `paste-file` (018: `paste-file -`); `view`, `surface`, `redraw` (019, 020: `surface --patches`); `input`, `scroll` (021); `view-set` (022: `--claim`, `--inactive`); `start`, `new-workspace` (023, 024); `issue-sources`, `issue-list`, `issue-read` (024: `issue sources`, `list`, `read`); `changes`, `changes-file`, `changes-viewed` (025); `files-list`, `files-read`, `files-search` (026).
    - 7 features: `boot` (010, 012: `boot` and `stale-boot`); `views`, `surface-patches` (019 to 022: the CLI refuses `--view` and `--patches` without them); `machine-start` (023: the CLI refuses `start --placed` without it); `issues` (024: `start --issue`); `changes`, `files` (025, 026: the shape of their answers).
    - 7 streams, each at version 1: `events`, `watch`, `app`, `surface`, `view`, `changes`, `files`. Another version changes the lines that 012, 019, 025 and 026 parse, so a stream that is absent or at another version counts as missing.
    - Left out: `requests --follow` and `input --follow` (011's queue), subcommands of the CLI rather than operations of the socket, so the contract has no name for them (Upstream gaps); 011 falls back to single commands when they do not start. `update-check` and `update-install`, which a dev build of cornercase marks unavailable. The operation that lists the agents cornercase knows, which 023 adds once it picks one.
  - **`missing(descriptor)`** lists what the server lacks, operations then features then streams, each in `REQUIRED`'s order, with its `Kind` and, for an operation the server has but marks unavailable, the server's `reason`. All or nothing for now: 012 stops on any `Missing`, so a server without `files` blocks the whole app though only 026 needs it. `Missing` already names the entry, so degrading screen by screen later is additive.
  - **An old cornercase**: a server without `contract` answers `` has no `contract` command ``, and an older CLI refuses it with clap's `unrecognized subcommand 'contract'`. `outdated` turns a `Failed` whose stderr holds either into `Outdated`, which says to update cornercase on the Mac and restart its server. They are matched as substrings, since the CLI prints the server's text after anyhow's prefix (upstream's own tests do the same), and the text is what tells them apart from the bridge's exit 2 (an argv outside its allowlist), which shares clap's code. Servers older than the JSON requests stay a plain `Failed`.
  - **A CLI and a server of different versions**: `contract` speaks for the server, but the installed CLI parses the flags (`--placed`, `--patches`, `--follow`). An old CLI with a new server fails in that command, with clap's exit 2 and `unexpected argument`, not here. Documented, not solved.
  - **The boot** (`cli/contract/boot.rs`): `Descriptor::boot` gives the server's `Boot` (its pid and start time, not a secret). `BootWatch::observe` says `Same` for the first boot it sees and while it does not change, and `Restarted` once when it changes, for 012 to rebuild the `Store`. The boot is the server's, not the route's: the same Mac reached by another route gives the same boot.
  - **`stale-boot` is exit 4**: a command given a `--boot` that is no longer the server's fails with 4, and `transport::json` maps it to `StaleBoot` with the stderr. Only `stale-boot` uses 4 today (3 is a partial result, 2 a usage error, 126 and 127 come only with `--remote`, which the bridge refuses); if upstream ever reuses 4, this mapping would lie.
  - **The fixtures** (`crates/core/tests/fixtures/contract/`): `0.13.19.json` is `contract --json` from cornercase 0.13.19, the same as upstream `origin/main` at `7f08441f` (124 operations, all available, 42 features, 10 streams); `no-operations.json` is the same without `operations`. The tests of `contract.rs` and of `boot.rs` both read the first through `cli/contract/fixtures.rs`, a module only the tests build, so no test module imports another.
  - Rejected: a minimum version read from `--version`, like cornercase-gpui (a version cannot name what is missing, nor tell what a build of upstream `main` has); one list of names without kinds (an operation and a feature or a stream share names, such as `changes`, `files` and `events`, and a stream needs its version).
- **Input and the actions that must follow it go through one ordered queue** (`crates/core/src/queue.rs`, `queue/`), as in cornercase-gpui: the server does not order requests that come on different connections, so a key followed by a focus or a split could arrive in the wrong order. One worker runs the jobs one after the other, in the order they were queued. `Queue` is a handle that can be cloned and is `Send` and `Sync`; queuing never blocks.
  - **The core starts nothing**: `Queue::new(transport, on_error)` returns the handle and the worker as a future that the caller spawns on its runtime (013; the tests run it on a paused clock), so the core stays without a runtime and tokio gains no feature. Waiting on several things at once uses `futures-util`'s `select`, not tokio's `select!`. Rejected: a `tokio::spawn` in the core, which would need tokio's `rt` and would take the clock out of the tests' hands.
  - **Commands go through one process** (`queue/requests.rs`): `requests --follow -`, started at the first command and kept, one line per command, `{"args": [...]}` or `{"args": [...], "stdin": "…"}`. The next line is written only once the previous one is answered. An answer is read leniently (each field has a default, unknown fields are ignored): with `status` 0 it is what the command printed, in the same shape `transport::output` gives (`json` written back as text, then `text` if there is any), so the parsers of 016 to 025 read both paths the same way. `status` 4 is `StaleBoot`, any other status `Failed` with `error`, or `stderr` when `error` is empty. A line that is not JSON names the kind of mistake, never the text. A failed command does not stop the queue.
  - **Keys go through one process, the typist** (`queue/typist.rs`): `input --follow --json -`, started at the first event and kept, one line per event with its pane added (`{"pane": 14, "key": …}`), so a split does not start a process per pane. Consecutive events are written without waiting, at most 256 without an answer: past that the typist waits for their answers first. Each answer takes off its `events` (1 when absent) from the lines still waiting, since one answer can cover several lines; counting answers would make the wait below time out for nothing. An answer with `error` goes to `on_error` as `InputRejected` ("cornercase input: …") and the queue goes on.
  - **A job waits for the keys before it** (settle): before any job that is not input, and before the worker ends, it reads the typist's answers until every line written is answered, for up to 10 s. When the 10 s run out, `on_error` gets `SettleTimeout`, the typist is dropped (the next event starts another one), the lines left without an answer are not sent again, and the job runs.
  - **Coalescing**: a command queued with a key (`coalesced`, `ask_coalesced`: a drag's selection, a divider, the view's size) only runs as the last of a run of consecutive jobs with the same key. The others never run and their callers get `Outcome::Skipped`, with no warning. Rejected: dropping their replies, as cornercase-gpui does, since the caller would then read it as a lost answer.
  - **Scrolls add up**: consecutive `scroll` jobs for the same pane go as one `scroll --pane P --up N` or `--down N` with their net sum, and nothing at all when it is 0, so a trackpad costs one command per answer, not one per wheel event. They go through `requests`, not the typist, since `input` cannot move the view.
  - **Nothing is reordered**: a job of another kind, another key or another pane ends a run and stays where it was, to run next.
  - **Bytes go one-shot**: a command with `Stdin::Bytes` (`paste-file … -`, a pasted image, 018) takes its turn in the queue, after the keys before it, but runs as its own `Transport::run` with the bytes on standard input (the transport cuts them into `stdin_base64` messages and ends with `eof`), since a `requests` line's `stdin` is text (Upstream gaps).
  - **When a process cannot be used, the job goes one-shot**: a command runs as its own `Transport::run` with its argv and stdin, and events as one `input --pane P --json -` per run of events for the same pane, without the `pane` field. The next job of its kind starts the process again. That covers a process that could not connect (`Unauthorized`, `Rejected`, `Timeout`, `Connect`), whose lines never left, and one that had already ended. So typing and commands never depend on `--follow`.
  - **A CLI without them** (older than `requests` or `input --follow`) refuses the subcommand at once. Through the bridge there is no signal that a command started, so a process that ends before any answer, with exit 2 and clap's `unrecognized subcommand 'requests'` or `unexpected argument '--follow'`, counts as absent: its job runs one-shot, since it never ran, and the process is not tried again until `reconnect`. Rejected: treating it as a lost answer, which would fail every command on an older Mac.
  - **A line written and left without an answer is lost**: when a process ends after it wrote a line, the command's caller (or `on_error`, when nobody waits) gets `Unanswered`, "the command may have run but its answer was lost", and the line is never sent again, since it may have run. The next job starts a new process. Rejected: reusing `Dropped` or `Timeout`, which tell the app to retry or say the bridge did not answer, where the app must say the command may have been sent.
  - **The worker watches both processes while idle**: it waits for the next job or the end of either process, so their `Transport::run` futures keep being polled. The bridge transport reads the WebSocket only while polled: without it, it would not see the bridge's pings within its 45 s silence timeout, and a link that dropped while idle would only show at the next job. An end that `reconnect` or dropping the queue did not cause goes to `on_error` with the last line the process wrote on stderr, or the transport's error, so that keys or commands that may not have run are known.
  - **`reconnect(transport)`** (012 calls it after a restart or on a new route): it sends a signal on a channel of its own, which interrupts the job in progress even while it waits for an answer, and a fence in the job queue. The caller of the command in progress gets `Unanswered`, since it may have run. The commands queued before the fence get `Skipped`, and the keys and scrolls queued before it are discarded: after a restart the panes' ids may point at other panes. Both processes are dropped without a warning; dropping their futures makes the bridge end the commands. The jobs queued after the fence run on the new transport, which starts both processes again and tries again a process the old CLI lacked. Rejected: keeping the jobs that were waiting (an id from the old server could reach another pane), or keeping them only when `boot` did not change (012 would have to tell, for little gain).
  - **`on_error`** (`Fn(Error)`, `Send` and `Sync`) gets what no caller waits for: a failed `run`, `coalesced` or `scroll`, a failure whose caller dropped the future of its `ask`, a failed one-shot `input`, the typist's `error`, the unexpected end of either process, and `SettleTimeout`. No message holds the typed text or a command's standard input. A caller that waits (`ask`) gets `Outcome::Done` with what was printed, `Outcome::Skipped`, or the error.
  - **Dropping the last handle** ends the worker once it has run the jobs it holds and settled, and both processes with it.
  - Rejected: one connection per action (a round trip and a connection for each key over LTE), not waiting for answers (a key followed by ⌘T could reach the new tab), one `input --follow` per pane, commands with bytes through `requests` (its `stdin` is text), and the reads that order nothing (`read`, `changes`, `files`) or that only wait (closing agents, removing a worktree) through the queue: they stay one-shot `transport::output` and `json`, beside it, so a slow read never holds a key.
  - **Events are opaque**: an input event is a `serde_json::Value` object, as in cornercase-gpui, until 017 and 021 make keys. Rejected: an event type in the core now, which nothing would use yet.
  - Not checked live yet: nothing uses the queue until 013; it is tested with `FakeTransport` only, on a paused clock.
