# Connection

Follows cornercase-gpui's `design/connection.md`: the command line is the only contract, streams, an ordered queue, one `Store`.

Topics, in `design/connection/`:

- [Store](connection/store.md) (`crates/core/src/store.rs`, `store/`, `src-tauri/src/state.rs`, `events.rs`, `lifecycle.rs`): one per machine, its three streams and why `watch` and not `view`, its states (`Offline` included), the backoff, `resume_now` and the other reasons to wake it, what a restart empties, the queue inside its driver, the channel of changes, the fixtures; in the app, one for the active machine, its changes as events, the return to the foreground and what was checked live.
- [Network](connection/network.md) (`src-tauri/plugins/network/`, `crates/core/src/network.rs`, `src-tauri/src/network.rs`): the iOS plugin over `NWPathMonitor` and the Android one over `ConnectivityManager` (what counts as a change there), the 1 s debounce and the baseline, `Offline`, why a network change interrupts an attempt, Tailscale, false `none`, what was and was not checked live, plans B and C.
- [The connection bar](connection/bar.md) (`src/lib/ui/ConnectionBar.svelte`, `src/lib/connection.ts`): text, tone and pulse per state, the countdown.
- [Machines](connection/machines.md) (`crates/core/src/machines/same.rs`, `machines/pairing.rs`, `src-tauri/src/commands/routes.rs`, `probe.rs`, `src/lib/machineForm.ts`, `addMachine.svelte.ts`, `src/lib/scanner.svelte.ts`, `probes.svelte.ts`): adding a machine and its form, the scanner, one code per machine, pairing with cornercase's code and the orphan row it can leave on the Mac, the same machine, learned routes, which route wins, names, routes of the active machine, the active one remembered, switching, trying the others.
- [Identity and secrets](connection/identity.md) (`crates/core/src/identity.rs`, `crates/core/src/secrets/`, `src-tauri/src/secrets.rs`, `secrets/`, `src-tauri/src/identity.rs`, `src-tauri/plugins/secrets/`): the identity and its seed, two stores loaded apart, the Keychain on iOS and its accessibility, the Keystore on Android and why an encrypted seed, the same promises over the plugin, a secret that no longer opens, moving 030's route tokens from their file into the Keystore, the device's secret from cornercase.
- [The contract](connection/contract.md) (`crates/core/src/cli/contract.rs`, `cli/contract/`): what the app needs from cornercase, checked against `contract --json` and not a version, `REQUIRED` and what it leaves out, the version that brings a name, an old cornercase, a CLI and a server of different versions, the boot, `stale-boot`, the fixtures.

- **Transport behind a trait** (`crates/core/src/transport.rs`): `run(&self, argv, stdin, out) -> BoxFuture<'_, Result<Exit, Error>>`, where `stdin` is a `BoxStream<'static, Stdin>` whose end is the command's end of input, `out` a boxed `Sink<Out, Error = Closed>` that gets the stdout and stderr lines in the order they arrive, and `Exit` the code and the stderr gathered. `--follow` streams and commands that read stdin fit. The WebSocket transport to cornercase's `/cli` is the first implementation; SSH, iroh and Cloudflare come later as new transports, without touching the callers.
  - **Usable as `dyn`, `Send` and `Sync`**: a boxed future, stream and sink rather than a native `async fn` and generics, so task 008 can mix routes of different transports, 012 can keep the winning route's as an `Arc<dyn Transport>`, and the futures run on a multi-threaded runtime. The trait names no runtime: tokio stays inside the WebSocket transport and the output sink. Rejected: `async fn` in the trait with a generic `Store<T: Transport>` (the whole core generic, and one kind of route at a time); the `async-trait` crate (a dependency for what `futures-util`'s `BoxFuture` already gives).
  - **Input as text or bytes**: `Stdin::Text` is a line, `Stdin::Bytes` raw bytes, for `paste-file -` (task 018). Rejected: lines only, widened by 018, which would change the trait under every transport.
  - **The output sink** has its own unit error, `Closed`, and is built with `sink::unfold` over a tokio `mpsc` sender (no `tokio-util`). A sink that refuses a line means the app no longer listens: the command ends as on a cancel and `run` returns `OutputClosed`, apart from `Dropped`, so the `Store` (012) does not reconnect for something the app did itself.
  - **Cancelling is dropping the future**: it drops the connection, since nothing is spawned that would keep it, and cornercase then ends the command and its group (upstream's `design/phone-app.md`).
  - **`Exit.stderr` keeps the last 64 KiB**, its lines joined with `\n`, never cutting a character: a `--follow` alive for hours must not grow without bound, and an error message needs only the end; every line also goes to `out` as it comes. Rejected: no limit.
  - **A code other than 0 is not a transport error**: `run` returns it in `Exit`, cornercase's 128 + signal and −1 as they are. On top, `output` gathers the stdout lines joined with `\n` and keeps the code and the stderr apart, and `json` turns a code other than 0 into `Failed` and output that does not parse into `Json`, which names the kind of mistake and its line and column but never the text, since output can hold secrets. `json` adds nothing to the argv: the caller passes `--json`. `output`'s sink drops the stderr lines instead of queueing them, since it keeps only `Exit.stderr`: the 64 KiB bound holds there too.
- **Errors told apart** (`crates/core/src/error.rs`): `NotPaired` (a 403 on cornercase's `/cli`: the Mac forgot the phone, in Settings or with `config remove app.<id>`, and only pairing again fixes it, so it is told apart from `Rejected` and never retried), `Rejected` (another HTTP status, a `401` included: only the bridge answered one, and with it gone (059) so did `Unauthorized` and everything that showed it, so a `401` now reads as any refusal of the server), `Timeout` (no upgrade within the connect timeout), `Connect` (TCP or the upgrade failed, with the system's reason and never the URL or the token; an error without a system code, which is how a name that does not resolve fails (std's lookup, tokio's empty list), says "the address could not be resolved or reached", since its text may hold the host and its kind alone, "uncategorized error", tells the user nothing), `Dropped` (the connection ended before `exit`, or went silent), `Protocol` (a message that is not one of the protocol's, a binary frame or one over the limits: a bug on one side, not the network) and `OutputClosed`. `Dropped` is one variant for a close, a reset, the end of the stream and cornercase stopping (1001), since 008 and 012 retry the same way in every case; telling 1001 apart can come later without breaking anything. The transport's `Debug` shows only its config, not the URL with its token. Pairing has errors of its own (Machines › Pairing with cornercase's code). The texts of `Rejected`, `Timeout`, `Connect`, `Dropped` and `Protocol` say "the Mac" (058, CA9), and none names the bridge.
- **No retries in the transport**: it makes one attempt. Retrying, trying another route and reconnecting are for its callers (008, 012), which know whether a command can run twice.
- **The WebSocket transport** (`transport/websocket.rs`), `ws://` only, without TLS, like cornercase's `/cli`:
  - **Connect timeout of 3 s by default**, configurable, over TCP and the WebSocket upgrade together, so task 008 tries routes fast: an address of another network often never answers rather than refusing.
  - **Nagle off** (`disable_nagle`): input goes as small messages, one per keystroke or line (the chat's `keys`, a `requests` line per tap, 017; the terminal's `input`, 021), and with Nagle each one that follows an unacknowledged one waits for the other side's delayed ACK, tens to hundreds of ms over Tailscale or LTE.
  - **Frames and messages of up to 7 × 16 MiB**, the server's: a line is 16 MiB at most, and its message can take about six times that, since JSON escapes a control byte as `\u00XX`, which passes tungstenite's defaults of 16 MiB a frame and 64 MiB a message (`LONGEST_LINE` in `protocol.rs`; upstream's `design/phone-app.md` › Limits and backpressure).
  - **Input in pieces under 1 MiB**: `Stdin::Bytes` is cut so that each `stdin_base64` message, JSON included, fits the 1 MiB `/cli` reads (`LARGEST_MESSAGE`); the command reads the pieces one after the other.
  - **Sending and reading at once**, in the same future, so a command that answers before it has read all its input never blocks the exchange. When `exit` comes first, the rest of the input is dropped. A failed send is not reported on its own: the reading side then meets the close or the reset and decides the error, so a broken connection is always `Dropped`.
  - **Ping and backpressure**: tungstenite answers the server's Ping only while it reads, and reading waits while `out` waits. An `out` that stays slow for 45 s gets the connection cut by the server, and `run` ends with `Dropped`. Wanted: a client that does not read holds a command and its output. Why a WebSocket Ping and not a message of the protocol is in Bridge.
  - **Silence timeout of 45 s by default**, configurable, the server's own: a half-open connection (the Mac asleep or off the network without a FIN or a RST, a NAT entry that expired) never fails on its own, since the client does not write while it reads and keepalive is off, so a `--follow` would wait forever and the `Store` (012) would stay connected with stale data. cornercase pings every 15 s, so 45 s without any frame (a Ping included) is a dead link, and `run` ends with `Dropped`, which 012 retries. Only the wait for the next frame counts: a slow `out` is the server's to cut, as above.
  - **The secret in a header** (058): a route opens `ws://host:port/cli` with `Authorization: Bearer <id>.<secret>`, never in the URL, so neither the address the bar shows nor a log can hold it. cornercase serves the bridge's protocol byte for byte, with its limits, ping and 1001 (upstream's `design/phone-app.md`), so from 058 to 059 one transport served both kinds of route, taking a URL plus headers, and with the bridge gone it serves the one. Rejected (058): a second transport for `/cli`, a copy of the first. A secret that cannot go in a header, which a validated one always can, so only a broken Keychain gives it, is `Secrets` and not `NotPaired`, which would say the Mac forgot the phone.
  - **`ws://` in clear** (058): on the LAN the secret crosses the Wi-Fi in clear, the same risk the bridge's token had; over Tailscale WireGuard encrypts it. Accepted because upstream serves no TLS either: a self-signed certificate with its fingerprint in the code, which the app would pin without a CA, is left for later on both sides (Upstream gaps).
  - **Close after `exit`**: the client answers the server's Close and waits for the end of the connection for up to 500 ms, so the server sees a normal close and not a broken connection; anything after `exit` is ignored. The result can thus come up to 500 ms after `exit`.
- **`FakeTransport`** (`transport/fake.rs`, for tests only): answers by exact argv with canned lines and a code, a canned error, or a script that gets the input stream and the output sink. An argv it has no answer for fails like a command that is not found, `Failed` with code 127 and `no answer is scripted for [...]` as its stderr, not a panic, so a test names what it forgot. Rejected: an `Unscripted` variant of the real `Error`, dead code outside the tests. It is public behind the core's `test-util` feature, for `src-tauri`'s tests (013).
- **Tests against a fake `/cli`** (`transport/fake/cli.rs`, `crates/core/tests/cli.rs`, 059): a WebSocket server on `127.0.0.1:0`, public behind the core's `test-util`, that refuses with `404` a handshake on a path other than `/cli` and with `403` one whose `Authorization` is not the test's secret, as `/cli` does, and hands each connection to the test's script: `heard` reads the client's messages up to `eof`, `request` decodes them into the argv and the input, `say` answers with protocol messages, `closed_cleanly` tells a close from a reset. The transport's unit tests and the integration tests (`run` and `pick_route` end to end, a secret it does not know giving `NotPaired`) share it. Until 059 the integration tests ran the bridge inside the test with a fake `cornercase`, which made a dev-dependency cycle (core → bridge → core) and so could not be unit tests. Rejected: keeping a copy of the bridge's server in the tests, more code than the scripts need and nothing of `/cli`'s own. An IPv6 URL (`[::1]`) is not tested: the fake listens on 127.0.0.1 only.
- **Machines with several routes** (`crates/core/src/machines.rs`, `machines/`): a machine is a Mac the phone reaches, through cornercase's `/cli`, saved by the app; not the `machines` of cornercase's `status` (the machines its server links), which the `Store` (012) ignores. Each has routes, one per address of the Mac, LAN and Tailscale: cornercase's since 058, the bridge's before, and both kinds in one machine from 058 to 059. The best kind of route that answers wins (the LAN, then Tailscale, then the rest; The race, below); routes are tried again on a network change (Network) and when the app returns to the foreground (012, 013), which is calling `pick_route` again.
  - **A route is an enum tagged by `kind`**, `{"kind": "cli", "url": "ws://host:port/"}`, cornercase's own server, to whose address the transport adds `/cli`; SSH, iroh and Cloudflare come as new variants without changing the file. `Cli` is the only variant since 059, which removed `Bridge` (`{"kind": "bridge", …}`, the first one) without touching it: the reason 058 made it a variant of its own rather than `Bridge` with a flag (P1). The format stays at version 1: an app older than 058 fails to load a file with a `cli` route (`Error::Store`, never overwritten, below), accepted since none was published, and a file written before 059 with a `bridge` route fails to load the same way, accepted since only development phones held one (Bridge › Retired in 059).
  - **Routes come from cornercase's code** (`MachineCode::parse`, Machines › Pairing with cornercase's code): the app makes no route from a URL of its own. Until 059 `Route::parse` read a URL of one bridge route, `ws://<host>:<port>/?token=<token>`, whose checks of the scheme, the user name, the host, the port and the path the code's parser shared and keeps, each with its own message and none holding the code or the secret. A saved address is read back only in the form the app writes, `ws://host:port/`.
  - **The token is a secret**, and so is cornercase's, `<id>.<64 hex>`, a `Token` too (it accepts the `.`) under the same key: it goes to `Secrets` (`crates/core/src/secrets.rs`, key → bytes, `Send + Sync` and synchronous like keyring-core; meant also for 009's seed; the Keychain one is 009's), never to the file, under `route/<machine id>/<address>`. The address is the key, so a machine's routes never repeat one: adding a route at an address it already has replaces its token, which is how pairing again replaces a secret. `Token` has a redacted `Debug`, no `Display` and no `Serialize`, so neither `Debug`, an error nor the file can show it. Only the core makes a token (`Token::new` and `RouteUrl`'s fields are `pub(crate)`), from a code it parsed or a secret it was given in pairing; `Token::fake` is for tests.
  - **What `Secrets` promises** (and 009's Keychain must keep): a missing key is `Ok(None)` for `get` and `Ok(())` for `delete`, never an error; 009 maps keyring-core's `NoEntry` to them, and 031's Keystore keeps them too (Identity and secrets). Otherwise a phone restored from a backup, whose Keychain lacks the tokens, could not load its machines, and removing one would fail after the file had already forgotten it. `MemorySecrets`, the tests' store, behaves the same.
  - **A route whose token is missing is kept**, without a token, and fails in `pick_route` with `NoToken` without touching the network: the app says to scan the Mac's code again, the same remedy as for a Mac that forgot the phone, and the `Store` stops as `NotPaired` when no route has one (Store › States). That is the case of a backup restored on another phone, whose Keychain (`ThisDeviceOnly`, 009) lacks the tokens. Rejected: dropping the route on load, or failing the whole load (what the user set up would be lost).
  - **The file** (`JsonFileStore`, behind the `MachineStore` trait, so the app picks the path, `machines.json` in Tauri's `app_data_dir`, and the tests a temp dir) is `{"version": 1, "next_id", "machines": [...]}`, each machine with its id, name, routes without tokens and `last_route` as an address. A missing file is an empty list. An unknown version or a file that does not parse is `Error::Store` and is never overwritten, since that would lose the machines. The app then starts without machines, like when a Keychain read fails while loading: every command that needs them answers `machines_not_loaded` with the reason, which the UI shows from `machines_list` on mount, and nothing writes the file, so a fixed file loads at the next start; with no data folder they answer `no_data_dir`. Its message names the kind of mistake, its line and column, never the file's text.
  - **Atomic write** (`crates/core/src/files.rs`, shared with `FileSecrets`, which held Android's tokens in 030: Identity and secrets): a temporary file in the same folder (`.<name>.tmp`), `sync_all`, then `rename`, so a crash or a failed write leaves the previous file whole; a failed step removes the temporary file. It returns an `io::Error`, which each caller turns into its own variant (`Store`, `Secrets`). It uses `std::fs` on the runtime's thread: a few KB, not worth a blocking task.
  - **Ids from a counter**, `next_id` in the file, never reused, so a new machine never picks up a deleted one's secrets. Loading raises it past the highest saved id, so a file edited by hand or written by a bug cannot make `add` give an id twice. Rejected: random ids, which would make the tests not deterministic (`getrandom` is in the core since 009, for the identity's seed only).
  - **The order of the writes** (`Machines`, `machines/registry.rs`, over a `MachineStore` and `Secrets`): adding writes the secret before the file, removing the file before the secrets. A failure in between leaves at most an orphan secret, never a saved route without its token. A change is written to a copy of the list first, and kept in memory only once the file is saved, so a failed write spends no id. An id the list lacks is `Error::UnknownMachine` and an address the machine has no route to `Error::UnknownRoute`, not `Store`, which says the disk failed.
  - **The race** (`pick_route`, `machines/pick.rs`): every route with a token runs `contract --json` through `transport::json` in a `FuturesUnordered`, all at once, within one deadline counted from the start that covers connecting and answering. The best kind of route that succeeds wins (below); the others are dropped, those that answered and lost too, which cancels them, and cornercase ends their `contract`. It returns the route, its transport and the `contract` JSON, so 010 and 012 do not ask again. When none wins, `AllFailed` holds each route's error in the order of the routes, `Timeout` for those still running at the deadline; a machine without routes fails at once, without the network.
  - **The deadline is 5 s**, above the WebSocket transport's `connect_timeout` of 3 s, so that a slow network connects and still has time to answer; both are configurable (`PickConfig`, `SocketConfig`).
  - **The LAN first, then Tailscale, then the rest** (046): a route's kind comes from its address (`machines::reach`). The LAN is a private IPv4 (`10/8`, `172.16/12`, `192.168/16`, the ranges cornercase listens on), Tailscale is `100.64/10` and `fd7a:115c:a1e0::/48` (CGNAT counts as Tailscale, as in cornercase), and the rest is everything else: host names (MagicDNS ones too, since cornercase announces addresses only), loopback, other IPv6, public addresses. A LAN route wins as soon as it answers. When the first to answer is of another kind, the race waits a window of 150 ms (configurable, `PickConfig::window`) from that answer for routes of a better kind; at its end the best kind that answered wins, and within a kind the first to answer. The window ends sooner when no route of a better kind is still running (they all failed, or there were none), so Tailscale alone, or a LAN refused at once, waits nothing; and it never passes the deadline. A `10/8` VPN or a VM's `192.168.64/24` counts as LAN too: it only wins if it is cornercase with the phone's secret, and costs the window only when it hangs.
  - **Why 150 ms**: on the same Wi-Fi the LAN and a direct Tailscale route answer tens of ms apart, so the window catches the LAN. Away from home the LAN route usually hangs until the connect timeout, so every race there waits the whole window before Tailscale wins. A race runs only on a network change, the return to the foreground or a retry, so that is 150 ms each time.
  - **No lead for the last winner** (046): until 046 the last winner started alone, with 300 ms of lead over the others, so that a route that kept working was not dropped for one a little faster and the connection did not bounce between two routes at every race. What it cost (029, on the user's iPhone on 2026-11-10): on the home Wi-Fi the bar said `via [fd7a:115c:a1e0::…]`. Once Tailscale had won, away from home or in a race where it answered first, it answered within its lead at every race after, and the LAN never got back. A preference by kind keeps the connection as steady, as the same kind wins at every race, without sticking to the wrong route. `last_route` is still saved, for the machine's screen, and no longer decides: `pick_route` saves nothing and reads no last winner, and 013 saves the winner with `Machines::remember`, which writes the file only when it changed, once the `Store` says `Connected { route }` (Store).
  - **Success** is the transport without error, code 0 and JSON that parses; `pick_route` does not read it (010 does). An old cornercase without `contract` loses with `Failed` and its stderr, which `contract::outdated` turns into `Outdated` (Connection › The contract).
  - **`websocket_transports(SocketConfig)`** is the factory `pick_route` takes: a `WebSocketTransport` per route, on its `/cli` with its secret in `Authorization: Bearer`, where a `403` is `NotPaired`.
  - Rejected: `select_ok`, which keeps only the last error; routes one after the other, starting with the last winner (an address of another network that never answers would cost its whole connect timeout); keeping the lead only when the last winner is of the best kind the machine has, or keeping it with the window on top (more code for what the kinds already settle, and a LAN that hangs would hold Tailscale back by the lead after leaving the Wi-Fi); counting the window from the start of the race (a LAN answering at 200 ms would lose to Tailscale at 190); dropping routes without a token (above).
- **Adding a machine**, from cornercase's code (058), scanned or pasted, one per Mac (035): the form, its checks and what follows are in Machines › Adding a machine.
- **Input and the actions that must follow it go through one ordered queue** (`crates/core/src/queue.rs`, `queue/`), as in cornercase-gpui: the server does not order requests that come on different connections, so a key followed by a focus or a split could arrive in the wrong order. One worker runs the jobs one after the other, in the order they were queued. `Queue` is a handle that can be cloned and is `Send` and `Sync`; queuing never blocks.
  - **The core starts nothing**: `Queue::new(transport, on_error)` returns the handle and the worker as a future that the caller polls (the `Store`'s driver, Store; the tests run it on a paused clock), so the core stays without a runtime and tokio gains no feature. Waiting on several things at once uses `futures-util`'s `select`, not tokio's `select!`. Rejected: a `tokio::spawn` in the core, which would need tokio's `rt` and would take the clock out of the tests' hands.
  - **Commands go through one process** (`queue/requests.rs`): `requests --follow -`, started at the first command and kept, one line per command, `{"args": [...]}` or `{"args": [...], "stdin": "…"}`. The next line is written only once the previous one is answered. An answer is read leniently (each field has a default, unknown fields are ignored): with `status` 0 it is what the command printed, in the same shape `transport::output` gives (`json` written back as text, then `text` if there is any), so the parsers of 016 to 025 read both paths the same way. `status` 4 is `StaleBoot`, any other status `Failed` with `error`, or `stderr` when `error` is empty. A line that is not JSON names the kind of mistake, never the text. A failed command does not stop the queue.
  - **Input events go through one process, the typist** (`queue/typist.rs`): `input --follow --json -`, started at the first event and kept, one line per event with its pane added (`{"pane": 14, "key": …}`), so a split does not start a process per pane. Consecutive events are written without waiting, at most 256 without an answer: past that the typist waits for their answers first. Each answer takes off its `events` (1 when absent) from the lines still waiting, since one answer can cover several lines; counting answers would make the wait below time out for nothing. An answer with `error` goes to `on_error` as `InputRejected` ("cornercase input: …") and the queue goes on. It carries the terminal's typing (021); the chat's keys are `keys` commands on `requests` (017, Chat › Keys).
  - **A job waits for the keys before it** (settle): before any job that is not input, and before the worker ends, it reads the typist's answers until every line written is answered, for up to 10 s. When the 10 s run out, `on_error` gets `SettleTimeout`, the typist is dropped (the next event starts another one), the lines left without an answer are not sent again, and the job runs.
  - **Coalescing**: a command queued with a key (`coalesced`, `ask_coalesced`: a drag's selection, a divider, the view's size) only runs as the last of a run of consecutive jobs with the same key. The others never run and their callers get `Outcome::Skipped`, with no warning. Rejected: dropping their replies, as cornercase-gpui does, since the caller would then read it as a lost answer.
  - **Scrolls add up**: consecutive `scroll` jobs for the same pane go as one `scroll --pane P --up N` or `--down N` with their net sum, and nothing at all when it is 0 (`rows_up` positive scrolls up, into the history, and negative down; the socket's `scroll` request counts `lines` the other way round), so a trackpad costs one command per answer, not one per wheel event. They go through `requests`, not the typist, since `input` cannot move the view.
  - **Nothing is reordered**: a job of another kind, another key or another pane ends a run and stays where it was, to run next.
  - **Bytes go one-shot**: a command with `Stdin::Bytes` (`paste-file … -`, a pasted image, 018) takes its turn in the queue, after the keys before it, but runs as its own `Transport::run` with the bytes on standard input (the transport cuts them into `stdin_base64` messages and ends with `eof`), since a `requests` line's `stdin` is text (Upstream gaps).
  - **When a process cannot be used, the job goes one-shot**: a command runs as its own `Transport::run` with its argv and stdin, and events as one `input --pane P --json -` per run of events for the same pane, without the `pane` field; a refused one-shot `input` exits with 1 and its `Error: …` line reaches `on_error` as `Failed`, as any command's. The next job of its kind starts the process again. That covers a process that could not connect (`NotPaired`, `Rejected`, `Timeout`, `Connect`), whose lines never left, and one that had already ended. So typing and commands never depend on `--follow`. Rejected: reading the one-shot's output as the typist's answers, since without `--follow` `input --json` prints one pretty-printed answer over several lines, not a line per event, and each of those lines would reach `on_error` as a refusal.
  - **A CLI without them** (older than `requests` or `input --follow`) refuses the subcommand at once. Over `/cli` there is no signal that a command started, so a process that ends before any answer, with exit 2 and clap's `unrecognized subcommand 'requests'` or `unexpected argument '--follow'`, counts as absent: its job runs one-shot, since it never ran, and the process is not tried again until `reconnect`. Rejected: treating it as a lost answer, which would fail every command on an older Mac; and any exit 2 before an answer, since `/cli` also ends with 2 a command that already ran when a line of its output passes 16 MiB, which would then run again and turn the process off until `reconnect`. `REQUIRED` asks for 0.13.78, which has both subcommands, so this path is for a CLI and a server of different versions (The contract). Until 059 the bridge's `… is not allowed through the bridge` counted as absent too: its allowlist refused the argv, so nothing ran.
  - **A line written and left without an answer is lost**: when a process ends after it wrote a line, the command's caller (or `on_error`, when nobody waits) gets `Unanswered`, "the command may have run but its answer was lost", and the line is never sent again, since it may have run. Why the process ended (the last line it wrote on stderr, such as `no cornercase server is running`, or the transport's error) goes to `on_error` as well, also when it ended before its first answer, so the app can say why. The next job starts a new process. Rejected: reusing `Dropped` or `Timeout`, which tell the app to retry or say the Mac did not answer, where the app must say the command may have been sent.
  - **The worker watches both processes while idle**: it waits for the next job or the end of either process, so their `Transport::run` futures keep being polled. The WebSocket transport reads the socket only while polled: without it, it would not see the server's pings within its 45 s silence timeout, and a link that dropped while idle would only show at the next job. An end that `reconnect` or dropping the queue did not cause goes to `on_error` with the last line the process wrote on stderr, or the transport's error, so that keys or commands that may not have run are known.
  - **`reconnect(transport)`** (the `Store` calls it on every connection after its first: a new route, a restart, a `resume_now`; Store): it sends a signal on a channel of its own, which interrupts the job in progress even while it waits for an answer, and a fence in the job queue. The caller of the command in progress gets `Unanswered`, since it may have run, or `Skipped` while it still waited for the keys before it to be answered, since its line was not written yet. The commands queued before the fence get `Skipped`, and the keys and scrolls queued before it are discarded: after a restart the panes' ids may point at other panes. Both processes are dropped without a warning; dropping their futures makes cornercase end the commands. The jobs queued after the fence run on the new transport, which starts both processes again and tries again a process the old CLI lacked. Rejected: keeping the jobs that were waiting (an id from the old server could reach another pane), or keeping them only when `boot` did not change (012 would have to tell, for little gain).
  - **`on_error`** (`Fn(Error)`, `Send` and `Sync`) gets what no caller waits for: a failed `run`, `coalesced` or `scroll`, a failure whose caller dropped the future of its `ask`, a failed one-shot `input`, the typist's `error`, the unexpected end of either process, and `SettleTimeout`. No message holds the typed text or a command's standard input. A caller that waits (`ask`) gets `Outcome::Done` with what was printed, `Outcome::Skipped`, or the error.
  - **Dropping the last handle** ends the worker once it has run the jobs it holds and settled, and both processes with it.
  - Rejected: one connection per action (a round trip and a connection for each key over LTE), not waiting for answers (a key followed by ⌘T could reach the new tab), one `input --follow` per pane, commands with bytes through `requests` (its `stdin` is text), and the reads that order nothing (`read`, `changes`, `files`) or that only wait (closing agents, removing a worktree) through the queue: they stay one-shot `transport::output` and `json`, beside it, so a slow read never holds a key.
  - **Events are opaque**: an input event is a `serde_json::Value` object, as in cornercase-gpui, until 021 makes them from the terminal's keys; the chat's keys (017) are commands, not events. Rejected: an event type in the core now, which nothing would use yet.
