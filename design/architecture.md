# Architecture

Topics, in `design/architecture/`:

- [Android](architecture/android.md) (`src-tauri/gen/android/`, `src-tauri/tauri.conf.json` › `bundle.android`): the Gradle project as `android init` wrote it, `MainActivity.kt` and the keyboard's insets, and what stays out of git, the `applicationId`, why `minSdk` 24, the permissions, cleartext only to `localhost` and `ts.net` and why no IP ranges, no backups, the Keystore (one AES key, the secrets sealed in the preferences, no `setUnlockedDeviceRequired`, StrongBox nor biometrics, a lost key), Vite through `adb reverse`, how the emulator reaches the bridge, the versions, what was checked live.
- [Plugins of our own](architecture/plugins.md) (`src-tauri/plugins/`): why native code goes into plugins, `network` (Swift and Kotlin, and the Rust they share) and why not polling from Rust, `photos` and why not `tauri-plugin-dialog`, `secrets` and why not `EncryptedSharedPreferences`, stronghold or JNI by hand.

- **Tauri 2 for iOS and Android**: one Rust core shared by both platforms, a WebView UI. Bundle id `dev.usecornercase.mobile` from the start, so the transfer to `usecornercase` never changes the app's identity.
- **All networking in Rust**: the WebView never opens a socket. It calls Tauri commands and listens to Tauri events whose TypeScript types come from tauri-specta. Rejected: networking in the WebView (iOS suspends it unpredictably, keys would leave the Keychain, and SSH or iroh routes are Rust-only anyway).
- **A strict CSP** (`app.security.csp` in `tauri.conf.json`), so the rule above holds by itself and the terminal and agent output the UI shows can neither load nor send anything: everything from the app (`'self'`), images also as `data:`, inline styles allowed, and connections only to Tauri's IPC (`ipc:` on iOS and macOS, `http://ipc.localhost` on Android and Windows). Tauri adds nonces and hashes only for inline `<script>` and `<style>` tags in the HTML, and Vite's build has none, so `'unsafe-inline'` still works. The policy applies to the bundled `dist/` only: in `tauri ios dev` the page comes from Vite through Tauri's proxy without any CSP (Tauri 2.12.5's sources; `devCsp` only matters without `devUrl`), so hot reload is unaffected and there is no `devCsp`. To check the policy, run `pnpm build` and `pnpm tauri ios dev "<iPhone>" --features tauri/custom-protocol`, which embeds `dist/`. Checked that way on 2026-11-08 in the iPhone 17 simulator (iOS 27.2): styles, inline styles and IPC work; a `fetch` to another origin and `eval` are blocked. Plain `ios dev` was checked the same day, with hot reload.
- **Workspace**: `crates/core` holds pure logic (no Tauri, no platform) so it is tested on Linux CI; `src-tauri` is the shell (commands, events, key storage, lifecycle, network changes); `src-tauri/plugins/` holds the Tauri plugins of our own, each a crate of the workspace with its native code; `bridge/` is a separate binary for the Mac.
- **`Secrets` per platform**: the trait lives in `crates/core` (`secrets.rs`), with `MemorySecrets` for its tests. `src-tauri` picks the stores per platform (`src-tauri/src/secrets.rs`), one for the identity (`store`) and one for the routes' tokens (`routes`): iOS gets the data protection keychain for both, through `KeychainSecrets` over keyring-core (`secrets/keychain.rs`, `keychain/ios.rs`); Android gets the Keystore for both, through the secrets plugin (below), once the tokens 030 left in `FileSecrets` (`crates/core/src/secrets/file.rs`, a JSON file in the app's data folder) are moved into it; every other platform gets `KeychainSecrets` over a missing store for both, which fails every call with a message, so the app starts and says why it has no identity. `FileSecrets` and the move live in the core, without `cfg`, so Linux CI tests them and the platforms that do not use them have no dead code. Why, and what was checked: `design/connection/identity.md`. Rejected: moving iOS to the plugin too, with a Swift half over `SecItem*`: its Keychain works and was checked live, so it would add risk for nothing.
- **Native code in Tauri plugins of our own** (`src-tauri/plugins/`): `network` in Swift and Kotlin, `photos` in Swift (the picker, the image shrunk and, since 041, a small thumbnail for the chat's composer), `secrets` in Kotlin, each with a stub on the other platforms; why plugins, and what each was preferred to, are in Plugins of our own.
- **UI**: Svelte 5 + Vite + TypeScript. Chosen for its small bundle, runes and built-in transitions for gpui's motion. Rejected: React (more runtime and re-render care for the live terminal), SolidJS (smaller ecosystem, motion by hand), no framework (routing, state and motion by hand).
- **Svelte + Vite, without SvelteKit**: the app is a few screens inside one WebView, where routing is state. The `svelte-ts` template of create-tauri-app 4.7 is SvelteKit with `adapter-static`; it was rejected for file routing the app does not need, server rendering to turn off, and `svelte-kit sync` before every check. The frontend is set up by hand around `@sveltejs/vite-plugin-svelte`.
- **Dev server**: Vite on port 1420 with `strictPort`, the port `tauri.conf.json` expects. When the app runs on an iPhone, `tauri ios dev` sets `TAURI_DEV_HOST` to the Mac's address, Vite listens there and hot reload goes over its own WebSocket on 1421; without it Vite stays on localhost, which the simulator reaches, and which `tauri android dev` publishes on the emulator or the phone with `adb reverse` (Android).
- **Platform order**: iOS first (simulator and iPhone); then Android, in three tasks: the project and the emulator (030, Android), the Keystore (031) and the keyboard and network changes (032).
- **Native projects in git**: `src-tauri/gen/apple` and `gen/android` are versioned, since they carry the Info.plist, the camera permission and the entitlements. What Xcode and the builds write inside them stays out (`.gitignore`): `src-tauri/gen/**/build`, `xcuserdata/`, `DerivedData/`, `*.xcuserstate`, `Externals/` (where the Rust build leaves `libapp.a`) and `Pods/`, besides the `.gitignore` that `tauri ios init` writes in `gen/apple` (`xcuserdata/`, `build/`, `Externals/`) and the two `tauri android init` writes in `gen/android` (Android). `src-tauri/gen/schemas` is regenerated by every build, so it is ignored too.
- **`gen/apple` as `ios init` wrote it**: `project.yml` is xcodegen's source and `cornercase-mobile.xcodeproj` its output; both are versioned: the Tauri CLI regenerates the project from `project.yml` (it did on `ios init` and again on the first `ios dev`), and Xcode opens the `.xcodeproj` as it is. A change to the project goes in `project.yml`. Bundle id `dev.usecornercase.mobile`, iOS 15.0 as the minimum, the Rust library linked as `libapp.a` and built by Xcode's "Build Rust Code" phase through `pnpm tauri ios xcode-script`. The entitlements are empty and the Info.plist has no permission yet; the `Podfile` has no pods. `project.yml` lists `Externals/` and `assets/` as sources but neither is in git (one is ignored, the other empty); the Tauri CLI creates both before it runs xcodegen, so `pnpm install && pnpm tauri ios dev` works from a fresh clone (checked on 2026-11-08), while `xcodegen generate` by hand in one fails. Checked live on 2026-11-08 with Xcode 27.2, the iOS 27.2 simulator (iPhone 17), xcodegen 2.46.0 and CocoaPods 1.17.0.
- **`features = []` in `src-tauri/Cargo.toml`**: `tauri ios init` rewrote `tauri` and `tauri-build` in that form, the one in which the CLI keeps their features in step with `tauri.conf.json`; the manifest keeps it, so the CLI's next run leaves the file alone.

## Commands and events

- **What the WebView can call** (`src-tauri/src/commands/`): `machines_list` (the machines and the active one), `machine_add(url, name)` (the new id), `machine_remove(id)`, `machine_rename(id, name)`, `machine_merge(id, code)` (what it added, updated and left to another machine), `machine_route_remove` and `machine_route_move` (`routes.rs`), `machine_probe(id)` and `machine_match(url, name)` (`probe.rs`), `connect(id)`, `connection_state`, `agents`, `identity_fingerprint` (Connection › Machines), the chat's `last_message(pane)`, `send(pane, text, force)`, `keys(pane, keys)` (one or more keys in one call), `mark_reviewed(pane)`, `attach(pane)`, `paste_attached(pane, id)` and `discard(ids)` (`commands/chat.rs`, `commands/chat/attach.rs`, `design/chat.md`), the start screen's `start_projects`, `installed_agents`, `start_agent(form)` and `start_issue(form)` (`commands/start.rs`, `design/starting-work.md`), the issues' `issue_sources(project)`, `issue_list(project, filter)` and `issue_read(project, source, key)` (`commands/issues.rs`, Starting work › From an issue), the issue's flows, `issue_flows(project)` and `start_flow(form)` (`commands/flows.rs`, Starting work › With a flow), the changes screen's `changes_follow(workspace, mode)`, `changes_unfollow(workspace)`, `changes_file(workspace, path, mode)` and `changes_viewed(file)` (`commands/changes.rs`, `design/changes-and-files.md`), the files screens' `files_list(workspace, paths)`, `files_read(workspace, path)`, `files_search(workspace, query)` and `files_search_stop(workspace)` (`commands/files.rs`, Changes and files › Files), `terminal_open(tab, pane, shape)` and `terminal_close(tab)` (Terminal › The terminal in the app), the chat's `question_open(tab, pane)` and `question_close(tab, pane)` (`commands/chat/question.rs`, Chat › The question), the chat's conversation's `history_load(machine, boot, pane)` and `history_save(machine, boot, pane, entries)` (`commands/history.rs`, Chat › Kept on the phone), and `terminal_input(pane, events)` and `terminal_scroll(pane, rows_up)` (Terminal › Typing). Each one is a thin `#[tauri::command] #[specta::specta]` wrapper over a function of `&AppState` (and an `Emit` where it emits), which the tests call without Tauri's runtime. Tauri hands a command its `State` and arguments by value, hence `#[expect(clippy::needless_pass_by_value)]` on each wrapper. Those that take an `AppHandle` (`machine_remove`, `machine_merge`, `machine_route_remove`, `connect`, which may start or end a `Store`, `terminal_open`, `question_open` and `changes_follow`, which start a task, and `attach`, which reaches the photos plugin) are generic over its `Runtime`, so the tests can run them on Tauri's `MockRuntime`; `collect_commands!` names them with `::<Wry>` for the types only, and `bindings::specta` is generic too.
- **Off the main thread**: in Tauri 2 a command without `async` runs on the main thread. `machine_add`, `machine_remove`, `machine_rename`, `machine_merge`, `machine_route_remove`, `machine_route_move`, `connect`, `terminal_open`, `question_open`, `changes_follow`, `history_load` and `history_save`, which write the Keychain, `machines.json` or the conversations' files or start a `Store` or a task, are `#[tauri::command(async)]`, so they run on Tauri's async runtime without blocking the UI; their signatures do not change and the bindings neither. The getters stay synchronous: they only read memory. Rejected for those that do not wait: `async fn` with `State<'_, _>`, the same effect with more ceremony. `machine_probe` and `machine_match`, which wait on the network (`pick_route`) and hold no lock across it, the chat's `last_message`, `send`, `keys`, `mark_reviewed`, `attach` and `paste_attached`, `installed_agents`, `start_agent` and `start_issue`, `issue_sources`, `issue_list` and `issue_read`, `issue_flows` and `start_flow`, `changes_file` and `changes_viewed`, and `files_list`, `files_read` and `files_search`, which await the transport or the queue, are such an `async fn`; `start_projects` only reads the `Store`'s session, `discard` only drops images from memory, and `changes_unfollow`, `question_close` and `files_search_stop` only abort a task, so they stay synchronous. `attach` calls the photos plugin in `spawn_blocking`: `run_mobile_plugin` blocks until the picker answers, which would hold a thread of the async runtime for as long as the user browses the photos. The chat, the start screen, the issues, the changes and the files reach the active `Store`'s transport and queue through `commands/reach.rs` (`connected`, `queue`, `ask`, `asked`, which also gives the job's output, and `answered`, which maps a queued job's outcome to its output, `not_sent`, `unanswered` or cornercase's reason; the starts' `answered` in `commands/start.rs`, which `start_flow` shares, reads the output into the start's answer as well), so they cannot drift. Running at once, `connect` holds the `active` lock from reading the machine until its `Store` is in place, so a `machine_remove` of that machine waits and then ends the new `Store` (with its `none`) instead of leaving one of a machine that is gone; the locks are always taken `active` then `machines`, `machine_remove` never holds both and the forwarder only takes `machines`, so they cannot deadlock. Two `connect`s in a row also wait for each other, but they may end in either order, so the last one called is not always the active one: so the UI runs them one after the other and drops one a newer call has replaced (Connection › Machines › Switching).
- **A screen's stream is a task in a slot of `Active`** (`src-tauri/src/state.rs`, `Slot`): one for the terminal, keyed by its tab, one for the changes, keyed by their workspace, one for the chat's question, keyed by its tab and pane (`ask`, `unask`), and one for the files' search, keyed by its workspace (`search`, `unsearch`), which holds a one-shot search rather than a stream, so a new query ends the last one (Changes and files › Files). None stops another, not even the terminal and the question of the same tab. Filling a slot aborts the task it held, emptying it with another key leaves it, and dropping `Active` (connecting again, removing the machine) aborts them all, which drops the stream and ends its process. The streams run the core's reopening loop (`crates/core/src/follow.rs`; `reopen` for the changes and the question, `revisit` for the terminal, whose fit can fall back to the passive `surface` at once): wait for a `Store` connected with a session, end when the session no longer holds what they show, open the stream on the `Store`'s transport and open it again after it ends or the `Store` moves to another transport (Terminal › Opening it again). Rejected: a reopening loop of its own for the changes, which would copy the terminal's and could drift from it.
- **The conversations live in the cache folder** (`app_cache_dir()/history/`, `AppState::history`), not in the data folder beside `machines.json`: they stay out of the device's backups and iOS may empty them, which costs only a gap line (Chat › Kept on the phone). Without a cache folder the app has no history: loads give nothing and saves go to the log. The store sits behind a `Mutex`, so two writes of a pane never cross.
- **Images waiting to be sent live in `AppState`** (`src-tauri/src/state/attached.rs`), not in `Active`: an image attached in the chat stays in Rust under an id until it is pasted or dropped (Chat › Attaching an image), so its bytes never cross to the WebView and back. Nothing on disk: a WebView that starts loading a page has lost the ids, so `lifecycle::on_page_load` empties the store then, and the app's process ending takes the rest.
- **The wrappers' tests** go through IPC: `test_util::Ipc` builds a mock app (`tauri::test::mock_builder`) with the same invoke handler and `mount_events` as `run`, manages an `AppState` and calls each command with `get_ipc_response`, so a wrapper that answered something else, or a command left out of `collect_commands!`, fails. `Emit for AppHandle` is tested by listening on the mock app; `lifecycle::resume` on a mock app with and without the state. `run` and the mobile `foreground` (and so `on_event`'s call to `resume`, since `WindowEvent::Resumed` exists only on mobile) are covered only by the simulator check (Connection › Store › In the app).
- **What it hears** (`src-tauri/src/events.rs`): `connection-changed { machine, connection }`, `agents-changed { machine, agents }`, `pane-status-changed { machine, pane }`, `terminal-changed { machine, tab, pane, size, cursor, colours, modes, replaced, rows, closed, unfitted }` (Terminal › The terminal in the app), `changes-changed { machine, workspace, mode, summary, closed }` (Changes and files › Following the list), `question-changed { machine, tab, pane, colours, rows, options, card, closed }` (the agent's pane cropped to its question, its numbered options and, when the rows read as one, the question as a card, sent whole, at most once per frame; Chat › The question) and `toast { level, message }`. `pane-status-changed` goes out with each `status` event that names a pane, and with `pane: null` on a `dropped` event and on each new `events` stream after the first (`Change::Reopened`), so the chat reads its message again (`design/chat.md` › Reading the message); it carries no message and no status, which come from `last_message` and `agents-changed`. `agents-changed` carries the board's rows (`AgentRow`, `design/board.md`), `null` before the first snapshot and after a restart, and goes out only when they differ from the last ones sent. Rejected: `session-changed` with the whole snapshot, which the app sent until 015: once the board took the place of the count of panes no screen read the session, and the snapshot crossed IPC about every 500 ms while an agent worked; a screen that needs more of the session brings its own, as the start screen's `start_projects` reads the session's projects when it opens. Rejected too: an event without the rows, after which the UI calls `agents` (a round trip per change), and a diff, which the contract gives no base for. How the `Store`'s changes become events: Connection › Store › In the app.
- **Getters beside the events**: the UI mounts after `setup`, so it may have missed events; `connection_state` and `agents` give the current state. The UI waits until its five listeners are registered (`listen` resolves once Tauri has them) before it calls the getters, so no change falls between the two. The changes screen listens to `changes-changed` only while it shows, and calls `changes_follow` once its listener is registered, so the stream's first summary is not missed.
- **Every event names its machine**, and the UI drops those of another machine than its active one: aborting a `Store`'s tasks does not wait for them, so a late `connection-changed` of a `Store` just let go can still arrive, even after `machine_remove`'s `none`. Rejected: waiting for the tasks in the command, a blocking command for events the UI can tell apart.
- **Data transfer objects, not the core's types** (`src-tauri/src/view.rs`): `MachineView` lists each route as `{kind, url}` with its address, never the token (the core's `Route` serializes it); `ConnectionView` is a union tagged by `state` (`none`, `connecting`, `connected{route}`, `retrying{in_ms, error}`, `missing{missing}`, `unauthorized`, `incompatible{error}`, `offline`), since `Connection` carries a `Duration` and the core's `Error`. `in_ms` is milliseconds; the UI rounds it up to whole seconds, so it never says "0 s". `ProjectChoice { id, name }` is a project of the session with the name the Mac shows, not the whole `Project` with its workspaces; `StartChoices { boot, projects }` gives them with the `Store`'s boot, which the start screen compares to tell a restart. The files' answers are unions of their own in `commands/files.rs`, tagged for the UI: `FileShown` is `read{read}` or `too_large_here{bytes, lines}`, a text past the phone's limit without its text, and `Searched` is `found{found}` or `cancelled`, a search a newer one ended (Changes and files › Files).
- **`CommandError { code, message }`** (`src-tauri/src/commands/error.rs`), never a bare string: `code` is a `snake_case` name, one per variant of the core's `Error`, one per `RouteError` (`route_*`) and the app's own `no_data_dir`, `machines_not_loaded`, `no_identity`, `not_connected` (no `Store`, or none connected yet), `not_sent` (a queued job that was skipped), `no_digest` (`changes_viewed` asked to mark without the version's digest) and `too_large_here` (`files_read` of a picture whose line passed the bridge's 16 MiB); `message` is the error's `Display`, which names neither a URL nor a token (Connection). The chat's commands, `start_agent`, `start_issue`, the issues' commands, `changes_file`, `changes_viewed` and the files' commands give a `failed` cornercase's own reason, its stderr without `Error:` rather than `cornercase exited with code 1: …`, since the user reads it in a toast, in the message's place or over the form's button (`CommandError::reason`). The UI shows `message` and can branch on `code`. `retrying` and `incompatible` carry one, and a `toast` the same message.
- **Toasts** are `error` for a `Store`'s warning and a route that could not be saved. `info` is in the contract, but nothing sends it yet: its `expect(dead_code)` goes with the first sender. Machines that did not load on start send no toast: `setup` runs before the WebView exists, so nobody would hear it, and the UI gets the error from `machines_list`, which it calls on mount and shows as a toast (`design/look.md` › Toasts). Rejected: keeping the pending error in `AppState` behind a getter, a second path for what `machines_list` already answers.
- **Generated bindings** (`src/lib/bindings.ts`, in git): `bindings::specta()` lists the commands and events once, for Tauri's `invoke_handler` and `mount_events` and for the export, so the two cannot drift. A Rust test exports to a temporary file (rc.26 exports only to a path) and compares it with the committed one, so CI fails while the file is stale, naming `UPDATE_BINDINGS=1 cargo test -p cornercase-mobile bindings`, which rewrites it. The UI never calls `invoke` by hand. ESLint, `scripts/check-rules.mjs` and jscpd skip the file (`design/code-layout.md`).
- **One type per direction**: tauri-specta exports a type as `_Serialize` and `_Deserialize` when serde writes and reads it differently (a field with `#[serde(default)]` is optional when read). The UI uses the `_Serialize` ones, what Rust sends. Kept rather than `disable_serde_phases`, so each side's type is exact.
- **`u64` as `number`**: specta-typescript refuses `u64`, a `bigint` that JSON cannot carry. Ids, `revision`, `in_ms` and a file's `bytes` are far below 2^53, so they go out as `number`: struct fields with `#[specta(type = u32)]` (a plain `number`, while `f64` exports as `number | null`), and the commands' arguments and results, which take no attribute, through `dangerously_cast_bigints_to_number`. That setting only shapes the export and sits behind tauri-specta's `typescript` feature, so the bindings test sets it on the builder it exports, and the app's `bindings::specta` goes without it. Rejected: ids as strings, a conversion on both sides for nothing.
- **specta in the core behind a feature**: `AgentRow`, `Missing`, `Kind`, the terminal's types, the start screen's (`AgentChoice`, `StartAgent`, `StartIssue`, `Started`), the issues' (`Sources` and `SourceInfo`, `Lists`, `IssueInfo` and `ListedInfo`, `ReadIssue` and `CommentInfo`, `ListFilter`), the changes' (`Mode`, `Summary` to `ChangedFile`, `Patch` to `Line`), the files' (`Listing` to `Entry`, `Read` and `Image`, `Found` to `FoundLine`) and the session's types (`Snapshot` to `Pane`, which no command sends since 015) derive `Serialize` (the forms the UI sends, `StartAgent`, `StartIssue` and `ListFilter`, `Deserialize`) always and `specta::Type` only with the core's `specta` feature, which `src-tauri` turns on, so the bridge builds without specta. Rejected: copying them as transfer objects in `src-tauri`, a duplicate jscpd refuses and that could drift.
- **The app's screens** (`src/App.svelte`, its logic in `src/lib/connection.ts`): `App` keeps the active machine, its connection and its agents, and shows the screen that state asks for (`design/look/navigation.md`): `no-machines` with the first machine's form, or, under the connection bar (`design/connection/bar.md`), `home` with the board or the `agent` a row opened, the `start` screen the board's `Start` or an agent's `New agent` opens (`design/starting-work.md`), the `issues` of every project its `Issue` opens and an `issue` over them, each with its own state (`IssuesState`, `IssueState` in `src/lib/issues.svelte.ts`) while its route is anywhere in the stack (`Router.latest`), so a `start` from the issue keeps both alive under it (Starting work › From an issue), the `changes` of an agent's workspace and a file's `change` over it, which share one `ChangesState` while either is on top (`design/changes-and-files.md`), the `files` of an agent's workspace and a `file` over it (also over a `change`), which share one `FilesState` while either is on top, the tree read again on the way back from a file (Changes and files › Files), and Machines and a machine's screen above it; or an agent's `terminal`, opened from its screen, in their place under its own bar (Terminal › Opening it), with the toasts over all of them. `connection-changed` and `agents-changed` go through `apply`, which drops another machine's events; one to `none` (the active machine removed) forgets the machine and its agents, back to `no-machines` if no machine is left, and otherwise on Machines without a connection. On mount, once the listeners are in place, it reads the getters and, while no `Store` runs, connects to the saved active machine, or to the first if that one is gone. A hot reload mounts it again and finds the running `Store` in `connection_state`, so it does not make another, and the screen follows from that state. Connecting from `setup` in Rust was rejected while it would have had to choose the machine; now that the active one is saved (027) it could, but the UI's load already connects once its listeners are in place, so no event is missed. Every command error, and a failed IPC call, which the bindings throw rather than return, becomes an error toast, except a message that cannot be read, which the chat shows in its place (`design/chat.md`). It touches Tauri only when `isTauri()`, so vitest renders it with `svelte/server`.

## Versions

Chosen on 2026-11-08, the latest stable of each unless said otherwise.

- Rust 1.99.1 (Tauri 2.12 needs 1.90), pinned in `rust-toolchain.toml` with `aarch64-apple-ios`, `aarch64-apple-ios-sim` and `aarch64-linux-android`, so rustup brings the phones' targets with the toolchain. Android's other versions (JDK, NDK, AGP, Gradle, SDK) are in Android › Versions.
- Tauri 2.12.5, tauri-build 2.7.4, `@tauri-apps/cli` 2.12.4. Tauri 3.0 is an alpha: not used.
- tauri-specta 2.0.0-rc.26, specta 2.0.0-rc.26, specta-typescript 0.0.13 and `@tauri-apps/api` 2.12.4, chosen on 2026-11-09 (Dependencies).
- Svelte 5.57.3, Vite 8.3.6, `@sveltejs/vite-plugin-svelte` 7.3.1, Node 22, pnpm 12.18.0.
- **pnpm, not Yarn**: Tauri's and Svelte's templates and docs use it; its strict `node_modules` fails on a package imported without being declared; pnpm 12 refuses versions published less than 24 hours ago, a guard against compromised releases. Rejected: Yarn 4, whose strength is Plug'n'Play, which breaks svelte-check, the ESLint plugins and the Tauri CLI; with `node-modules` it brings nothing pnpm lacks (decided on 2026-11-08).
- **TypeScript 6.0, not 7**: 7.0 has been npm's `latest` since November 2026, but svelte-check accepts `^5 || ^6` and typescript-eslint `<6.1.0`, and create-tauri-app pins `~6.0.3` too. TypeScript is `~6.0.3` and Dependabot ignores its majors; move to 7 once both tools accept it.

## Dependencies

- `tauri`: the app shell. Its default features and `specta`, which tauri-specta needs. Its plugins are our own `tauri-plugin-network` and `tauri-plugin-photos` and, on the phones, Tauri's `tauri-plugin-barcode-scanner` and `tauri-plugin-haptics`.
- `tauri-build`: `src-tauri/build.rs`, which turns `tauri.conf.json` and the capabilities into the context `tauri::generate_context!` embeds.
- `@tauri-apps/cli`: `pnpm tauri`, for `ios init`, `ios dev` and the builds.
- `@tauri-apps/api`, a runtime package: the generated bindings import its `invoke` and `listen`, and the UI its `isTauri` and `onBackButtonPress` (Android's back, Look › Navigation). It came with the first command the UI calls (013), so that no package sat unused.
- `svelte`, `vite`, `@sveltejs/vite-plugin-svelte`, `typescript`: the UI and its build.
- `mdast-util-from-markdown` 2.1, `micromark-extension-gfm` 3.0 and `mdast-util-gfm` 3.1: an agent's message as a tree (CommonMark with GFM's tables, strikethrough, task lists and autolinks), which `src/lib/markdown.ts` turns into a closed tree of its own and Svelte components draw, so nothing goes through `{@html}` (which `svelte/no-at-html-tags` refuses): HTML stays as its text, a link as its words and an image as its `alt`. Their mdast types come through `fromMarkdown`'s return type, without declaring `@types/mdast`. Rejected: `markdown-it` with `html: false`, whose flat tokens would need turning into a tree; `marked` with `{@html}` and DOMPurify, against the lint rule; `pulldown-cmark` in the core, more Rust and a recursive type through specta (016).
- No `@types/node`: `vite.config.ts` reads one environment variable (`TAURI_DEV_HOST`), so it declares the `process` it uses instead of pulling in Node's types for the whole config.
- `svelte-check`: type checks `.svelte` and `.ts` files (`pnpm check`).
- `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-plugin-svelte`, `globals`: `pnpm lint`, in flat config through ESLint's own `defineConfig` (typescript-eslint deprecates its `config` helper in its favour); `globals` declares the browser's globals.
- `vitest`: the UI's unit tests, configured in `vite.config.ts` so they share Vite's plugins. They render components with `svelte/server`, which needs no DOM; jsdom stays out until a test needs a browser. Vitest does not process CSS by default, so `tokens.css?raw` and `base.css?raw` would arrive empty; `test.css.include` lets only the `?raw` imports through.
- `serde` (with `derive`), `serde_json`: the bridge's JSON messages in `crates/core` (`design/bridge.md`); refusing unknown keys and wrong types is serde's work rather than hand-written checks. Both were already in `Cargo.lock` through Tauri. `bridge/` also takes `serde_json`, to write each `BridgeMessage` as the text of a WebSocket frame.
- `base64`: decodes `stdin_base64` in `crates/core`, with the standard alphabet and padding, so a malformed message is refused instead of guessed at. 0.23, the version Tauri already brought into `Cargo.lock`. `bridge/` takes the same version to write its token in the URL-safe alphabet without padding, so it goes into the URL's query as it is.
- `getrandom` in `bridge/` and `crates/core`: the 32 random bytes of the bridge's token and of the device identity's seed, straight from the system's generator, without features (no `rand`, nothing else needs randomness). 0.4, the major version already in `Cargo.lock`. The core takes it for the seed only: the machines' ids stay a counter (`design/connection.md`).
- `qrcode` in `bridge/`, without its default features (no image output): the code of each address's URL, drawn on the terminal with half blocks and fixed colours of the 256 palette, at error correction level L, as cornercase-terminal draws its own and at its version. Nothing else in `Cargo.lock` pulled it in.
- `thiserror` in `crates/core`: the core's `Error`, one variant per way a command can fail, as the rules of cornercase-terminal ask for library errors. 2.0, the version already in `Cargo.lock` through Tauri.
- `rstest` (dev, in `crates/core`, `bridge/`, `src-tauri` and the secrets plugin): the tables of named cases (`#[case::name]`) the Rust tests use, as in cornercase-terminal.
- `clap` (with `derive`) in `bridge/`: the bridge's options (`--port`, a `u16` with 8765 as its default, `--new-token`, `--loopback` and `--cornercase`), as in cornercase-terminal and with its features: no colours, help, usage, error context and suggestions for a mistyped option.
- `cornercase-core` in `bridge/`: the bridge reads and writes the protocol types that live in the core, so the app and the bridge cannot drift apart (`design/bridge.md`).
- `cornercase-bridge` (dev, with `test-util`) in `crates/core`: the transport's integration tests run the real bridge inside the test with the bridge's own helpers (`Served`, `fake_cornercase`, `HUNG`, `reaped`), rather than a copy of them that jscpd would refuse. It makes a cycle, core → bridge → core, which Cargo allows for a dev-dependency; it works in `crates/core/tests/` only, since in the core's unit tests the bridge's `cornercase-core` would be a second copy whose types do not match (`design/connection.md`).
- `tokio` in `bridge/`: runs the cornercase command, reads its stdout and stderr line by line and writes its stdin without blocking the bridge (`design/bridge.md`). Already in `Cargo.lock` through Tauri; the bridge turns on `process`, `io-util`, `rt`, `sync`, `time` and `macros`, and `net` and `signal` for the WebSocket server, which listens on TCP and stops on `SIGINT` and `SIGTERM`. `crates/core` takes `sync` for the `mpsc` channel behind the output sink `output`, `json` and `partial_json` collect the stdout with, a `sink::unfold` over its sender, and for the ordered queue's channels and replies, `net` and `time` for the bridge transport, which connects over TCP within `tokio::time::timeout`, `time` also for the queue's 10 s wait for the keys' answers, and in its tests `rt` and `macros` for `#[tokio::test]`, and `test-util` for `start_paused`, so the tests of `pick_route`'s deadline and window run on a paused clock that jumps ahead, rather than waiting seconds of real time (`design/connection.md`).
- `tokio-tungstenite` in `bridge/`: the WebSocket server, with only its `handshake` feature (no TLS: the bridge is for development, `design/bridge.md`). `accept_hdr_async` hands the request to a callback before the upgrade, where the token and the path are checked, and its `WebSocketConfig` bounds what is read and the write buffer. The tests also turn on `connect`, for `connect_async` as the client. `crates/core` takes it with `connect` and `handshake`, still without TLS, for the bridge transport's client, whose `WebSocketConfig` raises the frame and message limits to the bridge's 7 × 16 MiB. 0.30, the version cornercase-terminal's `tungstenite` is at.
- `futures-util` (with `sink` and `std`) in `bridge/`: `StreamExt` and `SinkExt` over tokio-tungstenite's stream, which implements the `futures` traits rather than its own methods. Already in `Cargo.lock` through Tauri and tokio-tungstenite. `crates/core` takes it for the `Transport` trait: `BoxFuture` keeps `run` usable as `dyn Transport`, and its input and output are a `BoxStream` and a `Sink`, without `async-trait` or tokio in the trait. `src-tauri` takes it as a dev-dependency only, so its tests can script a `FakeTransport` that reads what the queue writes on stdin and answers on the sink.
- `rustix` (with `process`, `fs` and `system`) in `bridge/`: signals the cornercase command's process group (`kill_process_group`) when it is killed or dropped and looks at whether it still has members, and asks the system whether this user may run the binary (`access` with `X_OK`, not any execute bit), and reads the host name (`uname`) for the machine code's name (Bridge › The machine code), with a safe API instead of `libc` and `unsafe`, as in cornercase-terminal and at its version (`design/bridge.md`).
- `if-addrs` in `bridge/`: lists the Mac's interfaces and their addresses (`getifaddrs`, through `libc`, without `unsafe` in the bridge), from which the bridge picks the LAN and Tailscale ones it listens on (`design/bridge.md`); `rustix` has no `getifaddrs`, and `nix` would bring far more than this one call. Licence `MIT OR BSD-3-Clause`; it builds on macOS and Linux. Without its `link-local` feature, since link-local addresses are never listened on. Nothing else in `Cargo.lock` pulled it in.
- `ed25519-dalek` in `crates/core`: the device identity's Ed25519 key pair, built from its 32-byte seed (`design/connection/identity.md`). 3.0, with its default features (`fast`, `zeroize`, so `SigningKey` wipes itself when dropped) and without `rand_core`, since the seed comes from `getrandom`. Nothing else in `Cargo.lock` pulled it in.
- `zeroize` in `crates/core`: `Zeroizing`, which wipes the seed's buffers when they are dropped. 1.9, the version ed25519-dalek brings.
- `cornercase-core` in `src-tauri`: the `Identity` it makes on start, the `Secrets` trait it implements, the machines and the `Store`, with its `specta` feature (Commands and events). Its `test-util` feature, on in `src-tauri`'s dev-dependencies only, makes `FakeTransport` public for their tests; the core's dev-dependency on itself turns it on in its own tests too, as the bridge does for its helpers (`design/bridge.md`).
- `tauri-specta` (with `derive`; `typescript` only in the dev-dependencies), `specta` and `specta-typescript` (dev) in `src-tauri`, `specta` (optional) in `crates/core`: the TypeScript types of the commands, the events and what they carry, from the Rust types. All three are pinned with `=`: tauri-specta is a release candidate (rc.26, 2026-10-21) that pins `specta =2.0.0-rc.26` itself, though specta is at rc.28, and asks for specta-typescript 0.0.13; a lone bump would not resolve or would change the export, so Dependabot ignores the three and they are bumped by hand together. `specta` is a workspace dependency, so the core's and `src-tauri`'s share the pin. Only the bindings test exports TypeScript, so specta-typescript and tauri-specta's `typescript` feature stay out of the app's build. Rejected: types written by hand, the task's plan B, not needed.
- `serde` (with `derive`) and `serde_json` in `src-tauri`: the transfer objects, `CommandError` and the events are `Serialize`, and `terminal_input` turns the typed events into the JSON values the queue takes (Terminal › Typing).
- `cornercase-bridge` (dev, with `test-util`), `futures-util` (dev, with `sink` and `std`) and `tokio` (dev, with `rt`, `macros`, `time` and `test-util`) in `src-tauri`: the tests' `TempDir`, the JSON the events turn into, the `FakeTransport` stream and sink the typist's lines are read from, and `#[tokio::test]` on a paused clock for the `Store`'s backoff. `futures-util` was already in `Cargo.lock` through Tauri and the core.
- `tauri` (dev, with `test`) in `src-tauri`: `MockRuntime`, `mock_builder` and `get_ipc_response`, to run the commands' wrappers, `Emit for AppHandle`, `lifecycle::resume` and `network::follow` in the tests (Commands and events). The same `tauri` as the app's, with one more feature in the tests only.
- `keyring-core` in `src-tauri`, on every platform but Android (`[target.'cfg(not(target_os = "android"))'.dependencies]`), and as a dev-dependency, since from 031 Android uses it only in its tests: the `Entry` API `KeychainSecrets` is written against, so the same adapter runs on iOS and over a missing store elsewhere, and its `mock` store, which tests the adapter and its errors on Linux CI. 1.0, without features (its `sample` store is not used). keyring's maintained line: `keyring` 4.x has no `apple-native` any more, and 3.6 cannot set the Keychain's accessibility.
- `apple-native-keyring-store` in `src-tauri`, iOS only (`[target.'cfg(target_os = "ios")'.dependencies]`), with `protected`: the data protection keychain, with an `access-policy` per entry. 1.0; it brings `security-framework` 3.7, which nothing else pulled in.
- `tauri-plugin-network` (`src-tauri/plugins/network`) in `src-tauri`: the network plugin (Plugins of our own).

- `tauri-plugin-barcode-scanner` in `src-tauri`, iOS and Android only (`[target.'cfg(any(target_os = "ios", target_os = "android"))'.dependencies]`, registered under `#[cfg(mobile)]`), and `@tauri-apps/plugin-barcode-scanner`, its JavaScript API: the camera scans a machine's QR code (027).
