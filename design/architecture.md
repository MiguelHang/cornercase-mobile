# Architecture

- **Tauri 2 for iOS and Android**: one Rust core shared by both platforms, a WebView UI. Bundle id `dev.usecornercase.mobile` from the start, so the transfer to `usecornercase` never changes the app's identity.
- **All networking in Rust**: the WebView never opens a socket. It calls Tauri commands and listens to Tauri events whose TypeScript types come from tauri-specta. Rejected: networking in the WebView (iOS suspends it unpredictably, keys would leave the Keychain, and SSH or iroh routes are Rust-only anyway).
- **A strict CSP** (`app.security.csp` in `tauri.conf.json`), so the rule above holds by itself and the terminal and agent output the UI shows can neither load nor send anything: everything from the app (`'self'`), images also as `data:`, inline styles allowed, and connections only to Tauri's IPC (`ipc:` on iOS and macOS, `http://ipc.localhost` on Android and Windows). Tauri adds nonces and hashes only for inline `<script>` and `<style>` tags in the HTML, and Vite's build has none, so `'unsafe-inline'` still works. The policy applies to the bundled `dist/` only: in `tauri ios dev` the page comes from Vite through Tauri's proxy without any CSP (Tauri 2.12.5's sources; `devCsp` only matters without `devUrl`), so hot reload is unaffected and there is no `devCsp`. To check the policy, run `pnpm build` and `pnpm tauri ios dev "<iPhone>" --features tauri/custom-protocol`, which embeds `dist/`. Checked that way on 2026-11-08 in the iPhone 17 simulator (iOS 27.2): styles, inline styles and IPC work; a `fetch` to another origin and `eval` are blocked. Plain `ios dev` was checked the same day, with hot reload.
- **Workspace**: `crates/core` holds pure logic (no Tauri, no platform) so it is tested on Linux CI; `src-tauri` is the shell (commands, events, key storage, lifecycle, network changes); `src-tauri/plugins/` holds the Tauri plugins of our own, each a crate of the workspace with its native code; `bridge/` is a separate binary for the Mac.
- **`Secrets` per platform**: the trait lives in `crates/core` (`secrets.rs`), with `MemorySecrets` for its tests. `src-tauri` implements it once, `KeychainSecrets` over keyring-core (`src-tauri/src/secrets.rs`), and picks the store per platform: iOS gets the data protection keychain (`secrets/ios.rs`); every other platform, Android included until its Keystore (030, 031), gets a missing store, whose every call fails with a message, so the app starts and says why it has no identity. Why, and what was checked on iOS: `design/connection.md` (Identity).
- **Native code in Tauri plugins of our own**: `src-tauri/plugins/network` is the first, a crate with a Swift package in `ios/` that hears `NWPathMonitor` and hands each path to a callback of the app (`design/connection/network.md`). A plugin is how Tauri 2 builds Swift, and later Kotlin (032), into the app, with a stub on the other platforms so Linux CI compiles everything else; the logic stays in Rust (the debounce in the core), and the plugin only reports. It has no JavaScript API, commands or permissions: the WebView never sees it.
  - Rejected, and kept as plan C: noticing the change from Rust without native code, as upstream does in `src/host/network.rs`, asking every ~2 s for the source address the system would use toward each route, through a `UdpSocket::connect` that sends nothing. It polls (it wakes the phone every 2 s instead of hearing an event), knows neither the kind of network nor its cost, and with Tailscale up its `utun` interface keeps an address with no network underneath, so it never sees `none`.
- **UI**: Svelte 5 + Vite + TypeScript. Chosen for its small bundle, runes and built-in transitions for gpui's motion. Rejected: React (more runtime and re-render care for the live terminal), SolidJS (smaller ecosystem, motion by hand), no framework (routing, state and motion by hand).
- **Svelte + Vite, without SvelteKit**: the app is a few screens inside one WebView, where routing is state. The `svelte-ts` template of create-tauri-app 4.7 is SvelteKit with `adapter-static`; it was rejected for file routing the app does not need, server rendering to turn off, and `svelte-kit sync` before every check. The frontend is set up by hand around `@sveltejs/vite-plugin-svelte`.
- **Dev server**: Vite on port 1420 with `strictPort`, the port `tauri.conf.json` expects. When the app runs on a phone, `tauri ios dev` sets `TAURI_DEV_HOST` to the Mac's address, Vite listens there and hot reload goes over its own WebSocket on 1421; without it Vite stays on localhost, which the simulator reaches.
- **Platform order**: iOS first (simulator and iPhone); Android gets its own task (Keystore, keyboard).
- **Native projects in git**: `src-tauri/gen/apple` and `gen/android` are versioned, since they carry the Info.plist, the camera permission and the entitlements. What Xcode and the builds write inside them stays out (`.gitignore`): `src-tauri/gen/**/build`, `xcuserdata/`, `DerivedData/`, `*.xcuserstate`, `Externals/` (where the Rust build leaves `libapp.a`) and `Pods/`, besides the `.gitignore` that `tauri ios init` writes in `gen/apple` (`xcuserdata/`, `build/`, `Externals/`). `src-tauri/gen/schemas` is regenerated by every build, so it is ignored too.
- **`gen/apple` as `ios init` wrote it**: `project.yml` is xcodegen's source and `cornercase-mobile.xcodeproj` its output; both are versioned: the Tauri CLI regenerates the project from `project.yml` (it did on `ios init` and again on the first `ios dev`), and Xcode opens the `.xcodeproj` as it is. A change to the project goes in `project.yml`. Bundle id `dev.usecornercase.mobile`, iOS 15.0 as the minimum, the Rust library linked as `libapp.a` and built by Xcode's "Build Rust Code" phase through `pnpm tauri ios xcode-script`. The entitlements are empty and the Info.plist has no permission yet; the `Podfile` has no pods. `project.yml` lists `Externals/` and `assets/` as sources but neither is in git (one is ignored, the other empty); the Tauri CLI creates both before it runs xcodegen, so `pnpm install && pnpm tauri ios dev` works from a fresh clone (checked on 2026-11-08), while `xcodegen generate` by hand in one fails. Checked live on 2026-11-08 with Xcode 27.2, the iOS 27.2 simulator (iPhone 17), xcodegen 2.46.0 and CocoaPods 1.17.0.
- **`features = []` in `src-tauri/Cargo.toml`**: `tauri ios init` rewrote `tauri` and `tauri-build` in that form, the one in which the CLI keeps their features in step with `tauri.conf.json`; the manifest keeps it, so the CLI's next run leaves the file alone.

## Commands and events

- **What the WebView can call** (`src-tauri/src/commands/`): `machines_list`, `machine_add(url, name)` (the new id), `machine_remove(id)`, `connect(id)`, `connection_state`, `agents`, `identity_fingerprint`, `terminal_open(tab, pane, size)` and `terminal_close(tab)` (Terminal › The terminal in the app), `terminal_input(pane, events)` and `terminal_scroll(pane, rows_up)` (Terminal › Typing). Each one is a thin `#[tauri::command] #[specta::specta]` wrapper over a function of `&AppState` (and an `Emit` where it emits), which the tests call without Tauri's runtime. Tauri hands a command its `State` and arguments by value, hence `#[expect(clippy::needless_pass_by_value)]` on each wrapper. The three that take an `AppHandle` (`machine_remove`, `connect`, `terminal_open`) are generic over its `Runtime`, so the tests can run them on Tauri's `MockRuntime`; `collect_commands!` names them with `::<Wry>` for the types only, and `bindings::specta` is generic too.
- **Off the main thread**: in Tauri 2 a command without `async` runs on the main thread. `machine_add`, `machine_remove`, `connect` and `terminal_open`, which write the Keychain and `machines.json` or start a `Store` or a task, are `#[tauri::command(async)]`, so they run on Tauri's async runtime without blocking the UI; their signatures do not change and the bindings neither. The getters stay synchronous: they only read memory. Rejected: `async fn` with `State<'_, _>`, the same effect with more ceremony. Running at once, `connect` holds the `active` lock from reading the machine until its `Store` is in place, so a `machine_remove` of that machine waits and then ends the new `Store` (with its `none`) instead of leaving one of a machine that is gone; the locks are always taken `active` then `machines`, `machine_remove` never holds both and the forwarder only takes `machines`, so they cannot deadlock. Two `connect`s in a row also wait for each other, but they may end in either order, so the last one called is not always the active one: so the UI asks for one at a time (Connection › Adding a machine).
- **The wrappers' tests** go through IPC: `test_util::Ipc` builds a mock app (`tauri::test::mock_builder`) with the same invoke handler and `mount_events` as `run`, manages an `AppState` and calls each command with `get_ipc_response`, so a wrapper that answered something else, or a command left out of `collect_commands!`, fails. `Emit for AppHandle` is tested by listening on the mock app; `lifecycle::resume` on a mock app with and without the state. `run` and the mobile `foreground` (and so `on_event`'s call to `resume`, since `WindowEvent::Resumed` exists only on mobile) are covered only by the simulator check (Connection › Store › In the app).
- **What it hears** (`src-tauri/src/events.rs`): `connection-changed { machine, connection }`, `agents-changed { machine, agents }`, `terminal-changed { machine, tab, pane, size, cursor, colours, modes, replaced, rows, closed }` (Terminal › The terminal in the app) and `toast { level, message }`. `agents-changed` carries the board's rows (`AgentRow`, `design/board.md`), `null` before the first snapshot and after a restart, and goes out only when they differ from the last ones sent. Rejected: `session-changed` with the whole snapshot, which the app sent until 015: once the board took the place of the count of panes no screen read the session, and the snapshot crossed IPC about every 500 ms while an agent worked; a screen that needs more of the session (023) brings its own. Rejected too: an event without the rows, after which the UI calls `agents` (a round trip per change), and a diff, which the contract gives no base for. How the `Store`'s changes become events: Connection › Store › In the app.
- **Getters beside the events**: the UI mounts after `setup`, so it may have missed events; `connection_state` and `agents` give the current state. The UI waits until its three listeners are registered (`listen` resolves once Tauri has them) before it calls the getters, so no change falls between the two.
- **Every event names its machine**, and the UI drops those of another machine than its active one: aborting a `Store`'s tasks does not wait for them, so a late `connection-changed` of a `Store` just let go can still arrive, even after `machine_remove`'s `none`. Rejected: waiting for the tasks in the command, a blocking command for events the UI can tell apart.
- **Data transfer objects, not the core's types** (`src-tauri/src/view.rs`): `MachineView` lists each route as `{kind, url}` with its address, never the token (the core's `Route` serializes it); `ConnectionView` is a union tagged by `state` (`none`, `connecting`, `connected{route}`, `retrying{in_ms, error}`, `missing{missing}`, `unauthorized`, `incompatible{error}`, `offline`), since `Connection` carries a `Duration` and the core's `Error`. `in_ms` is milliseconds; the UI rounds it up to whole seconds, so it never says "0 s".
- **`CommandError { code, message }`** (`src-tauri/src/commands/error.rs`), never a bare string: `code` is a `snake_case` name, one per variant of the core's `Error`, one per `RouteError` (`route_*`) and the app's own `no_data_dir`, `machines_not_loaded` and `no_identity`; `message` is the error's `Display`, which names neither a URL nor a token (Connection). The UI shows `message` and can branch on `code`. `retrying` and `incompatible` carry one, and a `toast` the same message.
- **Toasts** are `error` for a `Store`'s warning and a route that could not be saved. `info` is in the contract, but nothing sends it yet: its `expect(dead_code)` goes with the first sender. Machines that did not load on start send no toast: `setup` runs before the WebView exists, so nobody would hear it, and the UI gets the error from `machines_list`, which it calls on mount and shows as a toast (`design/look.md` › Toasts). Rejected: keeping the pending error in `AppState` behind a getter, a second path for what `machines_list` already answers.
- **Generated bindings** (`src/lib/bindings.ts`, in git): `bindings::specta()` lists the commands and events once, for Tauri's `invoke_handler` and `mount_events` and for the export, so the two cannot drift. A Rust test exports to a temporary file (rc.26 exports only to a path) and compares it with the committed one, so CI fails while the file is stale, naming `UPDATE_BINDINGS=1 cargo test -p cornercase-mobile bindings`, which rewrites it. The UI never calls `invoke` by hand. ESLint, `scripts/check-rules.mjs` and jscpd skip the file (`design/code-layout.md`).
- **One type per direction**: tauri-specta exports a type as `_Serialize` and `_Deserialize` when serde writes and reads it differently (a field with `#[serde(default)]` is optional when read). The UI uses the `_Serialize` ones, what Rust sends. Kept rather than `disable_serde_phases`, so each side's type is exact.
- **`u64` as `number`**: specta-typescript refuses `u64`, a `bigint` that JSON cannot carry. Ids, `revision` and `in_ms` are counters far below 2^53, so they go out as `number`: struct fields with `#[specta(type = u32)]` (a plain `number`, while `f64` exports as `number | null`), and the commands' arguments and results, which take no attribute, through `dangerously_cast_bigints_to_number`. That setting only shapes the export and sits behind tauri-specta's `typescript` feature, so the bindings test sets it on the builder it exports, and the app's `bindings::specta` goes without it. Rejected: ids as strings, a conversion on both sides for nothing.
- **specta in the core behind a feature**: `AgentRow`, `Missing`, `Kind`, the terminal's types and the session's types (`Snapshot` to `Pane`, which no command sends since 015) derive `Serialize` always and `specta::Type` only with the core's `specta` feature, which `src-tauri` turns on, so the bridge builds without specta. Rejected: copying them as transfer objects in `src-tauri`, a duplicate jscpd refuses and that could drift.
- **The app's screens** (`src/App.svelte`, its logic in `src/lib/connection.ts`): `App` keeps the active machine, its connection and its agents, and shows the screen that state asks for (`design/look.md` › Navigation): `no-machines` with the first machine's form, or, under the connection bar (`design/connection/bar.md`), `home` with the board or the `agent` a row opened; or an agent's `terminal`, opened from its screen, in their place under its own bar (Terminal › Opening it), with the toasts over all of them. `connection-changed` and `agents-changed` go through `apply`, which drops another machine's events; one to `none` (the active machine removed) forgets the machine and its agents, back to `no-machines`. On mount, once the listeners are in place, it reads the getters and connects to the first machine while no `Store` runs. A hot reload mounts it again and finds the running `Store` in `connection_state`, so it does not make another, and the screen follows from that state. Rejected: connecting from `setup` in Rust, which would have to choose the machine, while saving the active one is 027's. Every command error, and a failed IPC call, which the bindings throw rather than return, becomes an error toast. It touches Tauri only when `isTauri()`, so vitest renders it with `svelte/server`.

## Versions

Chosen on 2026-11-08, the latest stable of each unless said otherwise.

- Rust 1.99.1 (Tauri 2.12 needs 1.90), pinned in `rust-toolchain.toml` with `aarch64-apple-ios` and `aarch64-apple-ios-sim`, so rustup brings the iOS targets with the toolchain.
- Tauri 2.12.5, tauri-build 2.7.4, `@tauri-apps/cli` 2.12.4. Tauri 3.0 is an alpha: not used.
- tauri-specta 2.0.0-rc.26, specta 2.0.0-rc.26, specta-typescript 0.0.13 and `@tauri-apps/api` 2.12.4, chosen on 2026-11-09 (Dependencies).
- Svelte 5.57.3, Vite 8.3.6, `@sveltejs/vite-plugin-svelte` 7.3.1, Node 22, pnpm 12.18.0.
- **pnpm, not Yarn**: Tauri's and Svelte's templates and docs use it; its strict `node_modules` fails on a package imported without being declared; pnpm 12 refuses versions published less than 24 hours ago, a guard against compromised releases. Rejected: Yarn 4, whose strength is Plug'n'Play, which breaks svelte-check, the ESLint plugins and the Tauri CLI; with `node-modules` it brings nothing pnpm lacks (decided on 2026-11-08).
- **TypeScript 6.0, not 7**: 7.0 has been npm's `latest` since November 2026, but svelte-check accepts `^5 || ^6` and typescript-eslint `<6.1.0`, and create-tauri-app pins `~6.0.3` too. TypeScript is `~6.0.3` and Dependabot ignores its majors; move to 7 once both tools accept it.

- `apple-native-keyring-store` in `src-tauri`, iOS only (`[target.'cfg(target_os = "ios")'.dependencies]`), with `protected`: the data protection keychain, with an `access-policy` per entry. 1.0; it brings `security-framework` 3.7, which nothing else pulled in.
- `tauri-plugin-network` (`src-tauri/plugins/network`) in `src-tauri`: the network plugin (Native code, above).
- `tokio` in `src-tauri`, with `macros`, `sync` and `time`: the task that follows the network plugin waits on its channel (`mpsc`) and the debounce at once with `select!`; the terminal's task hands each screen through an unbounded channel, waits a frame between events and runs the stream and the emitter together (`join!`). The runtime is Tauri's; the dev line above adds `rt` and `test-util` for the tests.
- `tauri-plugin` (build, with `build`) in the plugin: its `build.rs`, which builds the Swift package in `ios/` and links it into the app; 2.7, the line of tauri-build 2.7 and Tauri 2.12.
- `tauri` and `cornercase-core` in the plugin: the plugin's `Builder`, `Channel` and `run_mobile_plugin`, and the core's `Network`, so the plugin hands the app the type the debounce reads; `serde` (with `derive`), iOS only, for the arguments it sends to Swift's `watch`.
