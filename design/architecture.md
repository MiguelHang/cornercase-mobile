# Architecture

- **Tauri 2 for iOS and Android**: one Rust core shared by both platforms, a WebView UI. Bundle id `dev.usecornercase.mobile` from the start, so the transfer to `usecornercase` never changes the app's identity.
- **All networking in Rust**: the WebView never opens a socket. It calls Tauri commands and listens to Tauri events whose TypeScript types come from tauri-specta. Rejected: networking in the WebView (iOS suspends it unpredictably, keys would leave the Keychain, and SSH or iroh routes are Rust-only anyway).
- **A strict CSP** (`app.security.csp` in `tauri.conf.json`), so the rule above holds by itself and the terminal and agent output the UI shows can neither load nor send anything: everything from the app (`'self'`), images also as `data:`, inline styles allowed, and connections only to Tauri's IPC (`ipc:` on iOS and macOS, `http://ipc.localhost` on Android and Windows). Tauri adds nonces and hashes only for inline `<script>` and `<style>` tags in the HTML, and Vite's build has none, so `'unsafe-inline'` still works. The policy applies to the bundled `dist/` only: in `tauri ios dev` the page comes from Vite through Tauri's proxy without any CSP (Tauri 2.12.5's sources; `devCsp` only matters without `devUrl`), so hot reload is unaffected and there is no `devCsp`. To check the policy, run `pnpm build` and `pnpm tauri ios dev "<iPhone>" --features tauri/custom-protocol`, which embeds `dist/`. Checked that way on 2026-11-08 in the iPhone 17 simulator (iOS 27.2): styles, inline styles and IPC work; a `fetch` to another origin and `eval` are blocked. Plain `ios dev` was checked the same day, with hot reload.
- **Workspace**: `crates/core` holds pure logic (no Tauri, no platform) so it is tested on Linux CI; `src-tauri` is the shell (commands, events, key storage, lifecycle); `bridge/` is a separate binary for the Mac.
- **UI**: Svelte 5 + Vite + TypeScript. Chosen for its small bundle, runes and built-in transitions for gpui's motion. Rejected: React (more runtime and re-render care for the live terminal), SolidJS (smaller ecosystem, motion by hand), no framework (routing, state and motion by hand).
- **Svelte + Vite, without SvelteKit**: the app is a few screens inside one WebView, where routing is state. The `svelte-ts` template of create-tauri-app 4.7 is SvelteKit with `adapter-static`; it was rejected for file routing the app does not need, server rendering to turn off, and `svelte-kit sync` before every check. The frontend is set up by hand around `@sveltejs/vite-plugin-svelte`.
- **Dev server**: Vite on port 1420 with `strictPort`, the port `tauri.conf.json` expects. When the app runs on a phone, `tauri ios dev` sets `TAURI_DEV_HOST` to the Mac's address, Vite listens there and hot reload goes over its own WebSocket on 1421; without it Vite stays on localhost, which the simulator reaches.
- **Platform order**: iOS first (simulator and iPhone); Android gets its own task (Keystore, keyboard).
- **Native projects in git**: `src-tauri/gen/apple` and `gen/android` are versioned, since they carry the Info.plist, the camera permission and the entitlements. What Xcode and the builds write inside them stays out (`.gitignore`): `src-tauri/gen/**/build`, `xcuserdata/`, `DerivedData/`, `*.xcuserstate`, `Externals/` (where the Rust build leaves `libapp.a`) and `Pods/`, besides the `.gitignore` that `tauri ios init` writes in `gen/apple` (`xcuserdata/`, `build/`, `Externals/`). `src-tauri/gen/schemas` is regenerated by every build, so it is ignored too.
- **`gen/apple` as `ios init` wrote it**: `project.yml` is xcodegen's source and `cornercase-mobile.xcodeproj` its output; both are versioned: the Tauri CLI regenerates the project from `project.yml` (it did on `ios init` and again on the first `ios dev`), and Xcode opens the `.xcodeproj` as it is. A change to the project goes in `project.yml`. Bundle id `dev.usecornercase.mobile`, iOS 15.0 as the minimum, the Rust library linked as `libapp.a` and built by Xcode's "Build Rust Code" phase through `pnpm tauri ios xcode-script`. The entitlements are empty and the Info.plist has no permission yet; the `Podfile` has no pods. `project.yml` lists `Externals/` and `assets/` as sources but neither is in git (one is ignored, the other empty); the Tauri CLI creates both before it runs xcodegen, so `pnpm install && pnpm tauri ios dev` works from a fresh clone (checked on 2026-11-08), while `xcodegen generate` by hand in one fails. Checked live on 2026-11-08 with Xcode 27.2, the iOS 27.2 simulator (iPhone 17), xcodegen 2.46.0 and CocoaPods 1.17.0.
- **`features = []` in `src-tauri/Cargo.toml`**: `tauri ios init` rewrote `tauri` and `tauri-build` in that form, the one in which the CLI keeps their features in step with `tauri.conf.json`; the manifest keeps it, so the CLI's next run leaves the file alone.

## Versions

Chosen on 2026-11-08, the latest stable of each unless said otherwise.

- Rust 1.99.1 (Tauri 2.12 needs 1.90), pinned in `rust-toolchain.toml` with `aarch64-apple-ios` and `aarch64-apple-ios-sim`, so rustup brings the iOS targets with the toolchain.
- Tauri 2.12.5, tauri-build 2.7.4, `@tauri-apps/cli` 2.12.4. Tauri 3.0 is an alpha: not used.
- Svelte 5.57.3, Vite 8.3.6, `@sveltejs/vite-plugin-svelte` 7.3.1, Node 22, pnpm 12.18.0.
- **pnpm, not Yarn**: Tauri's and Svelte's templates and docs use it; its strict `node_modules` fails on a package imported without being declared; pnpm 12 refuses versions published less than 24 hours ago, a guard against compromised releases. Rejected: Yarn 4, whose strength is Plug'n'Play, which breaks svelte-check, the ESLint plugins and the Tauri CLI; with `node-modules` it brings nothing pnpm lacks (decided on 2026-11-08).
- **TypeScript 6.0, not 7**: 7.0 has been npm's `latest` since November 2026, but svelte-check accepts `^5 || ^6` and typescript-eslint `<6.1.0`, and create-tauri-app pins `~6.0.3` too. TypeScript is `~6.0.3` and Dependabot ignores its majors; move to 7 once both tools accept it.

## Dependencies

- `tauri`: the app shell. Only its default features; no plugins yet.
- `tauri-build`: `src-tauri/build.rs`, which turns `tauri.conf.json` and the capabilities into the context `tauri::generate_context!` embeds.
- `@tauri-apps/cli`: `pnpm tauri`, for `ios init`, `ios dev` and the builds. `@tauri-apps/api` comes with the first command the UI calls (task 013), so that no package sits unused.
- `svelte`, `vite`, `@sveltejs/vite-plugin-svelte`, `typescript`: the UI and its build.
- No `@types/node`: `vite.config.ts` reads one environment variable (`TAURI_DEV_HOST`), so it declares the `process` it uses instead of pulling in Node's types for the whole config.
- `svelte-check`: type checks `.svelte` and `.ts` files (`pnpm check`).
- `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-plugin-svelte`, `globals`: `pnpm lint`, in flat config through ESLint's own `defineConfig` (typescript-eslint deprecates its `config` helper in its favour); `globals` declares the browser's globals.
- `vitest`: the UI's unit tests, configured in `vite.config.ts` so they share Vite's plugins. They render components with `svelte/server`, which needs no DOM; jsdom stays out until a test needs a browser. Vitest does not process CSS by default, so `tokens.css?raw` and `base.css?raw` would arrive empty; `test.css.include` lets only the `?raw` imports through.
- `serde` (with `derive`), `serde_json`: the bridge's JSON messages in `crates/core` (`design/bridge.md`); refusing unknown keys and wrong types is serde's work rather than hand-written checks. Both were already in `Cargo.lock` through Tauri. `bridge/` also takes `serde_json`, to write each `BridgeMessage` as the text of a WebSocket frame.
- `base64`: decodes `stdin_base64` in `crates/core`, with the standard alphabet and padding, so a malformed message is refused instead of guessed at. 0.23, the version Tauri already brought into `Cargo.lock`.
- `rstest` (dev, in `crates/core` and `bridge/`): the tables of named cases (`#[case::name]`) the Rust tests use, as in cornercase-terminal.
- `clap` (with `derive`) in `bridge/`: the bridge's options (`--cornercase` for now; task 005 adds the listening ones), as in cornercase-terminal and with its features: no colours, help, usage, error context and suggestions for a mistyped option.
- `cornercase-core` in `bridge/`: the bridge reads and writes the protocol types that live in the core, so the app and the bridge cannot drift apart (`design/bridge.md`).
- `tokio` in `bridge/`: runs the cornercase command, reads its stdout and stderr line by line and writes its stdin without blocking the bridge (`design/bridge.md`). Already in `Cargo.lock` through Tauri; the bridge turns on `process`, `io-util`, `rt`, `sync`, `time` and `macros`, and `net` and `signal` for the WebSocket server, which listens on TCP and stops on `SIGINT` and `SIGTERM`.
- `tokio-tungstenite` in `bridge/`: the WebSocket server, with only its `handshake` feature (no TLS: the bridge is for development, `design/bridge.md`). `accept_hdr_async` hands the request to a callback before the upgrade, where the token and the path are checked, and its `WebSocketConfig` bounds what is read and the write buffer. The tests also turn on `connect`, for `connect_async` as the client. 0.30, the version cornercase-terminal's `tungstenite` is at.
- `futures-util` (with `sink` and `std`) in `bridge/`: `StreamExt` and `SinkExt` over tokio-tungstenite's stream, which implements the `futures` traits rather than its own methods. Already in `Cargo.lock` through Tauri and tokio-tungstenite.
- `rustix` (with `process` and `fs`) in `bridge/`: signals the cornercase command's process group (`kill_process_group`) when it is killed or dropped and looks at whether it still has members, and asks the system whether this user may run the binary (`access` with `X_OK`, not any execute bit), with a safe API instead of `libc` and `unsafe`, as in cornercase-terminal and at its version (`design/bridge.md`).
